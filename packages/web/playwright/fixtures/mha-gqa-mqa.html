MHA / GQA / MQA：一个旋钮，两笔账

同一个模型有 32 个查询头，却在上下文里只保存 8 组 K、V。这一页把「为什么能这样共用、共用之后谁变谁不变」按给你看：左边的组数、容量会随旋钮走，右边的 32 份查询工作一动不动。

① 先说机制：为什么 32 个查询头可以只带 8 组 K、V

每个 token 的输入先被投影成三样东西：查询（q）、键（k）、值（v）。注意力只做两步：先用 q 与上下文里每个 token 的 k 打分，决定「该看谁」；再用这些分数把每个 token 的 v 加权汇总，决定「取回什么」。

32 个查询头 ＝ 32 套 q。同一个 token 上，模型同时提出 32 个不同的问题，各自得到一组分数、各自汇总出一份输出。这一步的份数由「要问多少种问题」决定，省不掉。

K、V 不是配给某个头专用的，而是「被查的那份数据」。一组 k 定义「什么算相关」，一组 v 是「可取回的内容池」。上面两步里没有任何一处要求每个 q 配一份专属的 k、v —— 所以同一份 K、V 完全可以供多个 q 使用，这就是共用的机制基础。

代价也要看清：同组的几个头从此必须接受同一套「相关性标准」和同一个「内容池」，模型能表达的关系种类随之变少。省下来的是上下文里要保存、要读取的 K、V 份数，不是查询这一侧的工作。

不降。右边那一行式子里没有组数：每个查询头仍旧各自打分、各自汇总，累计运算量还是 4 × 32 × 128 × Npair。

变的是「被查的那份数据」：一次读入的 K、V 可以供同组的多个查询头复用，所以省下的是上下文状态容量与读写量——以及键值投影的参数。把「省读写」当成「省这部分运算」，是这一节最容易踩的坑。

③ 带得走的规则与一次对账

把 KV 组数减半 → 键值投影参数与上下文状态容量都减半；查询头数不变 → 查询与上下文交互的运算量仍按原来的头数累计。

换个说法：层数或 KV 头数减半，每处理一个新 token 的增长速度也减半。所以在上面那块面板里，k 与 N 是同一个乘法的两端：N 决定「有多少个位置要存」，组数决定「每个位置存几份」。

一条可以自己核对的算术：GQA 档每 token 追加 144 KiB，8192 个 token 就是 144 KiB × 8192 ＝ 1.125 GiB，与书上的 1.125 GiB 对上（同一张表也把它写成 1,152 MiB）。

  • 把 k 从 4 调到 1：组数 ×4、每 token 字节 ×4、容量 ×4，而右边的 32 一直没动。
  • 把 N 从 8192 拉回 128：容量按比例缩小，组数与两侧的份数都不变。
  • 留给你的一问：既然组数越少越省，为什么不全用 MQA？提示就在「不动的一栏」里那两条 32。

口径与来源

本轮读到的书上原数：32 个查询头、8 个供查询使用的 KV 头、每头 128 维；Qwen3-8B 让每四个查询头共用一组 KV；四头单层例中 MHA／GQA／MQA 需保存的 KV 份数为四、二、一，GQA 在该例中把上下文存储量减半；若给每个查询头单独保存，容量是当前配置的四倍，全部共用则是八分之一；实际 GQA 配置保存 8192 个 token 需 1.125 GiB；每新增一个 token 追加 144 KiB，层数或 KV 头数减半增长速度也减半；投影表中 Q 投影为 m×4096 → m×4096，K、V 投影为 m×4096 → m×1024、共 2 个矩阵，QKT 与 AV 一行为 4×32×128×Npair 且无新增投影权重，以上均按 36 层；数值表里 Qwen3-8B（BF16 GQA）每 token 147,456 字节、8K 全局历史 1,152 MiB。

本页自己算出来的数（不是书上原数）：每 token 的 K、V 字节 ＝ 36 层 × 组数 ×（K、V 各 128 个数）× 2 字节（BF16）；状态容量 ＝ 该值 × N；键值投影参数量 ＝ 36 层 × 2 个矩阵 × 4096 ×（组数 × 128）。于是在 N ＝ 8192 时：MHA 档 576 KiB／4.5 GiB，k = 2 档 288 KiB／2.25 GiB，k = 4 档 144 KiB／1.125 GiB，k = 8 档 72 KiB／576 MiB，MQA 档 18 KiB／144 MiB。

单位一律用二进制的 KiB／MiB／GiB（1 KiB ＝ 1024 字节）。本页也没有把共用说成免费的：它改变的是上下文状态的容量与读写量，代价是同组的查询头共用同一套相关性标准。
