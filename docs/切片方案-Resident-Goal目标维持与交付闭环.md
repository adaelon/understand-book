# 切片方案：Resident Goal 目标维持与交付闭环

状态：2026-09-25 G0–G5 已完成工程实现；G6 章节自然请求已交付页面，其余自然场景与发布验收未完成。决策见 [ADR-0136](adr/0136-resident-goal-lifecycle-and-delivery-completion.md)，验证见 [G0–G3 记录](performance/resident-goal-g0-g3-20260925.md)与 [G4–G6 记录](performance/resident-goal-g4-g6-20260925.md)。本方案可由现有 Resident 独立实施，TutorSession、TutorLoop、LearnerContext 等仍为未实现的教学设计。

## 0. 问题、目标与基线

目标：Resident 持续围绕用户任务选择行动，准确区分已做工作、尚缺交付与本次运行的停止原因；同聊天后续请求能从有效成果继续任务。

2026-09-25 真实会话 `chat_1790313507677_60` 中，用户在“带我读多agent协作”之后提出“可以把这一章的内容富文本演示给我看吗，我想看一下整体”。第 1 轮能力发现命中 `presentation.author`，随后十二轮共调用 39 次工具：19 次正文读取、5 次搜索、13 次来源呈现、1 次结构查询、1 次能力发现。制作、预览及交付调用均为零。终局为 `incomplete=true`、`TURN_LIMIT_EXCEEDED`，回答仅有 Markdown，却自称“整体富文本演示”。

事故定位来自本机私有 `agent-history.json` 的消息与工具轨迹；该文件持续变化，不作为可移植测试夹具。G0 提取最小脱敏失败轨迹到测试数据，保留上述用户请求、工具结果与终态，不复制完整私人历史或配置。

| 现有能力 | 当前事实 | Goal 接入目的 |
| --- | --- | --- |
| `AgentChatSession` / `AgentChatTurn` | 保存会话、回合、结果、压缩检查点 | 保存跨 Run 的任务及回合关联 |
| `RunContext` | 持有当前运行证据、预览、已交付引用与取消令牌 | 为本次运行提供 Goal 快照与事实反馈 |
| `TurnProgressLedger` | 定位、证据、综合、最终回答阶段 | 保留其证据用途，任务进展另行表达 |
| `CompactionDraft.active_goal` | 来源约束的历史摘要 | 保留历史交接作用，不承担 Goal 权威状态 |
| `tool_loop_budget_instructions` | 每次采样可见预算，默认十二轮 | 根据目标缺口收敛，不只提示材料足够就作答 |
| `presentation.author` | 写入、预览、观察、交付的实际合同 | 提供网页交付的完成证据 |
| `finalize_agent_turn` | 验证引用并提交历史；回合终态与 incomplete 分离 | 在同次历史提交中确认 Goal 完成 |

## 1. 所有权与生命周期

首版由 Server 在 `AgentChatSession` 内保存 Goal，Runtime 定义任务语义与更新规则。Goal 的作用域是该聊天及其当前书；一轮运行引用所服务的 Goal。已有 Profile 中的长期目标、BuildIntent 的构建目标和未来 TutorSession 的学习意图各自保持原所有权。

| 角色 | 职责 |
| --- | --- |
| 用户 | 提出、调整、取消或替换任务要求 |
| Resident Agent | 解释目标，选择方法，维护工作焦点，提出完成 |
| Runtime | 投影目标与实际进展、处理更新、核对交付条件、遵守预算与取消 |
| Server | 保存任务及回合引用，执行原存储和页面权威操作，提交一致终态 |
| Reader UI | 展示当前任务与实际状态，发送继续、修改和取消意图 |

Goal 状态首版取 `open | completed | cancelled | superseded`。`open` 可以暂时没有运行；等待输入、超限、错误、中断是最近一次执行的停止原因，不扩成一套自动调度状态机。每个聊天可保留多个历史 Goal；一次 Run 服务一个当前 Goal，其他未完成任务不自动执行。

```text
明确的新任务 → open
open + 用户调整同一任务 → 更新要求，仍为 open
open + 有效交付并成功提交 → completed
open + 用户取消任务 → cancelled
open + 用户明确以新任务替换 → superseded；建立新 Goal
open + Run 超限 / 出错 / 停止 → 仍为 open，保存具体缺口
completed + 后续修改产物 → 建立关联该产物的新 Goal
```

“停止当前生成”只停止 Run；“不要做这个演示了”取消 Goal。预算停止后不自动续跑；用户“继续”或“重试”才启动新的既有预算 Run。语义不明确时询问实际影响范围的问题。

插入一个短问题可以建立并完成独立 Goal，保留原未完成任务；明确换题不把旧任务带入新请求。同一聊天存在多个可能对象时，优先使用用户选中的消息、产物或任务；缺乏明确对象才澄清。“继续”不能复活已取消的任务。

未来接入 TutorSession 时另定关联关系。Goal 完成只表示一次交付任务完成，不表示读者掌握，也不创建、切换或结束教学会话。

## 2. 数据合同与建立入口

以下为实施合同的逻辑形状，Rust 类型名可在对应切片按现有命名落定。

```text
ResidentGoal {
  id, revision,
  origin_turn_ref,
  intent: { user_message_refs, interpretation },
  scope_and_constraints,
  requirements: [{ id, description, basis, verification }],
  working_state: { focus, open_questions, next_move },
  result_refs,
  status,
  last_stop_reason
}

basis = 用户消息引用；Agent 自选方法另存 working_state
verification = 内容判断 | 页面交付 | 已请求的 Reader 操作
result_refs = 既有证据/回答/确切呈现版本/实际操作结果的引用
```

`intent.interpretation` 与 `working_state` 是 Agent 判断；工具执行与交付结果是宿主事实。`requirements` 记录有用户依据的要求：用户明确指定网页时，交付网页是条件；用户只要求讲懂时，Agent 选择网页只是可变方法。首版复用已支持的交付类型，不为假想产物建立插件式验收框架。

原用户请求在回合预提交时绑定 Goal。主 Agent 在正常决策中解释意图、建立或细化要求；使用轻量 `goal.update` 控制工具更新工作判断，工具在需要任务管理的采样中直接可见，不先进行能力搜索。工具不能写入“已预览”“已交付”或直接标记完成；完成由正常终答路径提出并核对。

复杂任务在开展工作前建立要求，以便后续结束检查有依据。简单的直接问答保留原请求和最小任务状态，可直接终答，不要求固定的额外模型调用。G2 必须验证这一分支与 native/react 两种工具协议；普通回答不得因 Goal 接入变成固定的计划仪式。

对已有 Goal，`goal.update` 区分工作判断更新与用户要求修订；后者必须引用本次用户消息并说明对应变更。宿主能校验引用、作用域、既有要求是否被删除及结果是否真实；“该消息是否真的允许缩减目标”仍是语义判断。相关自然语言反例纳入 G6，不能宣称仅靠字段校验能完全解决目标误解。

同一目标改要求增加 revision，历史回合保留采用的要求版本和结果关联；旧版完成判断不自动满足新版要求。首版按现有单宿主串行运行保存必要的目标快照与回合关联，避免新增事件存储基础设施。

## 3. 决策循环与恢复

```text
用户请求 + 当前选中对象 + 已有 Goal
  → 选择继续/调整/新任务，绑定原始请求
  → 主 Agent 形成所需的目标解释及工作判断
  → 投影：用户要求 + 实际成果 + 尚缺交付 + 剩余预算
  → Agent 选择读取、制作、修改或回答
  → 现有工具执行并返回真实结果
  → 更新结果引用；变化时更新工作判断
  → 下一次决策或完成检查
  → 历史提交：本次结果 + Goal 状态
```

每次采样从当前 Goal 与既有账本构造有界 `ContextFragment`。必保留用户交付要求、当前任务身份和关键未完成项；正文、历史轨迹及完整页面按原机制按需获取。模型内嵌调用不重复注入整套任务历史，回答修补只取得保持目标及执行事实所需的片段。

Harness 自动更新“实际读到了什么、候选是否存在、预览是否有效、版本是否交付”；Agent 只在焦点、方法或待解问题发生变化时更新工作状态。调用次数、模型自报百分比与重复的 `goal.update` 不算实际进展，也不重置现有无进展守卫。

当前 `TurnProgressLedger` 继续服务证据路径。Goal 投影把“尚无页面”与“已有正文”同时展示；不把任务进度压成只能前进的读取→综合→终答序列，允许制作后回头补材料。

压缩后从持久 Goal 重新投影；`CompactionDraft.active_goal` 表示过去的目标摘要，对绑定了新 Goal 的运行以当前 revision 为准。旧聊天没有 Goal 字段时仍可打开，只在新的任务请求中建立，不批量推断全部历史目标。

Server 在接受目标变更及关键实际成果时，沿现有历史提交路径保存可恢复状态。重启恢复使用确切交付版本和可重读位置；历史正文回执不升级为当前正文证据。候选 ID 与能力激活只在原 Run 有效，不能因 Goal 持久化而跨 Run 重用。

未交付页面若无法按现有合同恢复，只保留“已尝试、尚未交付”的状态及有效材料；重建候选并重新预览。首版不承诺恢复任意半成品浏览器现场。

## 4. 完成检查与预算

完成分两步：Runtime 得到可交付的完成候选；Server 将回答、确切产物引用、回合终态与 Goal 完成状态一起提交。已有页面版本保存成功但历史提交失败时，Goal 不能显示完成，沿现有未保存结果处理。

```text
检查完成(goal, final_candidate, actual_results):
  核对该 Goal 当前要求对应的交付证据
  若有客观缺口：
    仍有预算且未取消 → 返回具体缺口，继续正常循环
    否则 → 保存部分结果与停止原因，Goal 保持 open
  若客观条件满足：
    主 Agent 根据材料和实际预览判断是否回应内容目标
    有未解决内容缺口 → 继续或保留 open
    已回应 → 按原来源及交付合同编译，提交完成候选
  Server 持久提交成功 → Goal completed
```

页面条件复用实际 `deliver` 与最终回答的引用绑定，不能仅检查“历史中存在任意页面”。内容判断明确针对当前 Goal、当前要求及实际版本，范围完全不符的旧页不能靠存在性检查冒充交付；语义相关性由 Agent 判断并通过自然请求验收观察。

纯文字问答通过内容判断及原答案交付合同结束；不要求网页。明确请求 Reader 操作时使用原权限与真实执行结果，Goal 不授予新权限。正式学习掌握状态不参与本方案的完成写入。

继续使用现有十二轮上限和已有页面交付宽限。`goal.update` 作为工具调用的实际采样计入原预算；返回缺口后的修正也计入预算。Goal 更新、改计划、完成检查失败均不能获得新预算。

预算投影同时显示未完成交付，接近上限时要求围绕缺口收敛：材料足够且页面未制作时优先交付，不因“有文字可答”而丢掉明确要求。工具调用顺序和制作时机由 Agent 判断，不规定第几轮必须进入某阶段。

超限后的禁用工具收尾仍可给部分答案；宿主明确展示“演示尚未交付”等真实缺口。若页面或 Reader 操作已在最后一轮完成、没有客观交付缺口，且收尾回答成功编译，则该轮可作为 Goal 完成候选，不因触及轮数上限而强制保持 open。仅有文字要求的预算收尾仍按部分结果处理。与实际交付矛盾的完成声明进入原回答修补路径；修补只纠正完成状态措辞，不重写内容事实，修补失败沿用原失败结果。停止原因、Goal 状态和最终文字必须一致。

**G0：冻结能改变判断的基线。**

责任位置：现有 Runtime orchestrator 测试、Server presentation author 测试及其测试数据目录。保留“发现 author 后始终读材料、最终只有 Markdown”的最小失败链，另加正常短答、已交付页面、超限和取消对照。冻结完成条件及验收请求；后续红绿回归以同一输入验证。模型轨迹夹具只证明运行控制，不代替真实模型的行为改善。

**G1：任务状态与会话持久化。**

责任位置：拟新增 `crates/runtime/src/goal.rs`；`crates/server/src/lib.rs` 的 `AgentChatSession`、`AgentChatTurn`、`finalize_agent_turn` 和既有历史存储；`agent_run.rs` 的准备与结果提交。以普通 serde 缺省字段读取旧历史。验证 Run 超限仍 open、用户取消 Goal、已完成任务的新修改、要求 revision、重启恢复；用真实临时目录触发保存失败，确认磁盘和可见状态没有假完成。该片不新增教学会话或迁移框架。

**G2：建立、调整与续接。**

责任位置：`agent_prompt.rs`、工具注册/暴露、`goal.rs` 与 `agent_run.rs`。实现主 Agent 的目标解释和 `goal.update`，补明确的当前请求与选中对象输入。测试“做网页→只修引用”不能删掉交付要求、“改成文字即可”可以调整、插入短问不覆盖原任务、多个对象需消歧、取消后裸“继续”不自动复活。直接定义问答不增加固定模型回合；制作任务目标更新的实际开销进入 G6 成本统计。

**G3：投影、实际结果与压缩恢复。**

责任位置：`RunContext`、`orchestrator.rs` 请求组装、`ContextFragment` 及 `compaction.rs` 消费路径。结合现有证据、AuthorResult 和呈现版本引用构造 Goal 视图。测试新增正文但页面为零时仍保留页面缺口；重复状态更新不算进展；压缩前后用户要求一致；重启后只复用有效材料引用、重新发现能力；旧候选不进入新运行。失败时修投影或生命周期，不放宽来源合同。

**G4：完成与预算控制。**

责任位置：`orchestrator.rs` 正常终答/超限收尾、`deliver_agent_answer`、`finalize_agent_turn` 及现有呈现引用校验。测试有文字但无所需页面、只有候选、只有预览、有效交付但未挂载、交付引用不属于当前任务、全部条件满足六种路径。再覆盖超限、停止、Provider 失败、提交失败及完成检查反复不通过，确认不会越过原预算。用脚本化响应验证控制路径，真实浏览器验证页面事实；不新增独立评审模型。

**G5：用户可见状态与接续。**

责任位置：Server 会话/回合视图、`packages/web/src/api.ts`、生成类型和 `components/RightRail.vue`。显示简短目标、真实未完成说明和可用的继续/取消操作；运行活动沿用原时间线。测试重启后“继续”、中途“解释这个词”、修改任务、取消任务与停止生成的差别。后续继续新建 Run，沿用同一 Goal 和仍有效成果；不默认继承旧工具权限或重放已成功操作。

**G6：真实模型与宿主验收。**

使用 G0 冻结的自然请求，在相同模型、材料、预算和宿主上对比原基线与 Goal 版本。必含本次章节总览请求、普通短答、明确只要文字、制作中调整要求、超限后继续，以及多个未完成对象。用户请求保持自然语言，不补“请先调用某工具”等工程步骤来帮助通过。

记录用户目标、模型与配置、停止原因、实际工具轨迹、Goal 变化、交付版本、预览截图、最终回答、模型采样数和 token 用量。用真实页面与工具回执判交付是否存在，人工结合原请求观察是否呈现全章主要关系；两类结论分别报告。工程测试通过不能替代自然行为验收。

先验证开发宿主，再覆盖实际 Windows Debug 桌面包及现有 Linux Reader 入口的保存/继续/渲染关键路径；只有完成相应验证才声明该宿主通过。真实手机教学体验不由浏览器视口验收替代。

## 6. 验证如何影响下一步

| 验证会发现的具体失败 | 若失败，下一步改变什么 |
| --- | --- |
| Goal 在压缩或重启后丢失，或旧摘要覆盖新要求 | 修持久归属与上下文优先级，暂停结束语义验收 |
| 停止 Run 被当作取消 Goal，或取消后自动恢复 | 修生命周期和 UI 动作映射 |
| 用户要求被 Agent 的工作计划无依据缩减 | 修目标更新入口及来源约束，保留语义失败样本 |
| 未交付页面仍标 completed | 修完成检查、当前要求与交付引用关联 |
| 版本已保存但历史失败仍显示完成 | 修最终提交顺序，复用既有未保存结果处理 |
| Goal 反复更新耗尽预算，或短答固定增加回合 | 减少更新频率、缩短投影，调整控制协议 |
| 工程路径通过，真实 Agent 仍沉迷检索 | 修决策反馈及缺口表达；不靠扩大预算宣布成功 |
| 页面交付了但没表达用户要看的整体关系 | 修 Agent 的表示选择与观察反馈；不降低验收为“有 HTML” |

每片只运行能判定该片行为的定向测试；实现所需的类型/编译检查随片执行。G6 的自然行为改善与既有 ED3/ED4 表达质量分别记录，不能将两种变化混为一种收益。

## 7. 已知限制

- 用户意图解释、材料充分性和表达质量仍含模型判断；来源引用及确定性完成检查不能保证语义理解永远正确。
- Goal 状态首版限同聊天及当前书；跨聊天任务延续、长期教学会话与学习掌握证据另行设计。
- 首版只能恢复已有合同下的有效结果；未交付候选可能需要重新制作，预览与工具激活不能跨 Run 冒用。
- 维持当前运行预算可能仍使大型任务部分完成；任务状态与后续接续解决诚实停止和连续性，不保证所有任务在一次 Run 内完成。
- 真实模型稳定收益、额外调用成本及各宿主表现尚未验证；G0–G6 完成前，不将本设计描述为已实现能力。
