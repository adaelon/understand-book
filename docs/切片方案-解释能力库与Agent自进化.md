## 0. 目标与完成定义

让 Agent 从真实讲解、实际运行和用户反馈中，持续形成更会选择、制作和验证解释的能力。持久积累的基本单位是**语法卡、可运行最小作品和使用证据组成的解释能力单元**。下一次独立任务能发现它、读取它的代码、按新内容改写它，并产出经过验证的解释，才算能力进入使用。

首阶段的改进对象是解释方法、示例实现、选用方式和验证方法。模型权重保持现有配置；新旧方法用相同模型、工具和预算对照。首轮采用开发期的版本化资产更新和现有构建发布路径，闭环可以由 Agent 执行提案、制作和验证，采用决定与版本切换须有具体证据。

首轮完成需要贯通以下事实：

1. 一张可按理解障碍选择的语法卡，附一份能在现有演示宿主运行的最小作品。
2. Resident 从正式入口读到卡和源码，完成新题适配；交付版本保留所用能力单元的确切版本。
3. 读者能对确切演示版本选择喜欢或不喜欢，修改、撤回并选填原因。
4. 一个有真实依据的案例产生候选改进，完成新旧对照、独立迁移和相关回归，形成采用、保留旧版或继续修改的明确结论。
5. 若采用，后续独立运行确实加载采用版本；若不采用，旧版继续生效，失败和否决理由保留。

这些完成条件分别证明工程接通、局部方法收益和采用生效。关于“更容易理解”的学习效果结论，另以读者在新例子上的表现支持。

## 2. 解释能力单元

### 2.1 一个单元承载什么

每个单元采用一个稳定 method_id 和递增 revision。该 revision 同时固定语法卡、最小作品全部源码、运行说明及预期观察；任一行为或适用边界变化都形成新版本。验证报告另外记录评测合同版本。

| 内容 | 必须回答的问题 |
|---|---|
| 语法卡 | 读者卡在哪里？要呈现哪个关系？何时适用、何时应选更简单的表达？ |
| 表达配方 | 用什么对象、变化、对照、注意提示和交互，把关系变得可观察？ |
| 可运行最小作品 | 完整入口在哪，依赖是什么，怎样启动，哪些动作应得到什么结果？ |
| 适配说明 | 哪些结构可以复用，哪些变量、公式、条件、例子和来源必须重做？ |
| 使用证据 | 从哪个真实案例提炼？在哪个独立新任务使用过？遇到过什么失败？ |
| 采用信息 | 当前是候选、已采用还是已退役；适用范围、替代版本和决定依据是什么？ |

语法卡是针对关系的可组合配方。例如“追踪一次离散更新”“保持共同条件比较一个因素”“整体与部分对应”“从证据到结论”“正例与边界反例”。主题名、作者风格和渲染库可作辅助标签，但选用依据是当前理解障碍。

SE1 首次制作一个完整单元；当前首批库已扩展为八类解释关系，后续按真实任务补充。一个成功页面可以成为案例，也可以只贡献局部方法。重复使用暴露共同结构后，再提取小型通用函数。

### 2.2 首张卡的具体草案

**名称：追踪一次离散更新。**

- **理解障碍**：读者混淆当前状态、更新量与下一状态，或者把动画中间帧当成算法实际迭代。
- **要解释的关系**：在明确条件下，当前状态经一次计算得到下一状态；几何位置、公式与文字指向同一步。
- **配方**：固定同一对象身份；标出当前值和更新方向；展示更新量；推进到下一状态；用相同强调标记连接图形、公式和读数。
- **最小作品**：以二次函数上的一次梯度下降为初始内容，显示曲线、当前点、梯度/更新箭头和下一点；提供前一步、后一步、播放、暂停和重置，并支持现有 scene 定位与恢复。
- **可复用部分**：语义步与插值进度分开、确定性渲染、图文同步、暂停后的现场恢复、对象对应的表达方式。
- **必须重做部分**：变量含义、更新公式、成立条件、参数范围、边界行为、解释措辞及原文依据。
- **适用边界**：连续动画用于连接两个实际状态。只有静态定义或一句措辞修订时，优先使用文本或静态关系；物理连续过程须使用自己的时间模型。
- **预期观察**：切换步骤后公式、点和文字一致；回退与重复定位给出相同结果；非零小数现场保存恢复保持原位置且暂停；参数边界与正文说明一致。

这里的数学例子用于使配方可执行。迁移时将它改为 Newton 迭代等新关系，必须重新核对导数、零分母、失败条件和说明；保留同一动画外形不能证明迁移成功。

首个作品固定 f(x)=(x−2)²、初值 x₀=4、更新 xₖ₊₁=xₖ−2η(xₖ−2)，默认 η=0.25，展示前 8 次更新。独立核验可使用 xₖ−2=(1−2η)ᵏ(x₀−2)：η=0 静止，η=0.5 一步到达最小值，η=1 等幅往返；0<η<0.5 同侧接近，0.5<η<1 交替接近。可选 η=1.2 展示在该初值下发散。控件支持范围为 0–1.2，语义迭代值与仅供画面连接的插值位置分别显示。

### 2.3 资产组织与运行合同

SE1 的历史目录如下；候选清单与验证材料见 [SE1](performance/explanation-evolution/se1/README.md)。当前正式 catalog revision 2 已登记八个单元，统一增加 example/author.json；完整清单见 [模板库](../skills/presentation/methods/README.md)：

~~~text

  discrete-update/
    v1/

~~~

catalog.json 保存简短的 id、revision、名称、理解障碍、适用边界、所需技术能力和入口。每个版本的完整文件清单随资产登记，避免运行时猜文件名。首版例子使用自包含 HTML/SVG/JavaScript，可直接本地打开；正式验收经现有 presentation.author → preview → deliver → Reader 路径。若后续选择 Konva 或 Manim，运行说明注明项目固定版本与既有资源入口。

每份最小作品只承载一个主要解释关系，附启动方法、必要参数、预期观察及少量能发现具体错误的断言。它是可改写的工作起点，保持真实计算、来源和 Reader 合同。静态图片、伪代码、整页成品链接或仅列回归注意事项，都不能代替这份可执行源码。

候选源码可以按上述结构保存，候选清单与验证材料放在该次实验目录；正式运行目录只登记已采用版本。SE1–SE3 在隔离的试验构建中登记首个候选单元，使用与正式路径相同的编译装配和工具入口，原计划由 SE9 决定进入正式目录；当前首批登记改按 ADR-0168 §8 执行。旧版本由版本库和采用记录回读，历史演示保留自身代码与资源。删除重复方法、缩小适用范围、组合已有方法，与增加新卡同样是有效改进。

## 3. Agent 如何实际使用

### 3.1 发现、读取、适配与记录

正式使用与后续演进路径如下（SE1–SE3 已实现，反馈与采用见后续切片）：

~~~mermaid
flowchart TD
    A[当前问题与来源] --> B[判断理解障碍与解释关系]
    B --> C[读取简短方法目录]
    C --> D[选用零个或多个能力单元]
    D --> E[读取确切版本的卡与最小作品源码]
    E --> F[按当前内容改写局部作品]
    F --> G[现有 preview 与内容核对]
    G --> H[交付演示版本并记录使用关系]
    H --> I[实际使用与用户反馈]
    I --> J[案例与候选改进]
    J --> K[新旧对照、独立迁移、相关回归]
    K --> L{采用决定}
    L -->|采用| M[更新资产目录并构建发布]
    M --> C
    L -->|修改| J
    L -->|保留旧版| C
~~~

首版复用 presentation.author，SE2 已新增 read_method 操作，输入 method_id、revision 和可选 file/offset/length；默认读 card.md，返回登记文件清单、运行入口、所选文件正文及精确读取范围。Unicode 字符范围、预算投影和续读沿用现有源码读取合同。短目录随 Author 指导提供，普通无 Author 回答不加载；后续因实测体积增长再考虑检索。

语法选择和技术 needs 分开：Agent 先判断要表达什么关系，再选择 HTML/SVG、state、continuous_scene、Konva 或 Manim 等能力。prepare 仍管理当前阶段、framework、focus 和技术需要。选卡不改变来源访问和交付资格。

目录暴露、文件实际读取、候选声明使用分别留痕。SE3 的 write/patch 已接入 method_refs，每项包含 method_id/revision，可附 scope 说明作用局部。运行时从成功采样的实际 Provider 请求记录目录与已投影正文的文件/字符范围，保存为当前用户、会话、回合下的不可变输入记录；仅执行 read_method 尚不构成已观察依据。新引用须已登记并有本回合的读取依据；继承引用指向确切候选或交付版本，退役方法仍可从旧内容继承。候选保存当次输入记录快照，交付沿原持久化路径原样保存。作用局部是说明用途的记录，不新增持久分镜资源。

patch 省略 method_refs 时继承；提供时替换完整列表，因此替换局部时保留仍使用的项，移除已替换的项，[] 清空。write 不隐式继承，基版有非空使用记录时必须明确重新声明；新页省略时记录空列表。历史内容缺少字段时保持“未记录”，小修也不推断历史方法。read 返回使用关系，原候选与旧版本保持不变。验收同时看实际 Provider 输入和适配结果：登记存在、声明使用或读到文件，各自都不足以单独证明方法有效。

### 3.2 加载与版本生效

现有指导由 Rust include_str! 编译。SE2 的 runtime/build.rs 按选定 catalog 编译全部登记文件，presentation_methods 同时供指导目录和读取入口使用；新增文件登记进清单后随构建生效。构建默认选择正式目录，隔离试验以 UNDERSTAND_BOOK_METHOD_CATALOG 指定候选清单；运行中不读取或切换磁盘资产。

一次运行固定方法目录版本；中途采用另一版本不改变该次任务的输入。候选实验在隔离配置下加载指定资产组合，各组共同工具底座保持一致。正式采用需要更新登记、构建并按项目已有流程发布，后续运行再读取新版本。

新版本只影响之后的制作。旧演示的代码、内容 revision、现场与反馈保持原身份。回退改变之后运行的默认目录，旧交付继续可回读。

## 4. 用户喜欢与不喜欢

### 4.1 交互

演示宿主提供“👍 喜欢”“👎 不喜欢”两项，放在内容附近的轻量反馈区，独立于生成页面的 HTML。第一次点击即可保存；已选同项可撤回，另一项可改选。按钮支持键盘、明确选中状态和手机触摸，保存失败时给出可重试状态。

选择后可展开非必填的原因与一句补充：

| 选择 | 原因建议 |
|---|---|
| 喜欢 | 更容易理解、例子贴切、交互有用 |
| 不喜欢 | 没讲清楚、内容有误、画面难读、操作不便 |

反馈后保持原阅读现场。单击不启动模型修订；读者要继续处理问题时，可使用现有追问入口，把反馈及可用现场带入原对话。普通反馈不要求正式教学活动成立。

首版覆盖原对话演示、演示工作区及其附属窗口。笔记独立回看涉及保留演示的专有访问路径，扩展入口时沿用其确切引用与权限合同。

### 4.2 数据与归属

反馈由服务端当前用户身份和确切 PresentationRef 共同确定。原 session_id、turn_id 用于核对交付与访问关系；浏览器不指定其他用户身份。每名用户对同一内容版本最多保留一份当前选择，重新加载可读回；新 revision 单独评价，撤回后该版没有有效选择。

SE4 已保存的信息：

~~~text
reference: presentation_id + revision
交付归属: session_id + turn_id；用户取当前服务上下文
选择: like | dislike
可选: 原因列表、用户补充、PresentationFollowUp 现场回执
保存信息: created_at、updated_at、反馈修订号
~~~

首版使用现有私人演示存储中的版本级反馈记录，复用正常写入和额度边界。SE4 已接入同域的 read/set/clear 与 attach_state 端点；set 完整更新当前选择、原因和补充，clear 撤回，相同请求重试原样返回。每用户每内容版本一份当前文件，原子替换仅计算新文件的大小和数量。SE5 已接入原对话、工作区与附属窗口，客户端仅在保存得到确认后显示选中与已保存状态；原因和补充通过独立的可选表单更新。

反馈修订号由服务端推进，撤回也使原号失效；撤回后的空选择保留当前号。读取接口返回当前选择与该号，现场附加仅更新仍匹配的选择。这使“改选或撤回后又收到原快照”具有明确处理方式。

现场采集与选择保存分开：先保存反馈，再尝试使用既有快照与保存协议附上现场。现场附加必须匹配原内容版本和反馈修订号；改选、撤回或切页后的迟到快照不写到另一条选择。采集失败保留有效反馈并标记“无现场”，不补造参数，也不拿较新的现场替代。该约束对应页面快照等待期间用户确实可以继续操作的使用方式。

SE4 的空读返回修订号 0、空选择与空现场；有效改选或原因/补充变更推进修订号并移除旧现场，撤回保留空选择及新修订号。现场附加保持选择修订号，重复同一回执原样返回，另一现场回执拒绝覆盖。接口覆盖本地、多人对话别名、工作区及附属窗口；多人路径核对原出版授权，工作区再核对当前对话与 attachment。反馈不改变 Reader 或工作区 revision。确切字段、原因取值和调用顺序见 [SE4 API](performance/explanation-evolution/se4/README.md#api-与-se5-接入)。

私人反馈、原评论、演示内容及书源仍归原用户。原聊天删除后沿既有访问和保留关系处理；不借方法库读取失效的原聊天。进入共享能力库的是经整理的通用方法与可分享的独立例子，私人原文和评论保留在其获准的案例空间。

### 4.3 反馈如何影响判断

页面级反馈首先说明这一版整体体验。即使页面用了三张卡，也不能将一个赞同时算成三张卡的成功；需要局部描述、现场或进一步观察才能定位到其中的方法。只有总选择时保留页面级归因。

具体的“内容有误”可以触发原文和计算核对；“操作不便”可以触发真实控件检查；“没讲清楚”可以帮助诊断关系或例子是否合适。单条已核实的错误足以修复当前作品。方法的通用性仍由独立迁移和回归判断。

反馈不自动改写 ProfileFact、LearningEvidence 或掌握状态。重复出现的偏好可以成为待确认的个人偏好线索；公共方法采用与个人讲解偏好分别决定。没有点击表示缺少反馈，改票和多次打开不增加独立样本数。

首版以具体案例复核为主。未来展示统计时，明确有效选择人数、涉及版本和样本范围；采用率、点赞率与用户理解分别呈现，避免用一个总分替代判断。

## 5. 从案例到采用

### 5.1 两条工作路径

**当前任务修复**：读者指出问题或 Agent 观察到失败 → 定位原文/计算/页面现场 → 生成新候选 → 相关复查与正式预览 → 交付新版本。按当前问题的要求完成，已有 Author 生命周期负责候选和交付。

**跨任务能力改进**：原任务和修复保留 → 判断是否存在可复用经验 → 形成能力单元候选 → 冻结对照条件 → 独立新任务与相关回归 → 决定采用范围 → 后续任务验证实际使用。

跨任务路径可以由成功案例、失败案例或用户反馈发起。一次局部修复可以结束在第一条路径；提炼出的内容也可以只用于改卡的适用边界、修复最小作品，或删除多余指导。

### 5.2 案例与候选的最小记录

案例保存当时任务、理解障碍、来源版本、实际交付和现场、使用的能力版本、反馈原文、观察到的具体差异、修复及复查证据。可复现的操作、候选差异、图片、计算结果与用量足以支持诊断；RunActivity 元数据本身没有完整内容。

案例要区分事实与解释。例如“7+.999 恢复成 8+0”是观察，“输入吸附误用于恢复”是结合代码得到的原因判断。用户“不喜欢”本身只作为反馈事实。

每次候选说明一个具体假设：“哪些读者障碍下，哪项方法/代码变化，会改善哪个可观察结果，可能损害什么已有行为”。首轮一次改一个能力单元的一个主要问题；相关代码、说明和适用边界作为同一行为修改共同版本化。

~~~text
待诊断案例
  → 不提炼：仅修当前作品 / 已有方法已覆盖 / 证据不足
  → 方法候选
      → 修改后再评测
      → 保留旧版并结束候选
      → 采用：明确适用范围与可回退的上一组合
          → 后续使用证据
          → 保持 / 缩小范围 / 修订 / 退役
~~~

采用记录保存候选与基线、实验合同、逐任务结果、成本、决定理由和后续生效版本。首版使用仓库资产与本地案例/实验文件；这些概念无需先变成新的服务或工作流引擎。

SE6 已实现 `evals/semantic/explanation-case.mjs`：从明确选定的授权导出整理私有案例，核对原交付/修复及方法读取/继承关系，记录反馈导出时刻和确切现场。事实、原因解释与假设分别保存；缺失/不可用不以旧票或较新现场填补，页面反馈不分配给方法。公开索引只输出状态、数量和用量。输入和复现见 [案例合同](../evals/semantic/EXPLANATION_CASE.md)。

SE7 已对 D2 完成诊断，结论为“已有方法已覆盖”，不产生新版本；诊断另存为私有后续记录并连接 SE6 原案例，原始导出状态保持不变。当前四文件与 SE3 实际输入、HTML 与 SE1 最终交付逐字一致，已有精确恢复证据可沿用。SE1 候选仍待 SE8 独立比较，详见 [SE7](performance/explanation-evolution/se7/README.md)。

### 5.3 自动化边界

首轮实现可由维护者发起的一次有界改进运行：Agent 读取选定案例、提出候选、制作最小作品，并在已确定的运行预算内完成验证。通过后形成具体资产差异和采用记录，沿项目正常变更与发布流程生效。

形成稳定的首轮证据后，再按真实维护负担扩展自动发现案例和自动执行回归。线上反馈到达不直接修改正在运行的指导；运行失败、证据不全、收益不成立时，当前采用版本继续服务。自动化程度以可重复的闭环为依据逐步增加。

## 6. 验证与采用合同

### 6.1 不同证据回答不同问题

| 要回答的问题 | 主要依据 | 失败后采取的动作 |
|---|---|---|
| 最小作品和交付是否真的可用 | 真实运行、控件操作、状态恢复、Reader 三环境 | 修复实现；不进入收益比较 |
| 内容、条件和计算是否成立 | 原文、独立计算、实际图形与可读文字的一致性 | 修复内容并复查受影响关系 |
| 方法是否更适合当前障碍 | 同任务新旧结果、匿名呈现比较及明确理由 | 修改配方/边界，或保留旧版 |
| 是否能迁移到独立新任务 | 未参与提炼的新关系或新来源任务，重新制作 | 缩小方法适用范围或撤回候选 |
| 用户体验如何 | 喜欢/不喜欢、具体原因和现场 | 定位体验问题，区分个人偏好 |
| 是否帮助读者形成理解 | 新参数/新例子下的解释、预测或操作表现 | 修改教学设计；学习收益保持未证实 |
| 是否值得持续使用 | 整体质量变化、实际制作成本及后续维护负担 | 保留、局部采用、简化或退役 |

正式交付继续满足现有 320×420 touch、640×240 touch、960×720 mouse 预览与后续观察要求。关键关系另按风险补查；每次 preview 从新页面开始、每批最多四动作、read_selector 只对应末态等限制仍适用。相关完整规则见 [EX14](切片方案-EX14-视觉方法指导与关键解释时刻检查.md)。

### 6.2 可归因的对照

新旧组固定相同模型配置、任务和来源、初始状态、工具底座、生成/修复上限及评测合同。处理组只增加本次能力资产差异。目录、语法卡和源码读取消耗计入处理组上下文与运行成本。

分别记录 token、实际时长、工具和渲染调用、失败/修订次数；离线提炼与评测成本另列，说明在多少后续任务中才可能摊薄。若扩大预算才能成功，结论应明确依赖这项成本变化。

保留全部尝试和停止原因，按预先确定的顺序配对运行。主观呈现比较隐藏组别，并交换 A/B 顺序；技术正确性和来源判断使用独立依据。模型自评可提出检查位置，不能独立决定采用。

同一失败的变体和简单换数归同开发案例族。已读过留出题并据此调过候选，该题转为开发材料，补一个新留出任务后再判断迁移。真实材料和实际用户反馈持续进入案例库，合成任务补足局部覆盖。

### 6.3 采用判据

首批制作资产依据 ADR-0168 §8 的作品与接入验收登记。本节用于形成跨任务收益结论，后续有具体问题时执行：

1. 确认候选实际进入该组输入，并完成所要求的工程、来源和内容验证。
2. 确认目标关系有具体收益，且独立迁移成立；与该变化相关的已有能力没有已知回归。
3. 对照实际成本，决定适用范围与保留方式；质量相当且更复杂、更昂贵的候选保留为未采用。
4. 保存采用版本和上一组合，构建后在一条后续独立任务中核对实际加载与结果。

已核实的内容错误或回归阻止采用。检查未执行、迁移证据不足或结果冲突时标记待定，继续使用旧版。一次迁移仅支持已验证的关系与条件；跨领域通用性随着后续证据逐步扩大。

可采用的变化包括新方法、旧方法的新版本、更窄的适用范围、两个方法的组合或移除无收益内容。读取量、卡片数量与评测总分不作为独立的成功目标。

### 6.4 验证方法本身的改进

真实漏检可以形成独立的验证候选。先用已确认坏例说明它能发现原来漏掉的错误，再用已确认好例说明它不会把正确行为拒绝掉；规则只覆盖它有依据的性质。

验证合同修改后，新旧方法必须在同一个新合同下重新比较。原合同结果保留原版本，不能把新判分直接接到旧分数上宣称进步。若候选制作期间发现判据错误，先结束或暂停本批比较，修订验证合同，再开新批次。

确定性检查适合算式、位置、状态恢复和可达性；模型/人工判断补充解释关系。流畅、好看和通过执行各有自己的证据含义，验证器的改进也需要独立验证。

## 7. 首轮试点

### 7.1 历史案例的用途

[EX11.8 真实修订记录](performance/explorable-explanation-ex11-8-live-20260929.md)提供两个已归档例子：

- 学习率案例中，指定可见句子和 315 组数值/图形检查通过，readable_content 仍遗漏 η=0 的静止边界。它说明应按实际受影响内容核对页面与可读说明。
- 圆盘案例中，滑块端点的首修通过 84 组数值/几何检查及普通 Reader 操作，但把输入端点吸附用于精确现场恢复，导致合法的 7+.999 重开后变成整圈。后续修订恢复路径后通过，既有数学实现未改，原 84 组检查没有重复执行。

这些是历史版本事实。当前 continuous-scene 指导已包含精确位置与恢复要求，首轮先对照现有基线：若已有方法足以解决同类问题，优先把经验落实到可运行例子和明确适配边界，或不产生新候选。

### 7.2 试点任务组

| 任务 | 用途 | 观察重点 |
|---|---|---|
| D1：二次函数的离散更新 | 开发首个单元与最小作品 | 当前值、更新量、下一值；图/公式/说明同步；离散与插值分离 |
| D2：历史端点修订案例 | 诊断、回归及验证器改进的开发材料 | 输入量化与精确保存分别处理，合法小数恢复 |
| H1：另一类迭代关系 | 未参与提炼的迁移任务 | 新公式、新成立条件与新边界，保留可复用表达结构 |
| R1：已有静态页的小范围措辞修订 | 相关路由回归 | 原静态任务保持合理规模，使用卡确有必要才读取 |

H1 可选 Newton 迭代，但实际材料、用户请求和判定依据在 SE8 冻结；出题与核验材料独立于候选生成。已参与制作的具体题不能再作为留出。

首轮收益比较先采用现行方法 A 与“现行方法 + 完整能力单元”B。两组使用同一个已经接入 read_method 的共同底座；A 保持现行资产集合，B 的试验目录登记本次候选，区别只在资产与其读取内容。若需要判断代码例子相对于卡片文字的增益，再加“仅卡片”组，单独记录新增成本。这个对照是第二步问题，不阻断首轮接通。

用户反馈入口独立验收；工程用的模拟选择明确标记为测试数据。真实喜欢/不喜欢来自实际读者自愿选择，不能由开发者脚本生成后充当读者证据。

## 10. 已知限制

- 共同指导仍为 ex14.v4；SE1–SE7 已交付候选、编译目录、read_method、版本使用追溯、反馈存储/界面、有界案例整理和现有方法覆盖诊断。正式目录已有首批八单元；SE6 的真实案例来自历史 Agent 修复，没有实际读者投票或历史 method_refs，反馈行为验收仍使用工程数据。
- SE3 使用受控 Provider 返回工具调用验证真实输入、适配和交付，未验证自然模型选卡、跨题收益或读者学习效果。读取依据保留实际范围；读卡、读代码与声明使用分别记录，不将任意一项当作有效使用的充分证明。
- EX14.4–EX14.5 的自然模型比较、采用和完整 Reader 验收仍按原工作线记录，本方案不代替其未完成证据。EX11 的历史失败不自动等同于当前代码仍有同一缺陷。
- 本批尚无自然方法选择或收益对照结论；用户反馈存在自愿选择和样本稀疏。更广适用性和读者学习效果需要后续独立证据。
- 当前编译资产需要构建发布后生效；首阶段采用开发期闭环。在线自改发布、模型权重训练和跨用户原始反馈汇集尚无本方案的实现与授权。
- 能力示例可以不依赖 Manim；含媒体的后续单元按既有固定环境单独验证。首版反馈入口不覆盖删除原聊天后的独立笔记回看。
