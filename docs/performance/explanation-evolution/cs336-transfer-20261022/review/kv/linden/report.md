# linden 独立页面评审

主要计算、可容纳判定和稳定后的主图正确，完整讲解路径成立。需要处理两项会影响教学判断的问题：非整除容量边界把剩余/超出量显示成零，并把最大整数长度说成用尽预算；“T 翻倍”按钮在接近参数上限时实际只截到 32,768，未告诉读者这次没有翻倍。

## 方法与正确性结论

仅阅读本页指定 PNG、initial DOM 可见证据，并在浏览器操作本页。没有读取 HTML、项目源码、其他报告、runs 或组别，没有修改页面或调用线上服务。任意 T 通过页面提供的数值输入填写，B 通过原生范围控件方向键调整；按钮实际点击。截图等待稳定后采集。检验 960×720、320×640，以及 320 宽触屏模式。

独立推导：每 token、每序列保存 32×8×128×2＝65,536 元素；KV＝B×T×s/16,384 GiB，总量＝12＋KV。容量允许 T＝floor(196,608/(B×s))，实际控件再限制到 32,768。

| 已检验状态 B / T / s | 独立结果 | 页面结论 |
|---|---|---|
| 4 / 8192 / 2 | KV 4，总量 16，余 8 GiB | 正确 |
| 4 / 0 / 2 | KV 0，总量 12，余 12 GiB | 正确；蓝段消失 |
| 3 / 32768 / 2 | KV 12，总量 24 GiB | 正确；恰好装满仍可容纳 |
| 16 / 32768 / 4 | KV 128，总量 140，超 116 GiB；最大 T 3072 | 正确；红色条纹及说明一致 |
| 5 / 19660 / 2 | 可容纳，余 512 KiB | 判定正确；边界显示/文字有问题，见下 |
| 5 / 19661 / 2 | 不可容纳，超 128 KiB | 判定正确；边界显示有问题，见下 |
| 1 / 32768 / 2 | KV 4，总量 16，余 8 GiB；容量允许 98304 | 正确区分容量上限和控件上限 |

另外验证 s＝1/4 时默认 KV 分别为 2/8 GiB，固定项保持 10＋2 GiB；点击“再加一条序列”后默认 KV 变 5、总量 17；点击“T 翻倍”后默认 KV 变 8、总量 20。主图的三段、读数和当前参数解释相互一致。T＝0 有明确空缓存说明。

## 需要修正的具体问题

### 1. 小额余量/溢出被显示为零，非整除上限被说成预算正好用尽

复现：B＝5、s＝2，分别直接输入 T＝19,660、19,661。

容量计算为 196,608/10＝19,660.8，最大整数长度为 19,660。此时实际 KV＝11.99951171875 GiB、总量＝23.99951171875 GiB、余 512 KiB。页面统一保留三位小数，显示 KV 12.000、总量 24.000、余量 0.000；“每条序列最长”卡还写“到这一档正好把预算用尽”。后一句不成立：剩余空间不足以让五条序列各增加一个 token，但仍不为零。

T＝19,661 时实际总量＝24.0001220703125 GiB，超出 128 KiB。页面正确变成红色并判为装不下，且准确告诉读者需减少 1 token；但数值仍是总量 24.000，提示写“比 24 GiB 多 0.000 GiB”。因此相邻两个状态虽然判定正确，屏幕上的数值却无法解释差别，也与“等于上限算可容纳”的规则产生表面冲突。

范围内建议：边界附近用足够精度或 KiB/MiB 表示实际余量/超量；区分“最大可容纳整数长度”与“恰好用尽预算”。不需要改变现有容量公式。

证据：[19,660](nondivide-fit.png)、[19,661](nondivide-over.png)、[相邻状态文字](nondivide-over.json)。

### 2. “T 翻倍”按钮在靠近上限时执行截断，未解释这次没有翻倍

复现：设置 B＝4、T＝20,000、s＝2，点击仍启用的“T 翻倍”。

- 操作前 KV＝9.765625 GiB，页面显示 9.766。
- 操作后 T 变成 32,768，KV 变成 16 GiB，总量 28 GiB。
- 20,000 的两倍应为 40,000；实际动作只增长至控件上限，缓存没有翻倍。页面没有针对这次截断提供反馈，按钮仍叫“T 翻倍”。正文会根据新的 T 继续讲下一次理论翻倍，无法解释刚才发生的动作。

这对普通调参器或许只是范围限制，但本页明确用按钮帮助读者验证倍数关系，应让操作语义一致。达到无法完整翻倍的范围时，可停用并说明上限，或明确将按钮/反馈改成“增至 32,768 上限”。

证据：[操作前](double-near-limit-before.png)、[操作前控件值](double-near-limit-before.json)、[操作后](double-near-limit-after.png)、[操作后控件值](double-near-limit-after.json)。

## 阅读与图示

这页从先给初始答案，转到 K/V 的用途、单 token 元素数、T/B 的复制、固定预算，最后给交互与三个问题，能够不操作也读完整。乘法用不同层/头/元素索引各自占内存来解释，符合应用工程师已有的数组经验；s 被说明为元素字节数，固定权重不随其变化。

图先画一条序列中的 token 小块，再展开其中一块的 32 层，每层标注 8 头×128×2。这个展开关系直接解释 T 为什么乘整份记录，手机上层标签和乘数也可辨认。[手机结构图](mobile-diagram.png)

容量主图有 0/6/12/18/24 GiB 刻度，权重、其他开销、缓存用不同颜色。溢出时只在 24 GiB 范围内画条纹，并明确说明超出部分在条外、图中画不下；同时给出 116 GiB 超量，没有把截短图冒充全量。[手机最大溢出](mobile-max-overflow.png)

320 宽下主要正文与控件没有横向越界，交互区域高 44px。T 的数值输入可以精确设置 19,660，并同步到滑杆和读数，适合检验容量边界。[手机控件](mobile-controls.png)、[320触屏输入后的状态](mobile-touch.json)

两项较小但具体的阅读问题：

- 千位分组使用的空格允许数字断行；手机结构图后的计算步骤将“1 024”拆成两行，后面的解释把“8 192”拆成行末“8”和下行“192”。完整数值应保持同一行。[结构图及计算步骤](mobile-diagram.png)、[倍数解释](mobile-explain.png)
- 手机对照表初始只露 B、s＝1、s＝2，缺少明显提示右侧还有 s＝4。已实际横向滚动并确认第四列可访问，因此是发现性问题，不是内容丢失。[初始表格](mobile-table.png)、[横向滚动后](mobile-table-wheel.png)、[滚动证据](mobile-table-behavior.json)

篇幅不作为缺陷；编号结构与分步推导能支持连续阅读。没有发现需要扩大检验范围的图表计算错误。
