# stone 匿名教学页独立评审

评审对象只来自 blind/alarm/stone 的截图、可见正文/控件记录和 index.html 实际渲染页面。实际在 sandbox="allow-scripts" 的 iframe 中以 960×720 和 320×720 阅读、滚动、点击预设与用键盘调整滑块；未读取 HTML 源码、项目源码或其他评审。以下结论只针对这一页。

这页已经提供一条可以不操作就读完的完整故事：先给默认结论，再用分母表与逐步乘除解释四格，进入交互，随后解释基率、两个性能参数和无报警。主要数值关系及无报警处理是对的。实质问题在一处核心文字错误，以及预设按钮实际改动超出名称所说的参数。显示精度与边界段落另有表达限制。320 宽度下还有一个直接影响“看懂分母”的阅读断点。

**已经有效的教学表达**

- 开头直接把“590 件报警、95 件真缺陷、16.1%”与“100 件缺陷中 95 件报警”并排说清。即使不操作，读者也能先得到两个问题的不同答案。
- 默认四格从 10000×1% 起算，逐步得到 95、5、495、9405，再做 95÷590；没有先抛一个需要背景知识的公式。后来才把这个过程压缩成公式，顺序适合懂乘除的入门者。
- “两个 5%”一段把缺陷人群中的漏检和正常人群中的误报摆到一起，明确落在 100 与 9900 两个分母上。它让 495 为什么压过 95 变得具体。
- 基率对照表包含 0.5%、0.1% 情况与半件期望，解释 p 降低时真报警缩小、误报基本不动；提高 d 与降低 f 的表也让人看清漏检和误报分别发生在哪一群。
- “误报率 5%”与“报警里 83.9% 是误报”有专门一段，定义基本清楚。无报警界面明确用 —、说明分母为0，又与“有报警但全错”的0.0%区分，处理完整。
- 滑块本身只改所选参数；操作后数字、四格表、条带的方向一致。没有观察到随机模拟或整数批次抽样行为。

**需要修正的实质问题**

1. **核心分母对照表后的“三行分子相同”是错误陈述。** 页面原文：“三行的分子里都有同一批95件零件。”紧邻表格第二行却明确是“无缺陷却报警495件”。只有第一行“检出率”与第三行“报警中真缺陷比例”共享95件，误报率的分子是另一群495件。这个错误恰好出现在教读者辨别分母的位置，会把不同真实状态的人群重新混在一起。将“三行”改为“第一行和第三行”，并明确第二行计的是495件误报，即可在本范围内修正。证据：提供的960-first.png、320-scroll-2.png；本次320-denominator-table.png。

2. **预设按钮会悄悄覆盖未提及的参数，破坏连续探索。** 复现：点“把误报率降到1%”，此时p1/d95/f1；再点“换成更干净的一批p=0.2%”，实际变为p0.2/d95/f5，f回到5%。同样，先降低f再点“把检出率提到99%”，f也回到5%。按钮名称表达的是单一改变，交互附近没有说“这些都是从初始值出发的整组情景”。如果第二次真的只换批次p，前一组应变成正确报警19、误报99.8、报警118.8、可信度约16.0%；页面实际给518和3.7%，混入了检测器误报率改变的影响。建议按钮只改名称所指参数，或明确标为带全套p/d/f值的基准情景。证据：960-preset-before.png、960-preset-after.png；behavior-cases.json中的sequence-lower-f-then-cleaner-batch。

**显示与文字表达限制**

**正常滑块刻度产生两位小数时，件数被无提示地缩成一位或整数。** 复现：p0.1%、d95%、f0.1%。9990×0.1%=9.99件误报，正确放行为9980.01件，报警为19.49件；正文、图例和四格表写成10、9980、19.5，均未标“约”。实际显示的48.7%仍与正确期望相符，不能由此断言内部计算取整；这是呈现精度限制，严重性低于上面的分子身份错误。半件情景保留得很好，这组同样是公开控件的正常操作。若教学目标是让读者逐项核对，可保留本控件刻度产生的两位小数，或对件数统一标明近似精度。证据：960-two-decimal-rounding.png、behavior-cases.json中的two-decimal-expectations。

**无报警章节把一个特例的500接在泛称f>0之后。** 同一段完整上下文为：“按这里允许的参数范围，报警为0只会出现在f＝0且（p＝0或d＝0）的组合里。若p＝0而f大于0，报警照旧出现，只是全部来自无缺陷件——这时比例是0.0%，因为分母500件报警仍在。”该段没有限定f＝5%；前一个独立章节确实在讲默认f＝5%的误报分母，但本句使用了允许参数范围与f>0的泛称。500只适用于f5%；操作p0/f1时实际为100件，动态读数正确。这不影响“比例为0%而非未定义”的结论，但本节正教分母，数字不应被固定。改成“因为仍有报警件作为分母”，或明确“例如f=5%时有500件”，即可。证据：提供的960-scroll-3.png与behavior-cases.json中的p0-f1。

**实际阅读路径与交互图**

960 宽度下，正文栏的行长、段落与标题间隔清楚；读者可以先读默认推导，再自主使用交互。完整故事不依赖点击，不需要把内容硬压进首屏。

320 宽度下正文与控件仍可读，页面没有整体横向溢出，预设按钮也能逐个点击。四个表格都采用内部横向滚动。第一张表首次出现时只看得到“说法、分子”，关键“分母、初始值”在右侧，而且画面没有清晰的横向滑动提示；横移96px后能读到分母，但左侧“说法”又离开可视区。对于此页最重要的对应关系，这是实际阅读负担，不是内容不可访问。证据：320-denominator-table.png及320-denominator-table-scrolled.png。窄屏可把这张核心表改为三组带完整分子/分母的纵向条目，或至少给出明确横向阅读提示；无需重做全页结构。

交互图的颜色与读数关系可见：绿色为正确报警、琥珀为误报，报警归一化条单独标明“分母换成报警件”。但大幅100×100图实际看起来主要是一块浅灰区域，单元格边界并不清晰；960宽度时其高约732px，读者从比例读数到更直接表达16.1%/83.9%的报警条，需要经过几乎一整屏的浅灰画布。它确实传达“正常件占绝大多数”，但称为“点阵图、每格1件”并不帮助读者实际数格。可以保留全批面积表达，把报警比例条放到更近的位置，缩短从“590中95”到视觉解释的距离。320下画布约230px，反而占用较少，结果和条带的阅读联系更紧密。证据：960-low-p-graph.png、320-result-graph.png。

**验证边界**

评审读取的是渲染结果与公开控件；“数字、图、文字同源”只确认可观察的联动与一致性，不推断内部实现。图中不足一件的像素分割未做像素级计数。已知断点以上述可直接复现的读数、按钮变化和可见文字为依据。
