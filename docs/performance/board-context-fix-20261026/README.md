# 新画板续问的上下文容量与失败卡片修复

**后续恢复记录：** 22:30 版本的失败卡片判定同时影响了旧事件读取，导致含既有未完成回执的账号无法加载历史。22:45:11 HKT 先恢复上一版本，23:16:27 HKT 已发布包含上下文容量修复与旧记录恢复修正的 `board-refresh-20261026`。用户数据保留；修复和旧账号恢复验证见[刷新故障记录](../board-refresh-fix-20261026/README.md)。下文记录原实现与当时验收，不能视为旧账号刷新已通过。

用户在新建画板发起整理上下文状态的请求后，得到“模型服务本次未返回可用讲解”的长说明；该说明还被自动加入画板，标为问答讲解。

## 实际原因

2026-10-26 21:49 HKT 的请求约 13.42 秒结束。主调用在发送前约 35 毫秒被本地输出预算检查拒绝，原始错误为 `Model input leaves no output space in the context window`。随后的一次小型失败说明生成成功，整个结果 `incomplete=true`，未读取原文、未制作或提交原生图解。因而这不是书籍缺少资料，也没有证据说明外部模型服务停机。原请求和详细会话仍在私人数据区；这里只保留[故障摘要](incident-summary.json)。

新画板仍可以属于原来的长对话。DeepSeek Messages 的实际请求包含完整的历史状态快照，容量可能高于通用消息表示。`NativeAdapter::context_request_projection` 原本先执行发送时的输出预算校验；一旦实际请求超长，返回 `None`，反而让运行器继续使用较小的通用估算，跳过应有的状态整理与历史压缩。真正发送时再被同一预算校验拒绝，通用适配器将其记为 `PROVIDER_ERROR`。

失败说明通过了文字格式校验，但 `board_delivery::deliverable` 仅检查终态和格式，没有检查 `outcome.incomplete`。因此未完成的结果也会通过自动保存入口，形成截图中的问答卡片。

## 修改

- Runtime 的上下文投影独立于发送预算校验，超长请求仍可被准确计量；继续使用已有的状态整理与压缩流程。Native、Messages 和 ReAct 均保留此行为，实际发送仍受原预算限制。
- 未完成的最终回复保留在讨论记录中，不再自动成为画板成果。直接保存与恢复保存共用同一 `deliverable` 判定。
- 已提交的局部图解由既有独立回执恢复，不受最终回复失败影响。既有历史内容不做清理或改写。

## 验证

修改前，新增测试分别复现了超长上下文投影消失，以及未完成回复被保存为画板卡片。

- 上下文投影回归 1 项通过：实际协议请求超出窗口时仍可计量，通用估算尚可容纳的历史状态能够触发容量判断，原消息不被删除。
- 压缩相关 38 项通过，4 项已有忽略。覆盖超长实际请求改用有界来源压缩、续问前和中途压缩、压缩修订及原上下文保留；模型输出由受控替身提供。
- 保存相关 11 项通过。覆盖未完成回复不创建卡片、保留讨论、恢复保存、正常回答保存，以及取消或失败后已提交局部图解仍可读取。
