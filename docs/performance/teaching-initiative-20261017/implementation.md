## 教学选择进入实际动作合同

当前关系设计和理解记录继续沿用。每次 `select` 增加私有的 `participation` 决策，将用户请求与教师分配推理责任分开。普通 neutral 意图允许教师自主邀请；用户要求完整解释或停止时，仍尊重该请求。

| 选择 | Agent 要作出的判断 | 实际运行后果 |
|---|---|---|
| support | 当前还缺哪条连接，或正在进行的尝试需要什么帮助 | 可以直接提供帮助；不新建待答任务；可继续已有邀请 |
| invite | 为什么现在值得尝试、用户可用什么支持、留哪一步推理 | 必须对应普通表达邀请或可提交活动；不能只记录“准备邀请”却没有回应入口 |
| conclude | 当前请求或局部尝试为何已有足够回应 | 不新建任务；已有普通邀请必须处理或暂缓，不能留下 continue |

这三个选项没有顺序、轮数阈值或答错次数规则。第一次回应可以先补帮助，也可以提供必要前提后留一步给用户；用户有充分的局部解释时可以收束。`invite` 的支持和剩余推理必须由模型结合内容判断，运行时负责约束选择与实际交付的一致性。

`TeachingMove` 仍能读取旧历史记录，新选择必须满足当前合同。私有理由保存在 `MoveSelected`，对外工具参数和公开活动 move 都移除 `participation`。表达邀请、回应关联、最终交付和中断处理沿用现有生命周期。

## 为选择提供当前关系上的事实

`learner_context.learning_opportunity` 从既有存储派生：当前设计谱系与焦点积木、最近最多三条相关的真实帮助交付、相关且未被替代的理解记录引用、当前待答邀请。查询先限定来源版本、设计谱系和关系，再取有界结果。

这解决了两个具体问题：设计或选动作不再被当成已经给过帮助；最近发生的无关页面或阅读事件也不会把较早的相关支持挤出通用 recent 窗口。原来的理解视图仍可回填其他关系记录，新的机会视图只提供当前关系的精确范围。

已交付不代表用户看过或会用；缺失也不代表从未帮助。系统不给 ready 分数、不替模型判断能否尝试。需要更多内容时可以按 delivery_ref 读取真实交付。该视图沿上一阶段的动态刷新链路，在设计、证据或评估变化后进入下一次思考。

## 补齐中间帮助与实际回答的关联

检查“邀请 → 用户卡住 → 聊天补帮助 → 用户再表达”时，发现 `freeze_input_support` 原本会漏掉中间帮助。它调用的 `teaching_activity_events` 只匹配 `payload.delivery_ref`，而普通补充帮助通过 `move.responds_to.invitation_ref` 关联，正式活动的聊天帮助通过 `assistance_for` 关联。

查询现在仅对 `MessageDelivered` 补充这两个既有关系。用户后续表达的 `support_delivery_refs` 会冻结原邀请及中间实际帮助；之后再给的帮助不会回写旧表达的条件。没有新增帮助状态或把聊天消息冒充提示点击。

## 实际多轮对话

教师、学习者和独立内容审阅者均使用隔离的 gpt-6.1-sol。教师通过真实服务器的 ModelAdapter 文件传输处理实际模型请求；原文读取、工具执行、设计、理解记录、普通邀请和交付保存均走实际链路。首次问题沿用已有困惑，从第二轮起由学习者只看实际可见回答后产生输入，主线程原样转交，没有指定提问、演示或收束时机。四轮共 19 次模型请求，所有回合 HTTP 200，学习者自然结束，运行完成。

| 回合 | 实际表达与回应 | 内容判断 |
|---|---|---|
| 1 | 用户把 C/A/M/T 当成连续筛选。教师以候选目录分出章节和主题两条路径，并解释没进主干为何不等于删除。 | 先提供帮助，没有强行要求作答。首轮信息仍偏密。 |
| 2 | 用户修正串行模型，但混淆候选保留与最终清单。教师澄清后主动问：只撤掉主题选择、保留章节 accepted，丁是否从最终清单消失？ | 先给必要规则，再留下未代答的条件变化；邀请由教师主动提出。 |
| 3 | 用户回答“有一边还选着就会留下”，再问 accepted 非 macro 是否仍在正文中。教师确认这次并集应用，换用清单/主干并排示意，并指出原文不足以推出正文呈现。 | 针对实际表达反馈；处理新困惑，没有重复出题或把局部表现称为全面掌握。 |
| 4 | 用户自主整理各集合关系和正文证据边界。教师简短确认，并补全主题选择还需证据支持的条件。 | 自然收束，不制造下一道问题。 |

实际选择为 support → invite → support → conclude。它记录了这次内容判断的结果；系统没有把这个顺序写成教学流程。与前一组七轮全讲解的现象相比，本例出现了由教师主动留下推理、学习者给出依据、教师据此调整帮助并结束邀请的完整过程。

[完整实际对话](live-01/conversation.md)、[独立内容审阅](live-01/content-review.md)、[实验方式](live-01/experiment.md)分别保存。审阅者只读原文和可见对话，认为本例时机选择和反馈成立，同时指出第二轮问句重复和首轮信息偏密。字段合法、工具成功不替代这些内容判断。

## 对话暴露的重复邀请已修复

第二轮正文换一种说法提出邀请，旧界面因 public_prompt 无法逐字匹配正文而再显示一次。该重复保留在原始 visible-02.md 和完整对话中，没有回写为成功记录。

`TutorActivities.vue` 现在将普通邀请已有的实际最终回答作为唯一文字载体，邀请卡只保留回应、求助、完整讲解和暂缓入口。缺少回答、回答 DOM 尚空或关联演示页时，仍显示可用的 public_prompt；没有引入语义相似度或第二次模型判断。

普通邀请的展示记录观察最终回答末端的独立标记，正文开头或回应控件曝光不再足以记录该交付已展示。这表示到达交付末端，不表示阅读或理解了某句话。组件测试以第二轮真实两种问法覆盖去重、入口、末端曝光及回退；30 项通过，Web 类型检查通过。服务器多轮发生在此界面修复前，修复后的显示通过组件行为验证，没有伪称重新生成了整组对话。

## 已知验证边界

本次是四轮模型模拟，支持本例的局部应用与自主梳理，不能推出真人长期保持或跨情境迁移。邀请后的实际学习者一次给出了成立的理由，本例没有覆盖同一邀请下连续卡住的语义效果；中间帮助与后续输入的关联、继续邀请和结束邀请已由服务端回归验证。

首轮仍较密：同时给出分支、并集、反事实和多个“删没删”判断。当前没有证据说明它导致本例理解失败，保留为信息量控制的后续观察点；没有为此引入固定字数、概念数量阈值或每轮提问配额。本例只使用文字图表，没有产生交互演示页，因此不声称验证了自主选择页面的效果。此次修改在本地完成，未部署到线上。
