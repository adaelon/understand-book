## 代码修复

1. **重放已批准的预算决定时，复用本轮书籍快照。** `skills/build/automatic-build-driver.ts` 仅重新评估预算和下一动作。准备产物、恢复及其他实际状态变化仍重新加载状态，保留原有批准匹配逻辑。
2. **按目录读取路由所需的文件存在性。** `packages/core/src/build-orchestrator.ts` 在一次只读路由中枚举目录一次，再用文件名集合查询。索引限于本次路由；写入路径继续实时检查文件。
3. **只读取已存在的尝试记录。** `packages/core/src/automatic-build-task-store.ts` 合并现有任务目录与旧账本中的任务标识，待办失败投影和占用检查不再逐一探测从未执行的任务。真正领取任务时仍执行原有领取检查。
4. **没有旧产物时跳过迁移回执索引。** `packages/core/src/automatic-build-legacy.ts` 先查实际需要审计的旧产物；存在旧产物时保留原审计路径。
5. **消除预算分组中的重复线性查找。** `packages/core/src/automatic-build-budget.ts` 用当前待办的查找表计算派发分数。
6. **收到补位结果后先启动已分配的执行器。** 源码与发布插件的 Build 技能同步更新：如果另一个执行器在补位调用期间结束，先启动本次返回的新执行器、登记其槽位所有权，再处理追加终态。第二次补位继续携带新执行器的所有权，避免已经分配的工作又等待一整轮规划。

## 真实执行器补位验证

安装后使用本书现有交接启动原生专用执行器，保持最多三个活跃槽位。真实终态触发的前三次有效补位分别为 **45.313 秒、41.569 秒、45.286 秒**，依次返回 3、1、2 个替补。返回结果与实际空槽数量一致。

第二次补位覆盖了原先“追加终态让新工作多等一轮”的现场：

| 香港时间 | 事件 |
| --- | --- |
| 18:13:04.694 | 根代理收到 `executor_031` 提交成功的终态 |
| 18:13:05.560 | 进入补位；另外两个槽位仍登记为被占用 |
| 18:13:47.129 | 41.569 秒后返回一个替补；另外两个执行器已在调用期间结束 |
| 18:14:10.187 | 新执行器 `executor_034` 已启动并登记 |
| 18:14:12.186 | 携带 `executor_034` 的所有权，开始收割另外两个终态 |
| 18:14:57.472 | 第二轮补位结束，返回另外两个空槽的替补 |

这一现场中，从根代理观察到首个终态，到替补子代理启动后完成登记，共 **65.493 秒**，包含控制调用、根代理处理和原生子代理启动；引擎调用本身为 41.569 秒。`executor_034` 在第二轮补位前已经启动，避免了再等 45.286 秒规划才能启动的旧流程。

本轮共启动九个原生专用执行器（`executor_028` 至 `executor_036`），六次返回 `committed`，三次返回 `retryable_failure`。持久化进度从 187/6265 增至 **193/6265**，剩余 **6072**；Pass1 仍为 468/468。验收启动的所有执行器均已终止，完成记录已合入原 invocation。

验收收尾先以零容量收齐终态，再恢复容量 3，为后续继续构建保留三份未启动交接。恢复调用耗时 **70.479 秒**，返回正常 `SPAWN_EXECUTORS`，当前没有活跃子代理。该次调用也保留在证据中；它表明真实耗时仍有波动，不应把 42.6 秒视作每次补位的承诺。

## 已知边界

- 三轮对比验证完整补位调用的本机改善，不包含模型生成和原生子代理启动，也不用于推算全书完成时间。
- 对比没有重启机器或清空文件缓存；三轮样本不足以估计 p95。
- 每次补位仍有一次整书路由，因此本书的补位仍是数十秒。此次消除了已证实的重复工作，没有引入跨调用的长期快照缓存。
- 本轮的三次可重试失败计入真实执行结果；没有把它们作为提交成功。全书尚未完成，已提交进度为 193/6265。
- 附带发现一个错误提示分类问题：实验脚本漏写请求版本时，编译引擎返回 `build_engine_failed`，而 Build 契约约定无效 refill 请求应返回 `invalid_refill_request`。它未进入本次调度热路径修复范围；原始响应见 [被拒绝的请求结果](../../tmp/scheduling-fix-20261020/live-1-1-response.json)。
