# 2026-10-24 输出额度与追问恢复

## 决定

Flash 的主流程、审核、教学辅助、评估、压缩和补救回答统一使用模型配置中的 131,072 token 输出额度，推理与可见正文共用此额度。保留原有长演示编写的空间，移除按用途设置的 3K、8K、16K、32K 截断。上下文规划预留相同额度；最终发送前根据完整请求（含工具、保留推理和图片）与模型上下文再次限定。已知 Flash 模型首次明确返回 `finish_reason=length` 时，允许一次更大额度重试，最大 393,216，且不得超过该请求剩余上下文。未知模型与显式覆盖配置不猜测自动扩额能力。

费用预留继续读取最终发送请求的 `max_tokens`，两次尝试分别预留、结算；真实扣费来自各次供应商回执。重试不绕过账号额度、取消或结算失败。调用者明确指定低于模型默认额度时不自动升额，保留已有消融评测 8K 合同。供应商输出上限依据：[DeepSeek Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/)，核对日期 2026-10-24。

## 行为与链路

- `runtime/model_runtime.rs`：统一默认额度、能力上限和上下文限定；完整请求估算不将图片 base64 当成文本。
- `runtime/lib.rs:NativeAdapter::post_chat_completions`：一次输出触顶重试，沿用逐发送费用边界；同一逻辑调用的网络重试最多一次。
- `runtime/provider_stream.rs`：读完长度终态后的费用帧；向上报告各次尝试合计用量，同一尝试内的累计快照只替换、不相加。
- `runtime/answer_stream.rs`：重试前撤回截断草稿，最终正常发布完整回答；原本隐藏的教学草稿保持隐藏。
- `server/service_limits.rs` 与 `server/model_rates.rs`：网站默认额度来自模型配置；费用预留使用最终发送额度，结算使用真实用量。
- `runtime/tutor.rs` 与 `runtime/orchestrator.rs`：当前设计修订必须携带 `previous_ref`，窄追问明确选择当前局部目标；精确匹配同轮已接纳原请求的重复操作保留幂等性。来源与教学审核条件继续有效。

## 第二轮延迟归因（部署后的只读分析）

复用本次真实验收记录，没有再次调用模型。330.69 秒可以拆成：等待上一轮后台 coach 约 29 秒；主流程 9 次模型调用约 126 秒；交付审核 3 次约 175 秒。计费时戳精度为 1 秒，因此阶段时间取约数；明细见 [qa-followup-latency.json](qa-followup-latency.json)。这轮没有输出触顶或扩额重试。

最终正文 622 字，前台模型合计输出 52,219 token，其中推理 40,568；主流程每次请求的输入从 54,090 增至 174,689 token。扩大上限不等于要求写满上限，实际主要成本是串行往返、长推理、累计上下文和反复审核。

等待 coach 是 `server/teaching_coach.rs:146-174` 与 `server/run_admission.rs:1064-1072` 的显式前置依赖；coach 又与前台共用默认每用户 1 个模型槽位（`server/service_limits.rs:48`）。只删显式等待不能保证前台立即运行。active tutor 的文字 select 统一进入审核，正文在审核接受前隐藏（`runtime/orchestrator.rs:7244-7250,7812-7878`）。审核输入包含完整当前设计、coach、既往审核和本轮所有已读来源（`:7842-7867`），并非仅当前一句确认。

审核自身的 `answer_quotes` 不精确时，校验错误直接退回主流程，且该结果未进入有效审核历史（`runtime/tutor.rs:836-879`、`runtime/orchestrator.rs:3387-3402`），导致教师重新调用模型后再提交整稿审核。

后续优化优先缩小局部确认的审核材料、将审核自身的格式纠错留在审核内部；产品调度上让不依赖最新指导的前台追问优先，并同时处理模型槽位。将简单确认与完整教学推进使用不同负担的交付流程属于产品策略调整，应保留事实/来源核对和已审核正文交付。本次分析未实施这些优化，也没有测得候选延迟收益。
