# JSONL 原题与连续追问：匿名回答质量评审

日期：2026-10-21。评审对象为 `tmp/web-cache-eval-20261021/anonymous-answers.json` 中的 A、B 两组回答。

## 结论

A 对第一题的项目选型依据解释更准确；B 对第二题中 SQLite 如何维持确定顺序的说明更具体。两组都正确回答了核心方向：JSONL 通过历史重建间接影响模型输入，存储格式本身不保证缓存，SQLite 可以在保留重建与请求组装机制的条件下保留复用机会。

**B 存在值得阻止直接作出“质量未退步、可以上线”结论的问题。** 它在第一题弱化了项目已经写明的选型依据，在第二题又明确把服务端缓存匹配对象说成“请求里的字节前缀”。后者正是追问要求解释的核心机制，不只是措辞长短的差别。如果本次候选是 B，应先处理这些事实边界，不能只凭缓存指标放行。若候选是 A，未发现相对于 B 值得阻止上线的质量退步；A 自身仍有下文列出的不严谨表述。

这一结论针对给定回答的语义质量，不将一次回答差异归因为上下文布局的必然效果。

## 第一题：为什么选择 JSONL，有哪些替代方案

### A

A 抓住了项目实际要解决的问题：从保存整份历史改为保存已确认的增量变化，避免旧历史随每次提交重复写入；它也正确区分了磁盘增量写入与整体 CPU、内存、读取成本，没有把改用 JSONL 简化成所有操作都成为 O(1)。这与 [ADR-0152 §1–2](../../adr/0152-resident-linear-jsonl-session-log.md) 及[会话日志实施合同 §2–4](../../切片方案-会话JSONL与阅读回顾.md) 一致。

它对恢复边界的说明也准确：读取日志重建状态，不能重新执行已开始的工具；只有未领取且冻结输入完整的 queued 请求可按既有规则继续。SQLite 是本项目已使用的另一种存储；SSE 是展示进度，不能代替可恢复的持久事实。把这些实际分工放在一起解释，有助于回答本项目“为什么用”。

替代方案中，“整份历史追加一行”是被否决的保存策略，SSE 是被否决的事实来源，并不是与 SQLite 平行的存储引擎；回答已经解释了它们各自为何不适用，因此不构成实质误导。将 ADR 的“每轮完整 messages”概括为“整个 AgentHistory”稍有泛化，但没有改变重复保存历史的实质问题。

需要收紧的是“坏掉一行不会带走整份文件”。本项目明确支持的是不完整尾行恢复；中部无效 JSON、序号断裂或不支持的版本会停止恢复该会话，不能由逐行可解析推导出任意坏行都能隔离后继续使用。A 同段已经说“完整坏行报错”，因此这主要是总结句与前述限定不一致。

### B

B 对追加写、顺序读取、纯文本诊断，以及 SQLite、二进制日志等替代方向的解释基本成立。它主动区分格式、写入确认和原子性，承认规范不负责文件操作的原子提交，这一点是正确的。

但它以“没有交代为什么不用别的”开场，结尾又表示无法替作者说明取舍，遗漏了项目已有的直接依据：ADR-0152 明确否决整份 AgentHistory 快照反复重写、只把 JSONL 当导出格式、每轮重复写入完整 messages，并说明当前需求是线性阅读、追问和恢复。回答可以限定自己读到的某段文字，但完整回答本题应把这些项目依据接上。相比 A，B 把有据可查的项目决定退回了较多一般推理。

B 还有两处明确的事实泛化：

- “一事件一行，是可检验的格式要求”不成立。[JSON Lines 规范](https://jsonlines.org/) 要求每行是合法 JSON 值；值可以是数组或其他值，不要求它只代表一个事件。本项目的一事件一行、增量保存及身份序号是应用合同。
- “单一 JSON 数组文件每加一条都要重写整个文件”并不是 JSON 数组格式的必然属性；本项目旧实现确实整份重写，应把结论限定在该实现。表格也把崩溃可能导致整体解析失败写成了损失全部历史，混淆了无法直接解析与数据全部消失。相应地，不能在没有对比测量的情况下断言 JSONL 的“追加写入代价最低”。

此外，“读取不重跑工具，因为文件里记的是事件”因果不充分。不重跑来自本项目折叠逻辑与恢复合同；JSONL 或事件记录本身不会禁止重放代码执行副作用。A 在这里更清楚地解释了具体运行状态边界。

## 第二题：模型调用、缓存与 SQLite

### 两组回答正确的共同部分

两组均将日志和请求区分开，给出了“保存事件 → 恢复消息/回合 → 请求前缀稳定”的中间环节，没有说 JSONL 文件直接进入缓存。它们均提到了动态状态后置、工具定义或旧正文投影变化会影响前缀，也正确区分了本地字节度量与 Provider 的真实缓存 usage。引用已有历史命中率只能说明观测发生，不能证明 JSONL 导致该比例；两组没有作出这种归因。

这些机制与 [ADR-0155 §3、§5](../../adr/0155-goal-work-plan-and-version-centered-presentation-context.md) 一致：固定共同前缀，指导变更沿采样位置追加；必要状态照常更新；压缩和裁剪作用于模型输入投影，不能仅凭离线前缀一致声称真实费用下降。

### A 的具体表现

A 正确说出 JSONL 的作用是间接的，并把 SQLite 的已有教学事件/投影机制与假设中的会话日志替换区分开。现有 learning.db 的事件与可重建投影、生命周期操作与事件同事务、按操作身份重试，都可由 [ADR-0141 §3](../../adr/0141-global-tutor-control-and-session-ownership.md) 和 [Tutor 实施合同 §2](../../切片方案-Tutor全局模式与教学闭环.md) 支持；它没有声称聊天日志已经迁入 SQLite。

A 的不足是把“逐字节一致”当作过强的解释条件，接着说“缓存输入就能继续命中”“缓存命中率不受存储更换影响”。相同重建与组装可以保留可复用的模型输入前缀，但实际命中仍受 Provider 的缓存构建和保留状态影响，不能承诺命中率不变。更准确的结论应是：换库本身不必破坏复用机会；在其他条件相同的情况下，缓存方面的输入条件可以保持。

它没有像 B 那样点明 SQL 查询必须显式确定事件顺序，这是可补充的实用细节；但已经要求消息顺序与请求组装保持一致，核心条件没有丢失。

### B 的具体表现

B 对 SQLite 的关键条件表达得更清楚：显式确定读取顺序，保持消息重建逻辑，不引入重复或缺失。这确实对应本项目按会话序号折叠的要求；若实现为 SQLite，应按会话和事件序号查询，不能依赖自然返回顺序。[SQLite SELECT 文档](https://www.sqlite.org/lang_select.html#orderby) 明确说明，无 ORDER BY 的多行结果顺序未定义。B 将会话日志迁入 SQLite 标为条件性推断，也没有把它冒充为已有实现。

但“缓存命中比较的是请求里的字节前缀”是直接的机制错误。应比较的是服务端形成的模型输入前缀及可命中的缓存单元，不能等同于 HTTP JSON 序列化字节；HTTP 包装的键顺序或空白变化不必改变模型实际看到的序列。[DeepSeek 官方文档](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/) 说明的是输入前缀复用，并要求完整匹配已落盘的缓存前缀单元；缓存是尽力而为，不能由本地字节一致保证命中。B 后续反复使用“前缀的字节内容”“重放结果字节一致”延续了这个错误模型。这比 A 将字节一致当作足够严格的本地比较条件更明确地误述了服务端行为。

B 的“SQLite 顺序只在写了排序键时确定”还应落实为实际查询使用确定的 ORDER BY；仅有表字段或索引并不保证查询顺序。它正确指出了排序条件，修正到项目已有的会话序号即可，不需要引入额外机制。

## 需要保留的准确解释

本项目把事件持久化，以会话序号和冻结的历史位置恢复消息与当时的压缩投影，再与宿主规则、回合输入、工具协议和动态指导组装为请求。JSONL 适合追加事实，但稳定缓存前缀来自这整条重建和组装路径。SQLite 若保存同样的事件、序号、历史位置和检查点，并沿用相同重建及投影逻辑，就能保留相同的模型输入复用机会。两种存储都不能单独保证真实命中率。

## 已知限制

这份评审只覆盖给定两题、每组各一份回答，不能证明更广问题上的整体质量，也不能证明某个表述差异由布局改动必然导致。两组对缓存命中条件都有过强表述，A 不是无缺陷标准答案；B 的排序说明则是明确优点。对给定样本的判断未使用答案长度、检索次数或费用数据。
