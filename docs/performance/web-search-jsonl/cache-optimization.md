## 验证依据

- 请求差异测试应发现旧消息改写、工具定义变化、reasoning 变化和后台调用混淆；单纯追加不应误报。

## 已实现的变化

`request-diff.mjs` 按调用用途比较相邻请求，定位工具集合、定义、旧消息、system 和 reasoning 的首个差异，记录共同消息前缀及序列化字符／UTF-8 字节长度。比较发生在 recorder 剥离 reasoning 内容之前，产物只保留差异元信息，不保存私有原文。后台画像请求与主回答分别比较。

`SessionStable` 保持在前部；`TurnFrozen` 放在已完成历史之后、当前真实用户问题之前。普通与 checkpoint 路径采用相同布局，动态采样快照仍使用原锚点。原始历史、状态冻结时机、工具调用／回执配对和必要的当前状态均保留。

Tutor 示例使用固定的 `<pending_assessment_action_ref>` 和 `<learner_expression_fact_ref>`，实际调用仍从最新 learner view / trace 取得真实引用。不同实际 ID 不再单独改变同形态工具定义；状态、引用有无和合法操作变化仍正常反映在 schema 中。两份派生工具文档已使用本次通过测试的真实契约导出重新生成。

## 回答质量

两组答案匿名为 A／B，独立评估者只接收问题、答案和项目依据，没有接收版本映射、用量或费用。评审结束后揭示映射：A 为候选，B 为基线。完整判断见 [独立质量评估](cache-quality-review.md)。

候选更准确地引用 ADR-0152，解释选择增量事件而非反复保存整份历史，并交代恢复边界；基线追问对 SQLite 需要确定查询顺序的说明更具体。两组都说明 JSONL 不直接产生缓存，收益需要经过有序重建历史和稳定请求组装，SQLite 可以保留这种复用机会。

独立评审认为候选相对基线没有值得阻止保留此次优化的质量退步。该结论也与运行时／Server 测试一致：没有删掉当前状态或原始答卷来换取缓存；引用仍在真实 dispatch 与存储中验证。

候选答案仍需收敛三个表述，原答案保留，不进行事后润色：

- “逐字节一致，缓存输入就能继续命中”过于确定。应为模型输入的可复用前缀保持一致，且缓存已建立、未过期并满足供应商规则时，才可能命中；HTTP JSON 字节不是供应商缓存键。
- “缓存命中率不受存储更换影响”应附条件：SQLite 保存同样的有序事件，并用相同的确定顺序和投影组装请求，可以保留复用机会；实际命中率仍需测量。
- “坏掉一行不会带走整份文件”容易扩大恢复承诺。项目支持不完整尾行恢复，完整坏行会报错，不保证任意损坏后仍能恢复完整会话。

本轮通过的是相对基线的质量回归判断，并未把所有回答断言判为无误。没有针对这道题向生产 prompt 注入标准答案，也没有以少搜索或短答案作为质量通过的理由。

## 证据与限制

- 可随仓库保存的 [用量与请求差异数据](cache-metrics.json) 不包含私有历史正文。完整原始回执、账本、匿名答案和二进制冻结记录保存在 `tmp/web-cache-eval-20261021/`；核心汇总为 `comparison.json`、各组的 `summary.json`、`run.json`、`provider-trace.json`。
- 这是每组一条两轮连续会话，供应商缓存无法清空，模型生成与工具选择不同，第二题自然继承本组第一题答案。因此可确认本次更长前缀、更高实际命中和更低费用；不能把全部差额归因于某一个改动，也不能承诺稳定节省 36.41%。
- 诊断的序列化字节前缀不等于供应商模型输入模板或 token 前缀。[DeepSeek 官方缓存说明](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)采用已落盘前缀单元匹配，并不保证每次相同输入都命中。真实收益采用 usage 核对。
- 原网站私人 memory 和 Tutor 数据库未完整导入，实验使用隔离服务；同一本地书重新发布的身份也不同。Tutor 示例实际引用绑定由相关运行时与 Server 集成测试覆盖，本次技术问答没有触发真实教学评估工具。
- 本轮调用官方 DeepSeek 直连，费用按保存的真实 usage／费率结算，不代表 ahriapi 渠道报价或外部账单查询。此前 Search/Fetch 接入实验 ￥2.373798 单独保留，两轮任务累计 ￥3.300133。
- 1 项既有 ignored 压力实验需要另行录制输入，本次未执行。没有重新跑与改动无关的检查。本轮对照完成后，已于 2026-10-21 14:01 HKT 与 Search/Fetch 和独立分账一起部署，见[发布记录](release-20261021/README.md)。

本机前两次 Runtime 编译因内存不足在测试执行前退出。定向验证最终使用单 job、关闭相关包的调试信息与增量编译、Runtime 采用 256 个 codegen units 完成；未修改系统设置。候选程序也使用对应 dev 配置成功构建。
