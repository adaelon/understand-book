## 原因与代码依据

1. **语义动作粒度与执行器生命周期绑定。** `agents/formal-objects-extractor.md:19` 要求 alignment 每次 invocation 只返回一个动作。`packages/core/src/automatic-build-executor-session.ts:5092` 提交候选，随后在 `5102` 行对 v4/v5 handoff 返回 DONE。搜索、查看和补读都付出独立执行器启动、输入交付、提交和根调度的成本。本窗口约七个动作、七次以上启动才对应一个新增已对齐对象。

2. **三分支整批合并限制名额利用率。** `packages/core/src/teaching-build.ts:227` 的 `routeParallelAlignment` 选取三个 focus；已有 decision 的分支被跳过，但只要有任一分支 pending，`299` 行就返回。合并及下一批 focus 的创建发生在所有分支完成之后。快速分支没有立即补入下一个对象。实际连续运行窗口平均活跃数为 1.092，与配置上限 3 相差明显。该统计不能单独分解屏障与根调度各自贡献。

3. **微动作仍触发几十秒的控制路径。** `skills/build/automatic-build-refill.ts:59` 在释放终止归属后，每次都进入 `engine.step`。390 次 refill 累计 5.383 小时。上次对证据校验、内置资源、共享存储与缓存的修复有效，但修复后长期 refill 中位数仍为 47.73 秒；最近 20 次为 62.00 秒。没有新的 CPU 样本，不把当前成本武断归到某个内部函数。

4. **当前检索仍可能产生大量微动作。** `packages/core/src/teaching-object-alignment.ts:194` 的关键词路径以任意查询词命中对象 JSON 召回，再排序、分页。先前修复扩大了新查询页并优先意义/别名命中；它减少部分翻页，没有改变一个动作一次派发的协议。本次未读取候选或检索内容，不能给出当前 search/inspect/read 的精确占比。

## 建议的下一修复切片

先改变一个对象的执行粒度：由一个有界的专用执行器会话完成 search、inspect、read 到 resolve；每个动作仍由引擎校验、接纳和记录，提交中断后从已接纳进度恢复。仅在对象完成、明确恢复边界或既有预算边界时结束该会话。实现应修改代码拥有的会话协议及对应执行器说明，不能在根会话中复用终止子代理来绕过现行协议。

随后移除整批合并屏障：一个分支完成即可按现有冲突规则合并，并补入下一个可独立处理对象。保持并行上限 3；先提高已有名额的利用率。

验收先使用固定的 12–20 个代表对象，覆盖搜索、原文补读、合并冲突和中断恢复。对照当前实现记录对象/小时、每对象启动次数、根回读次数及耗时、候选接纳结果和来源覆盖。只有端到端对象吞吐达到可接受水平，才恢复剩余全书运行。目标阈值应明确作为验收目标，不能把预期倍数写成已实现性能。

直接提高并发、继续自动重试、缩减全书范围或降低来源依据要求，都不能替代上述执行粒度修复。
