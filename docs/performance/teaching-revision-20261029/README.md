# 教学修订流程：保留解释深度，减少无关返工

2026-10-29。复现输入为《失败的逻辑》的首问「这本书讲的是什么啊」。本次修改面向完整文字交付的修订过程，最终答案仍须通过事实审核和独立解释审核。

## 实现

1. `TeachingDeliveryReviewHistory` 保留结构化 `findings` 和 `request_resolution`；被退回的 `tutor.step select` 将同样的完整信息放入 `review_feedback`，供作者直接处理。
2. 作者先集中补读已发现的证据缺口，只修改真实错误及受影响的推理，保留正确解释、案例和深度。完整原稿与参与字段通过私有动态片段自动带回下一次作者请求，避免靠摘要重建正文。新证据支持原句时允许正文不变；重交仍必须提交完整 move、正文及合同必填字段。
3. 复审结合此前具体问题、实际变化、当前完整正文和全部已读证据。已解决的问题不重复提出；新出现或先前遗漏的实质错误仍须报告。保留原有完整证据投影。
4. 纯文字事实审核要求修订时立即返回作者，记录解释审核为 `skipped / factual_revision_required`。事实通过后才运行独立解释审核；解释拒绝、失败、取消或预算不足都不能变成已接纳交付。

相关实现位于 `crates/runtime/src/orchestrator.rs`、`tutor.rs` 和 `tutor_text_review_rules.md`。没有增加修订规划模型调用，也没有新增正文补丁接口。提示版本为 `teaching-design.v22`、`text-facts.v5`。

## 测量方法

- 修改前保存相关原文件、整个 runtime 的已有工作区差异，并编译单独的基线程序。基线以 HEAD `d791eea51009a4c36150528de50feb5d081c1281` 加当时未提交修改为准，不能把已有修改算入本次补丁。
- 使用 `evals/semantic/teaching-revision-replay.mjs`，分别启动新本地服务、新会话及隔离记忆目录，恢复原来已确认的讲解偏好，通过正式 API 提问并收集实际 SSE、工具状态和审核记录。
- 同题、同书源、同模型 `deepseek-v4-flash`、同本地配置，串行执行。书源既有 `source_revision` 与历史记录完全相同。不给模型预置答案，也不修改线上会话。
- 耗时以服务端 `run.completed.elapsed_ms` 为准；首个答案以首次有内容的 `answer.patch` 为准。模型调用按目的计数，工具统计包括 `failed` 和 `rejected`。所有失败结果均保留。
- 这是少量付费模型样本的案例对照，不是平均延迟或分位数测量；不同稿件的内容和模型耗时仍有随机差异。

## 原始问题与首次对照

历史线上记录总耗时 460.137 秒，6 次 select 提交，含 3 次事实退回、2 次参数错误；实际调用为外层 17 次、事实审核 4 次、解释审核 4 次。线上多用户环境与本地不同，此记录用于说明原问题，不用于计算本次补丁的提速比例。

本地修改前对照 `baseline-01` 耗时 207.052 秒。事实审核只要求把「买下失败的种子」改为「埋下」，作者却改动 22 个空行分段中的 8 个，并在重交时漏掉 `participation`。首次提交还出现了 `target.object_ids` 不允许的错误。共 4 次 select、1 次事实退回、2 次参数错误，复现了小改动引起扩大改写和重复提交的问题。

第一版候选 `candidate-01` 耗时 151.234 秒，1 次 select、0 次事实退回、0 次参数错误，答案从基线的 1,479 字符增加到 1,763 字符，两个模型审核均接受。但内容复核发现开头用表现好、差两组人数大体相等推断失败不能来自无知、粗心或智力不足，比例本身不支持这种排除性推论。因此该样本标记为内容复核不合格，**不把它的 26.96% 时间减少计为合格性能收益**。

针对这个实际漏检，在已有事实规则 R2 补充通用的因果推断要求：观察比例、相关或结果不能单独建立因果或排除其他原因；正确的作者主旨不能替具体推理补足证据。保留该失败样本后，用相同脚本复测 `candidate-02`。

`candidate-02` 耗时 200.995 秒，2 次事实退回、1 次参数错误，15 次模型调用。两次事实拒绝确实跳过了解释审核，但修订仍大幅重写，并且补证后新增了未经支持的教学效果结论。与基线相比仅少 6.057 秒，事实返工反而增加，不能认定收敛改善。内容深度和建设性结尾保留，但开场仍有一条从事故反复发生排除运气或能力因素的无依据推论。

继续定位到实质上下文缺口：`tutor::public_arguments` 在下一轮请求历史形成前就移除 `delivery_text`、`participation` 等字段，provider continuation 也不会恢复这些已删参数；私有工作摘要又只保留正文前 1000 字符。作者拿不到自动完整回传的原稿，必须另行 `tutor.step trace` 才能恢复。这解释了为什么仅要求「局部修订」没有足够执行条件，不能据此把所有改写都归为该因素。

最终补齐 `agent.teaching_revision` 私有动态片段：在参数校验前保留完整 select 请求，覆盖参数错误和审核拒绝；补读期间保留，后续稿替换，成功选择、新设计、outside 或暂停后清除。未接纳稿不进入公共消息，不增加模型调用或工具 API。以此版本继续同题验证 `candidate-03`。

**性能与质量验收未通过。** 最终候选比同环境基线慢 40.806 秒（19.71%）；事实返工从 1 次增至 2 次，模型调用从 14 次增至 20 次。教学参数错误在这次样本中降到 0 次，另有一次 `book.text_batch / LID_PROVENANCE_REQUIRED` 读源拒绝，已计入完整工具错误记录。历史线上 460 秒不能用来掩盖同环境对照的回退。

最终候选确实执行了两次事实退回，两次都跳过了解释审核，最后事实与解释双通过。第一轮四项缺口中有三项在下一稿解决，没有新增事实问题；但作者只补查第四章标题，继续保留未核实的第三、第五、第七章名称，造成第二次退回，最后以删去未核实章名收敛。因此「一次补齐所有已知证据缺口」仍未验证成功。

修订仍超出必要范围：第一稿 15 个空行分段中只保留 6 个，第二次修订 15 段中保留 10 个；仅剩目录问题时仍改动 5 段。私有全文回传修复了确定的上下文缺口，但本次真实模型样本没有证明它已经稳定约束作者只改受影响段落。

内容复核确认最终稿仍用限速 → 低挡驾驶 → 噪声废气 → 购物耗时 → 郊区购物的完整案例，以及打井与地下水耗尽案例解释系统连锁。实际已读原文 `1.115`、`1.116`、`1.130` 支持这些细节。结尾「每当你省掉其中一步，失败就在那一步埋下伏笔，只是要等一段时间才发作」却将倾向和可能性扩大为必然迟发失败，`1.1667`、`1.159` 不支持这个普遍结论；及时修正、学习和调整优先顺序的建设性收束也比用户认可的历史稿弱。因此不能以保住主要案例为由宣称效果完全不变。

## 已知问题与后续边界

- 当前四项修复解决了反馈丢失、修订原稿被截断/移除和事实拒绝后的冗余解释调用；作者仍会漏补证据并扩大改写，不能把提示遵循当成强约束。
- 事实与解释模型均可能漏掉过强推论。三个候选的内容问题都保留在记录中，没有将较快但质量不合格的样本当成成功。
- 下一步若继续改善收敛，需要把「使用原稿修订」落实为针对原文位置的修改操作，并能清楚承接尚未解决的证据项；不能继续仅靠追加「不要重写」提示来宣称问题已解决。本次没有加入此前推迟的正文 patch API。
- 测量样本少且真实生成内容不同。本报告只报告这几次实际运行和已确定的调用行为，不推断长期平均性能。
