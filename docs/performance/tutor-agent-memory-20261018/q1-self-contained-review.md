# 第一轮：回答自足规则的对照验证

本次对同一份第一轮原稿分别使用当前规则和增加“回答应自足解释当前问题”的规则。基线审核接受了原稿；实验组提出三项修改，主模型只按实际意见修改正文和页面，复审接受。但两组均未指出查询与候选怎样经过向量比较产生排序这一必要机制缺口，修改稿也未补齐。

新增规则在本次实验中促成了局部修正，尚未解决用户关注的机制解释问题。实验期间生产审核规则保持不变；实验后的正式采纳见文末记录。

## 问题、规则与输入

真实用户问题是：

> 那Embedding在哪里会被用到呢，怎么用呢，给我个演示页吧

两组均使用 run-5 的 `request-029.json` 中最后拟交付的正文、来源及实际演示页观测。基线规则是生产 `teaching-delivery.v12` 与共享写作规约 `plain-explanation.v1` 的完整组合。实验组只在末尾增加以下通用要求，归入 R1／R2：

> 回答必须在自身正文及本次实际展示的内容中，讲清用户当前问题所必需的对象、动作、连接和条件。读者应能据此理解回答中的结论为什么成立，无须打开引用来源，也无须自行补出关键步骤。引用用于支持事实与提供进一步阅读，不能代替必要解释。审核判断是否讲清时，只能依据实际交付中已经表达的关系，不能从来源、设计或审核者自己的知识中替回答补全；仍需补全的，应指出缺失的具体连接。

追加文字没有本题答案或具体机制诊断。两份实际请求除 system 外逐字相同；system 唯一差分就是这段文字及其归属标题。每次调用使用独立上下文，条件映射只保存在本地。

输入保留真实用户表达、冻结范围和偏好、已读来源、引用映射，以及演示页 revision 2 的三组真实预览观测。移除旧教师设计、审核、工作记忆、纠错历史、作者语义摘要和教学绑定，防止未公开计划代替实际讲解。没有加入此前外部复核意见。

两组都使用实际配置模型 `deepseek-v4-flash`；服务返回模型名为 `deepseek-flash`。参数保持 `temperature=0`、`max_tokens=32768`、JSON 输出和流式响应。输入、冻结 system 和唯一差分见 [实验目录](../../../tmp/tutor-three-turn-20261018/q1-self-contained-probe/)。

## 必要机制仍未补齐

修改稿在“怎么用”中仍然先说：

> 送进向量计算的只是短文本，完整词法字段和原材料位置另外保留。

紧接着跳到：

> 合并时先放含义精确匹配与别名匹配，再交替补入词法命中与按相似度排序的语义候选，并按身份去重。

这解释了候选的合并步骤，但没有解释查询与候选各怎样参与向量计算、比较怎样产生相似度与顺序。页面也仍使用预设的 0.93 等相似度演示结果，未补出这段连接。读者只有先知道相关机制，才能自行连接这两段。

复审的通过理由却写道：

> 读者无需打开来源即可理解候选怎样形成、相似度为何只决定顺序。

它所引用的仍是角色、调用位置、合并额度、短投影和模式切换。这说明本次审核虽然采用了“自足”的要求，仍将相关流程视为充分解释，没有提出目标机制缺口。主模型据实际反馈修好了候选来源的角色说明和两个页面问题，但没有得到要求补齐目标机制的反馈，也没有自行补齐。

上述判断在模型调用结束后作出，未反馈给模型继续改写。本次按固定协议结束，保留原始失败结果，没有继续添加规则、答案或外部诊断来追求通过。

## 已知限制

每组仅一次初审，这是固定案例的对照，不能据此估计稳定检出率或把所有结果差异归因于规则。它足以表明本次增加该规则后，目标机制仍未被发现和修复。

作者是独立的正文与页面修订调用，没有运行完整主教师工具循环或新增来源查询。浏览器验证覆盖独立 HTML 的实际交互，未验证来源按钮的宿主行为、状态提交或重载恢复，也没有把修改稿写回正在运行的应用。实验组复审只接收与原三项意见相关的前三组页面状态；查询一和空查询的观察另行保存。

实验阶段的代码变更仅为保存输出测试支持显式实验规则；当时新增规则仍在实验目录，未替换生产规则。
