## 工作过程与交接

```text
用户问题 + 必要材料 + 选定版本/现场（如有）
  → Agent 判断所需解释的范围
  → 全局设计：形成简短理解路径和暂定表示
  → 局部制作：先实现最能暴露关键表达问题的部分
  → 真实预览：观察关系是否可辨认，执行关键操作
       ├─ 局部表示问题 → 修改图文、布局、例子或操作
       └─ 前提/顺序/分段问题 → 修订全局框架后继续
  → 按框架完成其余内容，复用有效局部
  → 整篇串读：检查衔接、对象一致性及完整范围
  → 修订后的最终候选完成既有预览合同 → deliver
```

简单解释可以把框架浓缩为一句目的，直接制作或直接回答。已有页面的局部修订先读取选定版本和相关片段，沿用有效设计；只有改动影响全篇前提、顺序或对象约定时才返回全局设计。判断依据是工作本身，不使用页数、字数、参数数目或学科关键词作为强制分流阈值。

“先做局部”指制作顺序。可先在一个普通候选中实现关键关系，再扩展同一作品；已有 write/patch 和不可变候选语义足够。框架、关键局部和整篇候选均不必作为额外交付物展示给读者。只有用户要求草稿或局部内容时，才按该范围交付。

## 全局框架的最小内容

框架是供下一次制作使用的简短设计摘要。它需要表达以下信息，但采用连贯文字或简短段落均可，字段和标题不构成页面模板。

| 内容 | 下游实际用途 |
| --- | --- |
| 用户目标与完整范围 | 防止局部优化改变原问题或删去必要内容；原用户请求仍是范围权威。 |
| 最易混淆的关系 | 决定图文、例子和操作应显现什么。 |
| 理解路径与各段作用 | 指明先建立哪些对象和前提、各段解答什么、如何进入下一段。 |
| 贯穿全文的约定 | 保持术语、对象身份、颜色含义、比较基准与模型条件一致。 |
| 暂定表示与关键试做 | 说明先验证哪个表达选择，以及实际结果可能促使哪些调整。 |

局部制作收到：简短全局框架、当前局部目的、相关材料、进入该段所需前提、下一段需要的理解，以及适用的对象约定。必要证据通过现有读取路径提供；框架中的来源摘要不能代替实际证据。邻接关系可包含并列对照、回看或分支，不限定为固定三段式。

局部可以改变布局、例子、图形或交互。当变化影响前提、解释顺序或共同约定时，先更新当前框架，并修订受影响的已制作部分；其余有效内容继续复用。框架更新是设计修订，不能自动修改用户要求。

例如，一段关于模型执行估算的框架，可以先区分数据量与运算量，再建立搬运时间与计算时间的同单位比较，随后说明串行、理想重叠等条件对时间估计的影响，最后再引入批量与有效利用率。关键试做可选择“两个时间量如何共同决定当前模型下的估计”。这是待材料核对的示例，不是所有计算主题的固定路线。

## 提示组装与运行时接入

目标请求组成如下。共同工程约束保持精简，能力细节只进入适用阶段。EX13.1 已将注入位置调整为：共同规则保持前部；阶段/技术指导只在选择变化时于采样位置追加；每次投影当前状态与 user 设计数据，旧指导由新选择或失效事件替代。实施与压缩恢复见 [EX13.1 记录](performance/presentation-context-ex13/ex13-1/README.md)。

```text
全局请求 = 共同原则 + 用户任务/必要材料 + 全局职责 + 简短能力目录
局部请求 = 共同原则 + 当前框架/局部上下文 + 局部职责 + 所用能力的技术指导
串读请求 = 共同原则 + 当前框架/完整范围 + 串读职责 + 实际观察 + 所需技术指导
```

首版沿用同一 Agent 的模型—工具循环。在原 author 能力内增加 `prepare` 操作，记录当前制作上下文并选择后续采样的指导。它不调用另一个模型、不生成页面、不创建持久规划资源；工具回执只报告上下文已更新。

EX12.2 已实现的请求形状如下；phase 和 needs 必填，needs 可为空数组：

```text
presentation.author({
  operation: prepare,
  phase: global | local | review,
  framework?: 简短的当前全局框架,
  focus?: 当前局部目的及与全篇的关系,
  needs: [实际需要的技术指导项]
})
```

`phase` 是制作职责枚举；`needs` 引用已有能力，例如静态图、状态交互、连续场景、Konva、Manim。它们均不表示学科或页面模板。`framework` 是开放文本设计摘要，不要求 Agent 上交完整推理过程，也不以填满字段证明设计正确。

运行语义：

1. 首次激活制作能力时加载共同原则、全局职责和简短能力目录。普通短答不激活制作能力。
2. 复杂任务形成框架后，调用 `prepare(local, framework, focus, needs)`；后续采样再制作局部。简单制作或局部修改可直接选择局部职责，简短说明目的即可。
3. `prepare` 以当前调用提交的完整上下文替换运行内记录；需要继续沿用的简短框架明确带入。省略字段不从旧制作对象静默继承。一个运行内另做一篇内容时重新提交上下文；成功交付后清除该制作上下文。
4. 切换阶段或能力后，在下一次采样组装新模块，不与依赖新指导的内容写入放在同一批。一次只选择当前职责，核心正文只出现一次；工具参数的必要类型说明继续可见。
5. 运行内上下文通过现有请求片段路径投影，压缩后仍来自当前记录。旧工具回执只证明过去调用，不能覆盖当前框架。设计文本按任务数据处理，不能扩大来源、权限或交付资格。
6. `prepare` 不修改候选、不把旧截图授予新候选，也不构成交付或用户目标完成。重复提交相同上下文不计新的制作进展；继续沿用实际无进展处理。
7. 取消或新一轮运行时结束该运行内状态。后续修改先读实际交付版本，再形成当前所需摘要；跨轮持久 Brief 按 ADR-0133 的独立用途再实施。

```text
prepare(input):
  用 input 替换当前运行的制作上下文
  返回已选择的阶段与指导项

build_sample_request(..., authoring_context):
  保留现有基础规则、来源与权限约束
  若制作能力可见：
    加入唯一的共同解释原则
    加入当前阶段职责
    加入当前制作上下文数据
    加入当前所用能力的技术指导
  按现有预算、工具结果与图片投影组装请求
```

运行时验证参数和实际合同，Agent 判断框架是否足够、何时试做和何时返回全局。缺少框架不新增一个拒绝所有 write/deliver 的通用门槛；复杂任务是否按目标组织、是否完整交付，通过真实请求轨迹与实际成品判断。

## 技术指导的归位

| 当前内容 | 目标位置与处理 |
| --- | --- |
| 围绕用户问题、关键关系、对象与理解顺序组织解释 | 唯一共同原则。 |
| “开头必须一句问题，再主比较图和控件，推导放后面” | 从通用要求移除；作为适用时的局部编排例子。 |
| 指定学习率模型、固定步号和小数进度的修复说明 | 保留在对应连续场景示例和回归用例，通用指导表达前进、回退、重复定位的性质。 |
| 独立算例与来源检查 | 所有含相应主张的解释持续适用，不强制非数值内容制造算式。 |
| Konva 对象、拖动坐标、命中区域与尺寸更新 | 选择 Konva 时加载；使用 Konva 不自动要求动画时间轴。 |
| 状态读取、提交、恢复与参数含义 | 具有可保存交互现场时加载。 |
| 连续定位、数学状态与视觉插值的区别 | 采用连续场景时加载。 |
| Manim 渲染、解码帧、异步定位与媒体恢复 | 使用该能力时加载。 |
| 结果回读时携带参数、单位和步骤上下文 | 保留语义要求，按页面结果区域组织；不强迫所有参数挤在一条常驻文字中。 |
| 来源、确切版本、资源、自包含内容、真实预览与交付资格 | 保持共同工程合同及服务端原有检查。 |

实现同时整理 `SKILL.md`、`agent_prompt.rs` 的重复说明和 author 工具描述中的长教学段落。工具 schema 保留合法参数及必要调用语义；长使用示例进入按需指导。仅从 skill 删除内容、却继续在 policy 或工具描述中全量发送，不算完成分层。

资源可放在 `skills/presentation/` 下的共同正文、阶段说明及技术参考文件中；Resident 必须经实际注入路径读取。方法版本随真实注入资产更新，避免只改仓库文件而模型请求仍沿用旧正文。

## 观察与修订

关键局部优先检查“选定表示能否把目标关系直接呈现出来”。例如，同轴时间比较中计算条过短而无法辨认，应调整比较方法、局部放大或标注；仅缩小所有字体、增加数值卡片不能解释该关系。具体方法由实际画面决定。

整篇串读需要定位静态正文、图文衔接和交互结果。EX12.3 在现有 preview 增加最小 `scroll` 操作，使用明确的页面纵向位置，截图与 DOM/layout 一并记录实际滚动位置及视口。它只改变预览阅读位置；不改变模型参数，不借点击控件完成滚动。复用既有动作数限制、取消、截图投影和候选归属。

长页按实际段落与阅读位置观察，可分批定位。只在相关局部执行有解释用途的交互；短篇、分步页面和长篇文档各用自身阅读顺序。局部试做可先用最有诊断价值的视口，最终候选仍完成 320×420 touch、640×240 touch、960×720 mouse 的既有合同。

反馈采用“观察到的障碍 → 修改 → 新观察”的简短记录，例如“右侧文字提到蓝色对象，但当前图中它尚未出现 → 调整对象引入顺序 → 截图确认提及时可以定位”。每条观察必须绑定实际候选、视口和位置/动作。参数正确、页面可交付和读者理解分别表达。

## 比较方式与失败后的动作

首批采用三类真实需求：原模型执行估算的长篇机制解释、一项需要先作判断再观察结果的关系解释、一项文字/静态对照即可说明的概念关系。后两项在运行前选定具体材料与自然请求，目的是暴露不同的表达需要，不是建立模板目录。

提示对照的两组使用相同模型、材料、工具、预览能力和工程底座。一组保留当前指导与制作组织，另一组使用分层指导及框架交接；新增 scroll 能力对两组相同。既有 Linux 页面用于指出实际问题，同底座重新生成的结果用于判断新方案收益。首批每个请求每组运行一次；保留失败产物，不以连续重跑挑出最好页面。问题修订后的复验另记原因及改动。

比较直接回答：读者当前需要辨认的关系在哪里显现；必要前提何时出现；文字能否指向相应对象；操作是否有明确观察目的；全篇是否保持范围和承接。结论引用具体画面与操作结果，不合成美观总分，也不要求所有页面长得相同。

若两组都在来源、计算、执行或交付上失败，先修共同底座，不归因于设计指导。若分阶段组只是增加框架复述和调用，且实际障碍未减少，缩减框架与切换粒度；若关键关系仍不可见，修改表示与例子；若局部很好而整篇混乱，修改全局顺序和交接。复验只针对新改动及仍未解决的问题，不重复已定论的全部矩阵。

工程测试通过可以确认接口和生命周期正确；截图与操作支持具体的表达判断。只有取得读者辨认、解释或应用表现，才能进一步讨论学习效果。
