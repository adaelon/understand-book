## 1. 核心决定

让 Tutor 围绕一份可修订的教学设计工作：从用户想弄明白的问题出发，说明当前需要哪块关系、它解决什么困难，再组织可操作、可组合的支持；承接用户的理解表达和主动疑问；根据真实回应改变后续支持。

这份设计属于现有私人教学会话。公共书籍素材、实际交付、用户原话和理解判断继续由各自现有对象负责。系统可靠保存它们的关联，Agent 决定当下有意义的教学行动。

本次新增的关键连接是：

```text
用户目标 + 来源材料 + 有依据的用户理解
                    ↓
        可修订的 TeachingDesign
       核心模型 / 关系积木 / 当前焦点
                    ↓ 被本轮生成实际读取
    TeachingMove → 实际支持 + 可选的表达邀请
                    ↓ 成功交付后才成为接续事实
    用户普通表达 / 求助 / 直接讲解请求 / 改变方向
                    ↓
     原话事实 → 可修订的理解判断 → 后续教学选择
                    └────────→ 修订或继续使用设计
```

这是依赖关系，不是每轮必须走完的课堂步骤。直接讲解、示范、对比、共同操作、请用户解释、针对局部关系纠正，都可以成为下一步；用户也可以暂停、跳过或改变目标。

**首个交付切片就要打通纯文字的多轮过程。** 设计对象只有被生成过程和下一轮行为消费，才算实现；单独添加字段、提示词或“教学计划”面板不构成完成。

## 2. 为什么现有能力没有组成教学

### 2.1 最新会话提供的失败材料

2026-10-16 的线上会话先要求理解第五章并制作演示，随后要求把 BookStructure 预构建流程具象化，最后点击“把主题整理那一站的证据记账走一遍”。三轮都处于活动 Tutor，实际模型请求包含 `tb4.v5` 教学指导，已经写有认知积木、按理解调整、交付不等于学会等原则。

但实际交付连续展开步骤、术语和检查规则；问题出现在长解释末尾，后续按钮又主要指向更多解释。第三轮是纯按钮选择，没有用户对流程的理解表达。当前主题没有因此产生新的理解假设，普通问题也没有形成待回应状态。

这说明现有存储没有把纯点击误记为掌握；问题发生在教学选择：在用户理解仍未知时，讲解继续沿 Agent 已经读懂的内部结构展开。偏好中的“苏格拉底式讲解”也容易退化为固定的“小矛盾开场”，而不是依据当前困难选择支撑。

核对的第二轮 [LangSmith trace](https://smith.langchain.com/o/491b6259-365d-4169-b798-04d6e92643d7/projects/p/cbc2d6bb-40f1-4aa2-b7d1-4c7a98fd6d40/r/01a143e6-f1a8-7302-88d3-952be3725619) 与第三轮 [LangSmith trace](https://smith.langchain.com/o/491b6259-365d-4169-b798-04d6e92643d7/projects/p/cbc2d6bb-40f1-4aa2-b7d1-4c7a98fd6d40/r/01a143f9-ed39-71c1-a08e-d8ce1f79ce31) 可作为改造前的实际对照。有关内容错误和验证范围集中见第 11 节。

### 2.3 方法参考：让学习沿有意义的问题展开

本次参考用户提供的吴乐旻[《怎样用 AI 让自己沉迷学习？（“苏七”部署帖）》](https://zhuanlan.zhihu.com/p/2012398047620014256) Markdown 全文。采用其中可以转为教学行为的原则：

| 文章提供的启发 | 本方案的具体采用 |
|---|---|
| 从已有模型的局限引出下一种办法 | 设计表达当前问题、已有解释的适用范围和新关系的用途；演示让这个用途可见 |
| 学习者自己一步步形成解释 | 邀请用户贡献尚未代答的关系或判断；必要前提由教师提供，反馈依据实际表达 |
| 一步讲解可以引出连续追问 | 保存真实问题和返回焦点，补足疑问后接回原关系；不因追问就不断改换整堂课 |
| 课内与跨章知识串成逻辑链 | 连接说明为什么现在需要复用或扩展旧关系，沿用对象身份和来源 |
| 下次还会回到之前遗忘或困难的地方 | 依据旧表达和帮助条件重接，在有实际复用需要时给轻量的回忆或应用机会 |
| 学习的吸引力来自理解推进和持续同行 | 用具体反馈呈现用户确实做出的区分，保留可继续的问题和作品 |

这些原则沿当前设计、教学事件、理解记录和演示现场实现。文章的角色背景、部署步骤和课后文件维护方式不作为本项目的执行指令。引导式教学仍服从当前请求和真实起点，不把“全程提问”设为系统默认流程。效果宣称的证据范围见第 11 节。

## 3. 教学设计究竟保存什么

### 3.1 所有权

在现有 `teaching_trace` 中增加 `DesignRevised` 事件，其 payload 为 `TeachingDesign`。事件 ID 就是 `design_ref`，修订引用上一版本；不增加独立教学计划数据库。当前设计由会话、来源与事件投影恢复。

设计修订使用独立的设计版本，不递增 `TutorSession.revision` 或 `TutorControl.revision`。当前运行会核对冻结的会话与控制版本；用生命周期修改承载 Agent 的日常设计调整，会让当前回合自己失效。

沿用这些职责：

- `TutorSession`：用户想学什么，以及主动教学是否开启、暂停或结束。
- `ResidentGoal`：本次请求要求交付什么、哪些交付尚未完成。
- `TeachingDesign`：为了当前目标，怎样组织关系、提供支撑，并依据什么调整。
- `TeachingMove`：这一轮具体提供的支持、邀请或反馈。
- `LearningEvidence`：用户在何种条件下表达了什么，系统据此作了什么可纠正判断。
- `PresentationAuthoringContext`：某个演示的表达结构、局部制作目的和技术需求。

用户要求完整解释或完整演示时，设计要覆盖这一请求的全貌。当前聚焦一块关系，不能成为少交付用户所需内容的理由。任务完成和理解进展仍分别成立。

### 3.2 设计的最小内容

| 内容 | 保存的含义 | 对后续行动的作用 |
|---|---|---|
| `target` | 复用 `TeachingTarget`：用户希望能够做出的具体判断、解释或构造 | 防止把“具象理解流程”擅自改成“背出所有校验规则” |
| `organizing_model` | 当前问题与组织它的核心关系，包含已有办法适用到哪里、新关系为何有用 | 先给用户方向，局部内容能回到同一整体 |
| `blocks` | 少量会话内稳定引用的关系积木：关系本身、它解决的困难、成立条件、来源或公共材料引用 | 同一关系可以换表述、图示或例子，而不失去接续身份 |
| `connections` | 当前确有教学价值的连接：如何复用旧关系、改变适用条件或补足已有解释；简单内容可省略 | 表达为什么现在需要下一块，支持跨章串联；描述开放，不建立固定类型阶梯 |
| `focus_block_refs` | 当前正在建立、诊断或扩展的关系 | 决定当前材料、用户活动和下一轮理解检索范围 |
| 可选 `open_question_refs / return_to` | 当前值得继续承接的真实用户问题，以及追问展开前的关系、邀请或演示现场 | 支线澄清后能回到原问题；问题引用事实，处理情况依据实际交付 |
| `basis_refs` | 支撑本次设计选择的用户事实、有效理解判断及已交付支持引用 | 把设计选择与真实起点连接起来 |
| `revision_reason` | 发生修订时，哪条新事实使原安排需要调整 | 保留教学改变的原因，不生成整段内部推理记录 |

以上固定语义和关键引用；实现时由现有 Rust 类型、工具 schema、TypeScript 导出共同维护，避免另写一套手工合同。

设计只覆盖当前可行动的范围。一个简单问题可以只有一块关系，已有设计适用时直接复用；只有目标、组织关系、重要支撑或理解依据发生变化时才修订。不会为了“规划完整”而先生成整本书的课程树。

### 3.3 积木的身份来自关系，教学价值来自可操作性

“候选”“章节选择”“主题”三个名词还不是三块教学积木。一块有用的积木应能让用户做出新的区分，例如：**保存一份材料和为某个用途选用它，是两个不同的决定。** 它可以用卡片、表格、实际代码对象或一个反例来支撑。

同一个关系可以有多种呈现，含义不变时保留块 ID；含义发生实质变化时创建新块 ID 并保存新设计版本，历史表达仍指向当时版本。理解检索可以沿同一设计谱系、同一来源版本的稳定块引用取回旧依据，不只查当前 `design_ref`，也不因名称相同就迁移理解。块 ID 只在当前私人设计中用于接续，不成为新的公共学习对象注册体系，也不带“掌握分”。

公共对象和认知素材提供有来源的内容。现场自拟的例子、类比和活动必须标明其教学构造身份，并绑定它要说明的有来源关系；不能写回 `CognitiveMaterials` 冒充原文中的推理。

### 3.4 必须保持四种事实的区别

| 事实 | 可以支持的判断 |
|---|---|
| Agent 读取了材料 | 可以据材料组织讲解；不能推断用户接触过 |
| 某项支持已经成功交付，或收到展示回执 | 可以知道此前提供了什么；仍不知道用户是否看完或理解 |
| 用户作了具体表达或操作 | 可以分析其所用关系及帮助条件 |
| 有原话依据的理解判断 | 可以作为可修订的教学起点；适用范围不能超出该次表达 |

设计中的“基于用户已有理解继续”需要引用有效的理解依据。引用已交付材料只能表示可以回指该材料。没有依据时维持未知，Agent 可以给足起步支撑，也可以用一个低负担的表达机会了解起点；不必先全面测验。

### 3.5 新知识应有一个用户能理解的来由

设计中的关系既要正确，也要解释它为何在此刻有用。适合讨论方法或模型时，可以从一个具体问题出发，看已有办法能解决到哪里，再引入补足它的关系；用户已经提出了真实困难时，直接从那里展开。定义、事实或简单问题也可以直接说明，不必制造矛盾或编造知识演进故事。

这份来由放在 `organizing_model`、块的用途与连接描述中，不新增每轮必填的问答阶段。生成讲解和演示时，要消费这个用途：例如“保留候选”解决未来可能按不同目的重新选用的问题，而不只是流程中的一个名词。

邀请表达时，用户贡献的是有意义的推理、解释或构造，不是猜中教师预设的术语。合理的替代办法应先被准确理解，再比较其适用条件；不能因为与现有实现不同就判错。教师负责提供足够前提，也可以示范关键一步，让用户有条件继续思考。

## 4. 让设计在生成之前起作用

### 4.1 同一个 Resident loop 内接入

扩展现有 `tutor.step`，增加创建或修订设计的操作。`freeze_prepare()` 冻结当前适用设计、相关理解和未接完的邀请；Runtime 把它们作为动态任务数据交给同一 Resident。

活动 Tutor 在以下边界前必须已有被接纳、并进入前一次采样上下文的适用 `design_ref`：

1. 选择本轮教学动作 `tutor.step select`。
2. 为本轮教学制作演示的 `presentation.author prepare/write` 等支持产出操作。
3. 将本轮教学终答向用户交付。

新设计和依赖它的产出不能在同一次工具批次里被当作已经相互消费。设计接纳后先回到正常模型循环，再生成支持。原文读取、已有材料检索、理解回读、普通观察和 `outside` 不受此约束；简单直接解释可以复用已冻结的简短设计。

纯文本沿现有终答门槛增加“设计及动作就绪”，并在回答投影向用户流出内容前检查。未就绪的教学终答不先展示再补记计划，而是回到原循环完成所缺的选择。这里约束可交付行为，不声称控制模型内部先想了什么。

演示的 `framework/focus` 引用当前设计及关系；继续保存其表达、布局和局部制作信息。教学目标、用户理解和跨轮关系由 `TeachingDesign` 负责，演示作者上下文不再另造一份相互漂移的学习计划。设计修订后，与旧版本绑定的候选需被明确沿用或调整，不能静默称为新设计的产物。

### 4.2 `TeachingMove` 补齐连接

在既有目标、内容、`interpretation_refs` 和呈现引用之外，增加：

- `design_ref`、`block_refs`：本轮采用哪版设计、服务哪些关系。
- `responds_to`：正在回应的真实用户事实，以及适用时的原邀请引用。沿用既有 `interpretation_refs` 指向理解判断。
- 可选 `response_expectation`：具体公开邀请及关联关系，表达这次希望了解或让用户尝试的内容。
- 原邀请的处理：继续、已处理或暂缓；另发邀请时明确替代关系。这只是对话事项的生命周期，不表示理解成功或失败。

当冻结上下文包含当前未接完的邀请时，下一次动作要说明如何承接它；可以针对表达反馈，可以提供帮助，也可以暂缓后处理用户的新请求。系统不会因为“又收到一条消息”就把邀请标为答过。

程序核对引用真实存在、归属和版本相符、理解判断仍有效。关系选得好不好、是否该换例子、这一句话意味着什么，由 Agent 判断并通过实际多轮内容检验。不会新增每轮教学打分模型。

## 5. 用户表达、理解判断和针对性纠正

### 5.1 普通表达邀请独立于正式评分

`response_expectation` 至少包含一段独立可展示的 `public_prompt`、所指的关系，以及这次表达要帮助区分的内容。它可以请用户解释一个连接、画出关系、预测一个条件变化、完成局部操作，也可以让用户先说明自己的现有模型。

了解现有理解时，用户用自己的话表达很有用；这种诊断不必满足正式能力证明的要求。复述刚给出的答案能够揭示其表达方式，却不足以证明独立迁移。是否需要进一步尝试取决于目标和当前请求。

普通邀请不要求 rubric、分数、标准答案或正式 `submit`。正式判断仍使用原 `AssessmentContract`，在用户回应前冻结标准。判断性邀请本身仍需要来源充分、问题可答；不能因为免评分而让用户猜尚未提供的前提。

### 5.2 输入先成为事实，再决定如何承接

用户原话继续走现有 `UsageObserved` / `LearnerAction`，不另建消息存储。

在明确关联某条邀请的界面中输入时，输入携带该邀请引用；主聊天中的普通消息同时带入当前邀请作为上下文，由 Resident 判断它是在表达理解、求助、追问、要求直接讲解还是改变方向。来源相交和输入时机都不能代替语义判断。

接纳普通消息时，沿现有 `FrozenTeachingPreparation` 冻结当时相关邀请，以及截至该输入已展示的帮助引用；相关支持的已交付与已展示事实保持区分。Resident 确认消息属于相关表达后，用这个输入时快照建立回应与理解关联，不按稍后解释写入时的最新帮助重算。冻结上下文不预判消息就是作答。这补齐当前只有明确 `teaching_ref` 才冻结帮助条件的路径，避免把看过帮助后的复述当成没有帮助的表达，也避免把输入之后才提供的帮助倒记给原表达。

只在用户确实表达了与目标相关的理解时，沿 `tutor.step evidence` 写入 hypothesis。复用原话、事实引用、解释、`teaching_implication`、帮助条件和 `supersedes`，增加可选的 `design_ref/block_refs` 供精确检索。点击“我试着说说”或“继续”仍只是操作，不能独立支持知识诊断。

### 5.3 纠正需要改变下一次支持

一次有针对性的反馈，应能追溯到以下关系：用户哪句话表现了哪部分理解；哪一连接与来源中的条件冲突，或仍无法确定；下一项支持为什么针对这个连接。

这些内容由现有理解解释和后续 Move 共同承载。`responds_to` 指向原话，`interpretation_refs` 指向判断，实际交付保存反馈。无需再新增“错因库”或强制每次填满一套纠错字段。

例如用户得出正确结论，却给出错误理由，要保留其正确结论，只处理错误连接。用户没有提到某个条件，先记为尚不清楚；“我不知道从哪开始”表示需要起步支撑，不能自动解释为概念错误。用户纠正系统对自己的判断时，沿既有证据纠正机制使旧判断失效，后续不再以它作为依据。

纠正结束不自动形成“已经理解”。只有用户后来实际表达或运用，才能形成新的对应判断；暂时没有回应就保留这个事实。

### 5.4 理解上下文按关系恢复

将当前主要依赖“来源下最近 12 条解释”的读取方式，调整为优先获取：

1. 当前设计及焦点关系。
2. 这些关系对应的实际支持、当前未接完的邀请和真实回应。
3. 这些关系当前有效的理解判断及其帮助条件。
4. 近期其他事实作为补充，原文仍可按引用回读。

继续沿用来源版本和现有跨书理解边界。没有匹配的记录就显示未知；不能按相近词语把另一书、另一版本或另一条件下的理解自动迁移过来。无正式对象的普通关系仍可接续，不强迫进入长期对象计分投影。

### 5.5 承接用户自己的问题，并保留返回位置

教学设计同时接住用户主动问出的问题。用户连续追问时，保留真实问题的事实引用、关联关系和临时展开前的返回位置；新问题可以改变当前焦点，未被替代的总学习目标保持可回指。

`open_question_refs` 只收录当前有接续价值的问题；`return_to` 指向原关系、邀请或确切演示现场。它们复用当前设计事件和 `responds_to`。设计可以计划如何回应，只有实际交付才形成“已经回应”的记录；已经回应、用户仍明确表示不懂、用户暂缓，是不同事实。没有后续表达时，不能宣称疑问已经消除，也无需阻止用户继续或逐题要求确认。

返回主问题时，用具体连接承接：例如“刚才分清了搜索预览与合格证据，现在回到乙能否支持这个主题”。不会把一个局部澄清自动扩张为新的整章讲解。跨章转入新关系时，同样说明保留了哪个旧对象、增加了哪项新决定。

一次请求内部的工作安排继续使用 `ResidentGoal.working.open_questions/next_move`。当前普通自由文本通常会新建 Goal，正常回答完成也不检查这些问题，所以它不能独自承载多轮教学主线；跨轮接续归 `TeachingDesign`。依据：`crates/runtime/src/goal.rs:64,148`、`crates/server/src/lib.rs:1664,1675,1703,1829`。不通过故意让任务保持未完成来维持学习关系。

### 5.6 再次进入时，让旧关系重新成为可用的起点

用户再次主动进入相关学习时，取回原问题、上次实际表达、当时帮助和仍未确定的连接。当前问题若需要复用旧关系，Agent 可以邀请用户处理一个小变化，也可以根据直接讲解请求先给必要回顾。一次旧的正确表达不能永久替代当前使用；没有重新作答也不自动判为遗忘。

用户明确说“不记得了”时，补足当前所需支撑，保留旧表现的历史事实与新表达的具体范围。新尝试追加真实事实和解释，不把历史记录改成从来没懂，也不自动要求从头重学。

现有私人 `LearningStore` 和按来源版本读取的有效解释可承担这一点。`session_recap` 帮助定位上次讨论及交付，但其 `answered` 只表示回答完成，不是学习结论，也不是 Resident 已经自动消费的理解摘要。依据：`crates/server/src/session_recap.rs:50,80,102,276`、`crates/server/src/teaching.rs:1764,1800,1821`。首版在用户回来且有复用需要时接续，无须先建设复习日程或遗忘评分。

## 6. 交付、界面和中断恢复

### 6.1 设计、选择和实际交付分别保存

沿用现有提交链：`MoveSelected → finalize_agent_turn → record_delivery → MessageDelivered`。设计和用户输入可以先保存；“本轮已经提供支持”“已经给出邀请”“已经回应这句话”必须依赖成功持久化的实际交付。

现有 `record_user_delivery()` 会遍历本轮全部 `MoveSelected`。允许设计改案后，这会把弃用选择也变为交付，因此需要同步修正：

- `select` 返回并更新本轮完整待交付集合 `delivery_move_refs`，由服务端把同轮 move 身份解析为真实事件引用。
- 最后一次成功选择的集合是当前权威集合。追加真实活动保留旧引用；替换活动从集合中去除旧引用；历史选择事件不删除。
- Runtime 在正常完成并通过交付编译后，将该集合写进持久 `OuterOutcome`。
- `record_user_delivery()` 只为这个集合形成教学交付，继续核对实际回答包含的 presentation 版本。
- 预算耗尽或中断产生的未完成说明，不继承暂存集合来开放邀请。已经实际交付的独立呈现仍沿其既有交付事实保留。

这样可以保留同轮多个真实活动，而不新增一次“确认交付”模型调用。重开或补写仍沿现有持久结果和活动读取修复流程，不创建第二套事务协调机制。

### 6.2 普通邀请只需要自然的表达入口

复用 `TutorActivities` 的交付能力，增加普通邀请视图：把 `response_expectation.public_prompt` 显示为一段自然邀请，入口聚焦输入，不要求统一答题卡。文字教学放在回答旁；演示教学可以放在对应页面区域旁，由同一个宿主组件呈现。一个邀请只有一个身份和一份权威公开问句，交付绑定选择主要展示位置，另一处只提供定位入口；避免正文末尾、页面和活动各自发布一份任务。演示中的具体绑定见第 7 节。

普通邀请不显示分数、“尚未评分”或必答状态。需要时可以提供“换个起点”“先完整讲给我”等当下相关操作，不在每轮铺一排固定教学菜单。

成功交付意味着邀请内容可被恢复和展示；组件实际显示时沿既有 `Displayed` 回执记录。两者都不能证明用户已经读懂。当前焦点有开放邀请时，不再同时发布重复的 continuation 选择；用户仍可直接自由输入。

### 6.3 请求语义与输出形式分开

`ContinuationOption.move_kind` 不再同时代表用户请求和必选教法。新选择保存用户所请求的内容及明确的交互意图；`move_kind` 可以作为生成建议，不能单凭 `Explain` 就推导出用户拒绝参与。

“这一步没跟上”应请求帮助定位和补足当前连接；Agent 可以换例子、提供一个起步操作或先解释关键关系。“直接完整讲给我”仍明确要求完整讲解，不能被反问挡住。用户补充文字优先，需同时修改 `action_intent()`、`validates_current_action()` 和动态工具 schema，不能仅改按钮文案。

正式评分活动仍保留原提示、揭示、作答及帮助曝光合同。修正当前在接纳前仅凭范围相交就截走所有 UI 补充的分流：保留原题与帮助关系，把真实求助内容交给 Resident 处理；正式活动的帮助或揭示必须记录在原题下，不能借普通表达入口绕过帮助条件。

旧数据按原有字段语义解释；新字段缺省意味着没有这份设计或邀请记录，不补造过去已经教过、问过或理解过的事实。使用已有数据演进约定，不另建迁移框架。

### 6.4 让用户看见真实的理解变化

反馈可以明确指出本次表达已经完成的区分，以及接下来仍有用的问题。例如：“你这次把没有选用和已经删除分开了；接下来要弄清的是，找回的材料凭什么够用。”这种反馈必须依据真实表达，不能仅因点击或交付完成就宣告进步。

在自然的阶段收束或用户准备离开时，可以用很短的接续语保存当下意义：刚建立了什么关系、还有什么疑问、下次能借它解决什么。没有理解表达时，就回顾已提供的模型与待确认处。内容沿现有事实形成，不要求每轮生成额外日记、人物记录或独立总结文件。

陪伴感通过记得用户实际问过什么、耐心承接追问、支持暂停以及回来后能接上来体现。页面中用户明确提交的作品可以保留并回看，理解变化由其作品和解释呈现，不以操作次数、学习时长或连续天数替代。

## 7. 演示页作为可接续的教学现场

### 7.1 教学设计先决定页面承担什么作用

演示页承载一块或几块关系，让用户能够观察、比较、操作或构造，并让 Agent 能回到同一个对象解释用户的理解。页面首先要明确“当前看什么”“哪些条件可以变”“这个变化帮助理解什么”；复杂页面还要保留局部在整体中的位置。

不同现场可以采用不同的表达：

| 当前教学需要 | 页面承担的作用 | 用户可能贡献的内容 |
|---|---|---|
| 缺少整体方向 | 用同一组对象呈现结构和局部位置 | 指出想理解的连接或描述自己的整体看法 |
| 分不清两个概念 | 固定其他条件，呈现一处差异及其后果 | 解释差异来自哪一个条件 |
| 不知道如何开始 | 展示一次完整的具体操作，并保留中间状态 | 选择希望展开的一步，或尝试一个相近变化 |
| 已有局部理解 | 提供可改变条件的模型或可组合的对象 | 预测、安排、连接、比较并说明依据 |
| 暴露了具体误解 | 回到原现场，突出冲突的关系或给出有用反例 | 修订原解释，或提出仍未解决的问题 |

这些是可选用途，不是页面类型枚举或固定教学顺序。静态图、表格和完整演示都可以是合适的支持；是否增加操作、表达邀请或暂缓揭示，由当前目标和请求决定。用户要求完整演示时完整提供，不能为了收集作答而隐藏其所请求的内容。

### 7.2 从关系到画面，需要一层很小的对应

当前 `framework/focus` 提供解释组织，`state_contract` 提供状态含义和恢复合同。还要在制作与交付时明确一项对应：**哪块关系，在页面哪个位置，通过哪些对象或条件变得可观察。**

在既有作者上下文和演示版本元数据中保存这一对应，交付 Move 引用确切版本与落点。只为确有教学用途的区域声明，不登记每个按钮：

- `design_ref/block_refs`：教学设计与关系引用，沿主方案复用。
- 稳定 `region_id`：对应页面中的实际区域或对象组，用于定位和反馈。
- 相关状态字段及简短观察说明：例如改变章节选择时，候选目录中的乙保持存在。复用既有 `state_contract` 和页面状态，不另建一套仿真状态。
- 可选邀请引用及其展示位置：指向同一个 `response_expectation`；没有邀请时依然可以交付演示。

`presentation.author prepare` 先带入当前设计和这个关系对应；`write/patch` 将最终采用的落点随不可变版本保存。`preview` 在实际页面中操作相关条件，核对变化是否真的呈现预定关系。只有元数据声称“教了集合区别”、画面却把几个集合混为一栏，属于内容交付失败。

理解进展、用户回答和帮助条件仍在私人教学事件中；页面源码与模板不保存第二套学习者状态。作者的制作预览也不会形成用户已操作、已看过或已理解的事实。

现有方法库继续按理解障碍选用。例如 `compare-one-factor` 可帮助区分决定性条件，`object-transform` 可保持对象身份，`evidence-chain` 可表达主张依据。采用的是表达机制，示例的章节安排、结论和练习顺序需按当前设计改写。

当前 `skills/presentation/methods/_shared/linked-v1.js:22` 固定呈现主图控制、完整讲解和探索段落，一些 `topic.js` 的探索说明也直接给出了结论。这是完整说明作品的合法安排；若本轮要请用户判断同一个结果，就必须改写该安排或选择一个尚未代答的条件变化。不能保留模板中的答案，再将用户重复它解释为独立运用。完整示范时仍应保留必要答案，不把所有页面默认改成隐藏解答。

### 7.3 页面与聊天共同承接一个邀请

用户在演示工作区时，当前邀请应贴近相关区域；用户回到聊天时，仍能看到这条邀请及“回到这个现场”的入口。两处共享同一邀请身份、回应事实和处理状态。

页面未打开或对应区域不可用时，由聊天中的同一邀请承担展示，不留下只能在页内完成的悬空事项。

首版优先复用页旁宿主组件呈现邀请和输入，页面内部提供定位或聚焦入口。需要真正嵌入页面时，HTML 声明邀请槽位，由宿主注入同一公开问句及提交入口，不让页面自行复制题面和维护完成状态。普通页面自带的说明问题可以作为阅读文字，但不能被系统宣称为已经跟踪的待回应邀请。

请求仍是自然的：“我认为乙被删了”“为什么两边不同”“我想试另一个条件”。用户不必重新描述页面。发出请求时，宿主附上原邀请、确切页面版本、发送时现场和已展示帮助；原输入到达 Resident 后再判断是否属于理解表达。

### 7.4 复用现有现场回执，按真实表达取证

已有链路可以直接承担现场接续：`AgentPresentation.snapshotScene/followUp` 先捕获、保存现场，再发送消息；`PresentationFollowUp` 绑定原交付和不可变状态；`follow_up_context` 把同一版本和现场冻结到本轮。主输入框在绑定演示时也已经走这条路径。

接入教学时，扩大第 5.2 节的输入快照范围，覆盖演示追问和页旁输入。系统应保留以下不同来源：

| 内容 | 教学上能说明什么 |
|---|---|
| 页面状态和计算结果 | 当时选择了什么条件、页面呈现什么，不说明用户知道原因 |
| 用户实际输入的解释 | 可以分析其中的关系，但要结合此前提供的帮助 |
| 用户明确提交的排列、连线或参数构造 | 可以作为该任务下的外显作品；最终状态本身不能代替明确提交 |
| 页面生成并预填的文字 | 是系统提供的支持或选项；用户确认不等于独立构造了这段解释 |
| 提示、解法或结果的展示 | 表示相应支持被提供或展示，不能转为理解结论 |

操作型表达沿现有 `LearnerAction` 增加实际提交作品的引用，绑定任务和现场；真正由用户填写的文字保留原文，结构化作品保持结构，不包装成伪造的第一人称“用户解释”。普通探索只保存必要现场，不因拖动、切换或播放就生成理解记录。

现有 `requestTeachingAction(moveId, response)` 能把页面文字预填到活动输入；提交后该文字进入 `LearnerAction.response`。改造时保留预填内容的来源和用户实际提交内容，确认现成解释属于选择或认可。没有证据支持独立构造时，不能作这样的推断；无需键盘监控或原创性评分。

页面内部显示提示或答案时，应接入宿主已有的帮助展示语义，绑定原邀请，并在实际展示后记录 `HelpDisplayed`。后续隐藏答案、换参数或恢复旧现场，不会抹掉已经发生的帮助事实。普通视觉展开无需升级为帮助事件；只记录会影响当前理解判断条件的支持。

`observed_result` 目前是页面可呈现的文字，可能包含视口下方尚未滚动到的内容；现场快照也不是完整操作轨迹。因此“页面当时有这段说明”“收到展示回执”“用户说自己读过”保持不同含义。不能从最终参数推断用户此前尝试过所有条件。

拖动、播放、切换参数继续由页面本地响应。明确提问、提交作品或请求教学帮助时才进入 Resident；不让每次控件变化都触发模型调用。

### 7.5 针对性反馈优先回到原对象和条件

Agent 根据用户表达选择反馈时，优先使用当前页面已有的表达能力：

1. **现有关系已经可见**：引用原页面区域及确切现场，解释应该对照的两个对象。无需重新制作页面。
2. **需要看另一组条件**：沿同一模型给出有意义的对照；保留原现场，让用户可以比较前后。没有实际运行过的新条件，应作为待尝试操作提出，不能编造观察结果。
3. **页面本身表达不清**：例如“没有选中”在视觉上看起来像“已经删除”，对原版本 `patch`，把两种状态分开；问题归到支撑设计，不继续要求用户适应错误表示。
4. **原表示不适合当前困难**：修订教学设计并换表示，仍交代新旧对象的对应。

已有 `RightRail.locateScene()` 和 `AgentPresentation.restore()` 可以回到历史确切版本、恢复现场，并在恢复前保存当前现场。补充稳定区域定位即可支持“看这里”：版本元数据登记 `region_id`，宿主向页面发送定位消息，仅滚动或短暂强调，不修改模型参数、不记为用户作答。

只有内容或模型需要改变才产生新演示 revision。兼容的状态沿既有 `state_contract` 恢复；含义已变的状态不直接套用。反馈仍引用用户当时提交的版本和现场，随后操作的新现场不能覆盖原回应依据。

### 7.6 一个完整的页面教学过程

以第 8 节的 BookStructure 示例为首个落地对象。页面始终保留甲、乙、丙三张卡的身份。先让读者看见“按章做简短导览”与“回答跨章问题”可能需要不同材料，再把候选保留、章节选择和主题选用的关系接起来。页面可以直接完整示范，也可以在已有前提下让用户改变条件；不需要先让用户故意做错。

若用户在“章节未选乙”的现场说“乙已经没有了”，本轮冻结这个现场和原话。Agent 回指同一张乙在候选目录中的位置，说明改变的是选择关系；若画面之前把乙完全隐去了，就修页面，让这一关键区别真正可见。随后可以邀请用户构造一次“章节未选、主题仍使用”的状态并说明理由，也可以按用户要求继续完整讲解。

若用户已经说明乙仍被保留，下一步就在同一张乙上展示搜索预览与完整材料的区别，连接证据关系。不要为了换教学重点又生成一组不相关对象，让用户重新学习界面。

若用户追问“搜索预览不是也被模型看到了吗”，保留当前乙和原主题位置，展开“进入输入”与“成为本次判断依据”的差别，再回到乙能否支持该主题。下次用户重开时，可定位这个旧现场，依据其当时表达决定直接继续、简短回顾或尝试新条件；不将恢复成功解释为理解恢复。

页面给出的运行结果只说明模型在当前条件下发生了什么。用户为什么这样选、能否解释关系、是否能处理新的条件，分别依据其实际表达判断。

## 8. 用这次 BookStructure 问题走通一次

### 8.1 从用户要建立的模型开始

用户说：“我没看懂 BookStructure 具体的预构建流程，能具象化吗？”

教学目标可以定为：**能说明同一份材料如何被保存、按章节选用、组织成宏观路线，并被跨章主题重新取用。** 证据记账作为判断材料是否够用的一层随后接入，不先把全部拒绝条件堆成学习目标。

可以先给一个具体的组织任务：“按章导览要简短，围绕一个跨章问题又可能需要导览里没突出的材料。怎样让两种用途都能找到有出处的内容？”再用同一组卡片显示用途变化，让保存与选择的区别有明确用处。这里是解释实现的自拟情境，不冒充项目历史或用户已经提出的方案。

若用户提出重新读原文，也要承认它可以找回内容；随后比较直接重读和复用已保存候选分别需要什么，解释当前实现采用的选择。教学目标是建立关系，不能把“说出候选目录这个词”设为唯一正确路径。

全貌先呈现为：从书中定位材料，保存带出处的候选；为章节选取内容与简短路线；围绕跨章问题组织主题。实现中的类型和文件名放在用户需要对照实现时引入。

当前设计的两块关系：

- 第一块：保存材料与为某种用途选用材料是两个决定；一条路线没选到，不表示材料消失。
- 第二块：搜索结果帮助定位材料；检查完整材料或读取原文，才建立本次判断可用的证据。

第一块让用户理解“为什么会有不同的集合”，第二块回答“选用时凭什么相信这段材料足够”。它们构成后续步骤的方向。

### 8.2 用同一组可操作材料贯穿

以下为自拟示意，不作为书中原文：

- 材料甲：缓存复用已有结果，减少重复计算。
- 材料乙：输入改变后，旧结果可能不再适用。
- 材料丙：更新时使旧缓存失效，可以恢复一致性。

三张卡片都保存在候选目录。章节选择保留三张；为了让宏观路线简短，路线只突出甲、丙。现在围绕“缓存结果什么时候仍然正确”组织主题，可以选乙、丙。

演示只需让用户切换“候选目录 / 章节选择 / 宏观路线 / 当前主题”，看到同一张乙在不同用途下的身份。界面始终保留同一组对象和关系，不用四套互不相连的名词解释。

这里的准确代码关系是：

```text
宏观路线 ⊆ 章节选择 ⊆ 候选目录
主题成员 ⊆ 候选目录
最终 key_stops = 章节选择 ∪ 主题成员
```

`spine[章].key_stop_ids` 才是章节宏观路线；顶层 `key_stops` 不是宏观路线。主题也不要求每个阶段都有候选成员，可以用已读取原文支持阶段说明。

依据：`packages/core/src/book-structure-candidates.ts:74,102`、`book-structure-materialization.ts:126,135`、`book-structure-themes.ts:93,120,250`。这些关系供设计和内容验收使用，用户首屏不必看到集合公式。

### 8.3 表达邀请留下一个尚未代答的判断

在已经给足上述支持、且当前请求允许继续互动时，可以问：

> 如果章节选择也没有选材料乙，但候选目录仍保留它，跨章主题还可能用上乙吗？你觉得下一步要重新生成乙，还是查找并检查已有的乙？说说你的理由。

这次改变的是“章节选择是否保留”，不同于刚示范的“宏观路线是否突出”。用户需要运用第一块关系；不能把前文原句抄回来就算独立完成。

假设用户说：“应该得重新抽取，因为章节没选它，后面就没有了。”

系统保存这句原话及邀请引用。Agent 可以据此形成局部判断：用户把章节选择当作删除候选；目前无需推断其不会检索或不懂整个流程。下一轮回到同一张乙，展示它仍在候选目录，再让主题检索它；只处理“未选用是否等于删除”这个连接。

若用户说：“不用重做，找出乙再检查，但我不知道检查什么。”则第一块已有对应表达支持，下一步转向第二块：展示乙的搜索短预览与完整内容、条件、出处的差别。这里搜索预览确实进入模型输入；它尚未进入本次主题判断的合格证据账本，不能说成“模型没看到”。

若用户说：“还是不知道从哪里想”，先让其在同一张表中指出乙是否仍存在，再示范“存在”和“选用”的不同。若用户要求完整讲解，则直接完成讲解，暂缓邀请。若用户已经能说明关系并处理变化，可转向实际流水线或源码，不必补做一套固定练习。

这些分支都是基于实际表达的选择，没有按答错次数自动升级的固定阶梯。

## 10. 如何证明这次改变了教学

### 10.1 状态回归：只检查会改变下一步行为的失败

| 具体失败 | 检查方式与失败后的修改方向 |
|---|---|
| 尚未交付就被记为已支持、已邀请 | 中断在设计/选择之后；应无新开放邀请。失败则修交付投影边界 |
| 同轮改案把弃用动作也交付了 | 选择两个实际动作并替换其一；只恢复最终集合。失败则修持久 outcome 与选择绑定 |
| 新设计未进入生成上下文，先产出再补记录 | 捕获实际采样与作者工具顺序。失败则修前置消费边界 |
| 普通表达在重开后与原问题失联 | 自然输入后重开同一聊天；恢复原话、关系和待反馈项。失败则修冻结和关联 |
| 普通表达丢失帮助条件或被事后帮助污染 | 分别在输入前后展示帮助；理解只引用输入时已冻结的帮助。失败则修接纳快照及 evidence 消费 |
| 帮助、纯点击或暂缓变成错误/掌握 | 走现有输入路径查事实与 evidence。失败则修语义分流及证据准入 |
| 用户纠正后，旧理解判断仍指导新动作 | supersede 后取同一关系上下文。失败则修有效解释检索 |
| 正式活动经普通入口漏记帮助 | 原题内请求直接解释后作答。失败则修 assistance 归属 |
| 页面预填解释被当成独立表达 | 直接确认预填文字，与用户自行输入分开检查。失败则修输入来源及解释依据 |
| 页内先揭示再隐藏导致帮助丢失 | 查看提示后隐藏、恢复并提交；保留当时已发生的帮助。失败则修宿主帮助回执 |
| 反馈定位到后来变化的现场 | 提交后再改变参数；反馈仍指向原回执，恢复前保存现状。失败则修版本和现场引用 |
| 页面和聊天出现两份可执行邀请 | 从演示切到聊天后回应；仍只有同一邀请身份和处理状态。失败则修展示所有权 |
| 支线澄清后丢失原问题，或计划被当成已解答 | 连续追问后恢复设计焦点；返回原关系，已回应只认实际交付。失败则修问题引用与返回点 |

复用 `tutor_building_blocks_tests.rs`、`tutor_adaptation_tests.rs` 和现有交付、接纳测试。不要为每个字段复制一条“写入等于读出”测试。

### 10.2 自主教学轨迹：看最终内容和下一轮变化

沿现有 `POST /agent/chat` 及 `evals/semantic/agent-run.mjs` 执行实际多轮调用，记录来源、输入、实际模型版本、最终回答、设计和事件、帮助条件及用量。复用 recorder，不用现有事实槽评分器宣称教学有效。

首批保留以下有区分力的轨迹：

1. **最新 BookStructure 失败重放。** 先要求具象化，再说“仍不知道为什么有候选和章节选择”。如果只换词重复步骤，说明组织关系没有进入支持生成。
2. **同材料、不同起点。** 复用 TB1 的两种 Rust 起点。第一块关系和起步操作应有实质差异；篇幅或术语变化不算。
3. **正确结论、错误连接。** 使用 TB3 的“两个都能打印，因为复制了两个 Foo”。反馈应保留结论、处理复制推断，并据此改变支持。
4. **复述与迁移区分。** 用户先复述刚给出的答案，再处理决定性条件改变。不得将第一次复述记为独立应用；应依据后一次理由更新对应判断。
5. **改变活动与直接解释。** 开放邀请期间用户明确要求完整讲解或改变方向。应完成新请求并正确保留邀请状态，不能变成必答流程。
6. **连续追问后接回原问题。** 先讨论候选如何用于主题，再追问搜索预览与模型输入。澄清后应回到原材料能否支持主题；用户提出合理替代方案时要比较条件，不能按术语是否命中判错。
7. **再次进入时旧理解暂不可用。** 上次在帮助下正确表达，这次用户说“不记得为什么了”。应提供当前起点并保留原帮助条件，不能依据旧记录跳过支撑，也不能扩大成整体能力下降。

每条都核对：设计声明的关系是否真的被讲解或演示建立；用户表达是否改变了下一轮；纠正是否指向原话中的具体连接。采用同材料、同输入、同生产模型的改造前后对照，关键分支做小规模复跑以观察稳定性；如失败，再针对失败增加样本。结构合法、调用齐全、出现“积木”二字都不能代替内容判断。

真人过程重点观察用户能否借所提供的关系独立处理一个相关变化，并保留其自然表达及获得过的帮助。模拟用户轨迹只能检验系统应对这些输入的行为，不能证明真实的人已经学会。

演示专项复用 TB4 的实际浏览器与追问链：同一页面分别接收错误连接、正确连接但不知下一步、直接求助三种输入，检查反馈是否采用对应现场并改变支撑。作者预览另外验证关键条件变化确实可见、显示的结果符合来源或明确的教学模型，以及要留给用户的那个新判断没有被模板提前代答。失败时分别修改表示、模型或邀请设计，不以页面能运行代替教学有效。

内容比较还要判断用户是否能说清当前关系解决什么问题、为什么要接到下一块；仅把知识点顺序列对仍可能缺少教学设计。学习动力通过实际读者对进展、疑问和接续体验的反馈观察，不以停留更久、连续操作或接受泛泛赞美作为效果证明。

## 11. 已知问题与验证范围

线上抽查的三轮不是全量教学效果研究。已能确认的实际问题是：设计缺乏跨轮身份、普通邀请没有待回应关系、UI 请求过早锁定输出形式，以及当前主题缺少用户理解表达后的针对性推进。不能据此推断所有会话或所有模型都表现一致。

这次 BookStructure 回答还混淆了两个来源事实：搜索预览是否进入模型输入，与它是否成为合格证据；未进入宏观路线，与未被章节选择。前者见 `book-structure-retrieval.ts:60` 和 `book-structure-themes.ts:157`，后者见第 8 节。设计结构不会自动消除内容错误，因此验收仍要核对解释中的关键关系与真实来源。

演示专项代码核对确认：现场回传与恢复已存在，但关系落点及普通邀请尚未接通；受支持的页内预填路径没有保留表达来源区分；页内自行揭示也不自动进入 `HelpDisplayed`。这些是本次需要解决的具体接点，不代表所有线上页面都实际触发了错误的学习判断。当前模板示例的完整解释与探索安排也不能直接当作每位用户的教学设计。

现有 TB2–TB4 包含预读材料和固定工具回放，能证明给定内容的存储、交付和恢复，但不能证明生产模型会自主组织相同教学。TB6 尚未完成；本提案衔接其真实多轮与真人验证，而不把既有“通过”扩大为已经验证学习效果。

参考文章关于三倍效率、优于真人教学和广泛适用性的表述属于作者经验与判断；作者在 Q&A 中也明确说明当时没有效果数据。本方案采用其中的问题推进、持续追问、逻辑串联和接续机制作为待验证的设计依据，不据此承诺学习收益。角色风格与关系设定也不构成教学效果证据。

文章的课后教材改进笔记可提示我们区分“用户缺少理解”与“材料或表示有问题”。本项目目前没有等价的教学发现自动汇入书籍修订通道。已确认的材料问题先在实际回答中指明出处；用户要求保存时可沿现有私人笔记关联来源。演示表示问题沿原版本修订；公共教材或方法资产的修改仍走其已有维护与验证路径，不因一次困惑自动改写。依据：`crates/memory/src/note.rs:9,26`、`crates/runtime/src/tool_registry.rs:1571`、`packages/core/src/teaching-build.ts:614`。

目前只完成设计和代码依据核对，没有修改运行代码或部署，也没有运行教学效果实验。实施时还需根据当前工具合同收敛具体字段导出与事件 payload，但上述所有权、生成前消费、真实表达依据和实际交付边界不应被简化成提示词要求。
