# 联网检索与独立费用

2026-10-21。目标：Resident 自主使用 DeepSeek Search/Fetch 补充解释中的知识缺口，沿用现有账号额度、工具结果预算和费用汇总，分别记录模型、搜索、网页读取费用。

## 已确定的行为

- 对机制解释、方案比较和时效性问题，根据证据缺口探索概念关系，再核实具体结论。模型自信不代表解释已经完整。
- 只说明“是什么、做了什么”的材料不足以回答“为什么这样做、与替代方案相比如何”。当答案依赖尚未核实的重要外部机制、保证或取舍时，模型自主检索一手依据；“工程补充”标签不代替核实。
- 项目设计动机依据项目材料；外部机制依据适当的一手来源；实际收益依据实际运行数据。搜索排名和 authority 仅帮助选择阅读对象。
- 摘要用于定位，关键机制与条件读取正文；网页使用实际 URL，书内来源沿用已有来源绑定。
- 取得材料后解释因果、成立条件与替代方案。后续搜索必须补充仍影响答案的缺口，证据充分就交付。
- Search 和 Fetch 使用独立于模型渠道的配置。只有具备正式费用归属的网络 Reader 才提供付费联网工具。
- 复用相同请求和页面正文；分页读取缓存正文；支持主动刷新。缓存复用不产生供应商请求费用。
- 每次实际发送单独预占、结算，重试保持同一逻辑请求并记录物理尝试。已知免费响应释放预占，结果未知保留待确认。
- 模型、搜索和网页读取共用账号额度；费用分别展示后按原始任务归属汇总。模型 Token、请求次数、等待时间采用各自单位。

## 实现切片

1. Runtime：动态工具发现、参数契约、结构化结果裁剪、网页进度与解释指导。
2. Server：独立服务配置、Search/Fetch HTTP、取消、有限重试、请求缓存和限流等待。
3. 费用：按请求用量接入 billable_usage 和原有账号额度，保留费率快照和待确认状态；汇总及界面提供费用类别。
4. 验证：同一最终程序、模型、书籍和原始提问前历史，对照无搜索配置与有搜索配置。隔离账号、资料和费用记录。

## 配置与支持范围

联网工具由网络 Reader 的 `NetworkRunPort` 提供，使用接纳运行时固定的账号、回合和学习工作区归属。普通本地 Reader、离线桌面阅读和默认 `ResidentStatePort` 不提供付费联网能力。网络等待期间不持有用户或 Reader 锁，切换当前阅读现场不会转移已发请求的费用。

Search 与 Fetch 共用一组独立于模型的连接配置，分别限流。模型仍沿 `OPENCODE_API_KEY`、`OPENCODE_BASE_URL`、`FLUID_LLM_MODEL` 和现有模型费率配置执行；模型走 ahriapi 时，不会将它的凭据或费率自动用于联网工具。

这里的独立指配置与记账独立，不要求另建 API Key。DeepSeek Search/Fetch 使用普通 DeepSeek API Key；模型也直连 DeepSeek 时，两个配置项可以显式填入同一把官方 Key。实验脚本确认模型连接为官方直连后，将已有 `OPENCODE_API_KEY` 赋给隔离子进程的 `DEEPSEEK_SEARCH_API_KEY`；没有新建搜索专用 Key，也没有修改线上服务环境。生产服务不自动从模型配置回退取 Key，以免模型切换到 ahriapi 等渠道时把中转凭据发给官方搜索接口。

```dotenv
DEEPSEEK_SEARCH_API_KEY=<联网接口密钥>
DEEPSEEK_SEARCH_BASE_URL=https://api.deepseek.com
DEEPSEEK_SEARCH_QPS=100
DEEPSEEK_FETCH_QPS=25
```

`DEEPSEEK_SEARCH_BASE_URL` 默认如上，客户端追加 `/v1/tools/search` 或 `/v1/tools/fetch`，因此该值不再添加 `/v1`。两个 QPS 配置可省略，分别默认 100、25，允许 1–1000 的整数；部署时按实际渠道限额设置。缺少密钥或连接配置无效时，Runtime 不暴露这两个工具。QPS 队列按同一进程内的连接配置分别控制 Search/Fetch；多服务进程共享供应商账号时需各自分配限额。

费用文件为 `server --multi-user <service-root>` 的 `<service-root>/web-rates.json`，与书籍目录、模型配置分开。下例只演示每请求 0.005 元的配置结构，部署时必须核准实际渠道价格与有效期；示例有效区间是 UTC 2026-10-21 00:00 至 2026-11-01 00:00，不是永久价格声明。

```json
{
  "rates": [
    {
      "version": "deepseek-search-20261021",
      "provider": "deepseek",
      "service_kind": "web_search",
      "starts_at": 1792540800,
      "expires_at": 1793491200,
      "cost_micro_cny_per_request": 5000,
      "source": "https://api-docs.deepseek.com/guides/search/#billing"
    },
    {
      "version": "deepseek-fetch-20261021",
      "provider": "deepseek",
      "service_kind": "web_fetch",
      "starts_at": 1792540800,
      "expires_at": 1793491200,
      "cost_micro_cny_per_request": 5000,
      "source": "https://api-docs.deepseek.com/guides/search/#billing"
    }
  ]
}
```

金额以整数微元保存，1 元 = 1,000,000 微元；时间为 Unix 秒，采用 `starts_at <= now < expires_at`。同一种服务的版本不能重复，有效期不能重叠。每次实际发送前读取当前有效费率并保存快照；没有有效费率会返回 `WEB_RATE_UNAVAILABLE`，不发送请求。当前配置要求 `provider=deepseek`，没有自动猜价或使用模型费率的回退。

## 请求、缓存与正文预算

- `web.search` 接收 `query`，默认 3 条、最多 5 条。`query` 与可选 `ori_question` 为 1–128 个 Unicode 字符；可选 `localization` 是搜索目标地区的 IP，不根据提问语言自动填写。`need_content` 默认 false，模型需要同时取得正文时可开启。
- `web.fetch` 接收实际 `url`，默认从 `offset=0` 读取 6,000 个 Unicode 字符，单次 `max_chars` 最多 12,000；继续读取使用结果的 `next_offset`。Runtime 再按现有单工具和本轮工具正文预算裁剪，并保留实际交付区间与下一页位置。
- 搜索按完整供应商请求参数缓存 5 分钟，网页按 URL 缓存 30 分钟；这些是进程内缓存，重启清空。同配置、同请求的在途调用共用一次供应商请求，费用记实际发送者的原回合；缓存命中和等待复用者不新增费用行。
- 搜索返回的非空正文同时进入页面缓存，后续 Fetch 可直接读取。搜索空结果也缓存，避免原样反复查询；相同检索失败短暂保留 30 秒，避免 Agent 每次重新启动整组重试。
- `refresh=true` 跳过已完成缓存，允许新供应商请求；普通续页保持 false。续页缓存已失效时返回 `WEB_PAGE_EXPIRED`，不会自动购买一次 Fetch，确需重新获取时从 `offset=0` 主动刷新。

网页返回 `content_status`、`source_scope=web` 和取得时间；摘要与排名只提供线索，正文仍需由模型判断相关性、条件和是否为屏蔽提示。正文分页复用避免重复 Fetch 费用，但阅读这些内容产生的模型 Token 仍进入模型账。缓存命中状态、物理请求数、排队／请求／完整调用耗时保留在工具结果的 `usage` 中。

首轮真实重放还发现 Native 请求的历史工具名会随当前工具暴露集合改变：同一条历史调用可从 `book.text` 变成 `book_text`，导致旧消息前缀变化。当前修正沿现有完整 Resident canonical 工具目录固定历史名称映射；当前请求的工具 schema 与反向执行映射仍只包含可见工具。这项修正消除已观察到的前缀变化原因，实际缓存命中率和费用变化仍由后续运行记录判断。

## 额度、重试与分账

每次物理发送在限流等待结束后、HTTP 发出前，经 `ModelSpendStore::web_admit_run` 在账务事务中检查账号、工作区归属、有效额度期和余额，按单次费率预占。完整运行范围由 `NetworkRunPort` 在网络调用前后检查。模型、Search、Fetch 和已有服务通过 `billable_usage` 共同参与账号余额计算；待确认请求的预占也占用余额。普通聊天没有独立每 run 的人民币总额上限，现有 Runtime 回合、Token、上下文与工具结果预算继续约束模型流程。

单个联网工具调用的总时限为 45 秒，连接解析／连接时限 5 秒，单次请求最多 15 秒，最多 3 次尝试。HTTP 408、429、5xx 及网络传输失败可有限重试；其他明确 HTTP 错误和不可解析响应不会反复重发。排队与退避检查取消，已在途的同步 HTTP 请求受单次超时约束；收到结果先记账，再响应取消。`Retry-After` 的整数秒值最长等待 30 秒，仍受调用总时限限制。

同一逻辑请求使用一个 `logical_usage_id`，每次实际尝试分别写 `web_usage`：

| 已取得的结果 | 请求账状态 | 金额处理 |
| --- | --- | --- |
| 有搜索结果或非空 Fetch 正文 | `settled` | 按该次费率快照结算 |
| 明确 HTTP/API 错误、空结果，或准入后取消且尚未发送 | `released` | 释放预占，费用为 0 |
| 传输结果未知、成功响应无法完整读取或解析 | `pending` | 金额待确认，保留预占 |

正文是否相关、是否为屏蔽页不改变供应商已成功返回非空内容的计费判断。未知尝试后的重试另行预占、另写回执，不把前次费用当成 0。失败返回也保留已经写入的尝试账；缓存命中和分页读取不进入物理请求账。

`web_usage → billable_usage → cost_summary` 沿原回合和学习工作区归集，`cost_breakdown` 分别提供 `model`、`web_search`、`web_fetch`，已有其他服务保留在 `service`。每个分类及总计继续区分已确认、估算、活跃预占和待核算；存在未知金额时不声明完整供应商总额。网页输入产生的 Token 只记模型账，排队耗时单独记录，不转换成费用或重复计入搜索账。

最终候选的一手正文依据与来源区分有所改善，但仍没有解释 JSONL 持久化、请求前缀稳定与模型缓存之间的关系，部分替代方案的成立条件也未讲完整。判定为接入和分账验证通过、解释质量部分改善，不宣称原质量缺口已全部解决。实际 Token、原始回答、费用核算与限制见 [原题实验报告](performance/web-search-jsonl/README.md)。

## 当前边界

普通聊天已有的是账号共享货币额度，没有独立每轮人民币上限。上下文与工具结果预算继续由现有 Runtime 管理。

已有视频服务在额度不足时返回普通工具冲突，主模型可能再尝试一次调用后才沿模型额度准入停止；该路径仍受共享余额约束。本次联网接入不修改视频服务的停止行为。

隔离重放保留原始对话；跨聊天记忆与旧演示资产不会由 JSONL 自动恢复。新导入资料的出版身份与历史来源不同，两组采用相同处理方式。

模型和网页接口费率取实际渠道及生效时段。本次实际模型渠道为 DeepSeek 直连，记录的费用不代表 ahriapi 的结算结果。
