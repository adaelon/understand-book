# 预购建流程

结论：当前“预构建”已经不是一条线性脚本，而是一个持久化、可恢复、支持并发调度和协议迁移的状态机。真正难以掌控的是控制面，而不是各个提取器本身。

以下针对当前工作区快照，包含交接文档所述的未提交 V3 重构。

```
​```mermaid
flowchart LR
    A["Workbench：来源可信化"] --> B["磁盘门禁：source.txt / base.json / source_manifest.json"]
    B --> C["automatic-build CLI"]
    C --> D["build-orchestrator：重算快照"]
    D --> E{"next action"}
    E -->|"需要决策"| F["legacy migration / recovery"]
    E -->|"等待"| G["lease / dispatch 状态"]
    E -->|"执行"| H["stage work units"]
    H --> I["executor handoff"]
    I --> J["candidate → write → quality gate → close"]
    J --> D
    E -->|"全部收敛"| K["reading guide 验证"]
​```
```

### 整体流程

1. Workbench 先处理来源可信度

Workbench 负责把 PDF、EPUB 或已有工作区转成可信的磁盘基础：

- `source.txt`：规范化正文。
- `base.json`：可寻址的基础语义节点。
- `source_manifest.json`：来源身份、哈希和派生关系。

后面的语义预构建不会直接相信原始输入，而是围绕这三个文件及其哈希重新计算状态。这是 Workbench 与预构建之间最清楚的一条边界。

1. CLI 负责循环，不负责决定业务阶段

主入口在 [automatic-build.ts (line 917)](E:/allwork/download/agent/understand-book/skills/build/automatic-build.ts:917)。它的职责是：

- 解析目标工作区和兼容旧命令。
- 请求 orchestrator 计算快照和下一动作。
- 执行 migration、lease、dispatch、submit、write、close。
- 每次动作后重新读取磁盘并计算下一轮，而不是一次调用跑到底。
- 把完整 prompt、任务信封和身份信息写成 executor handoff。

[sidecar-entry.ts (line 29)](E:/allwork/download/agent/understand-book/skills/build/sidecar-entry.ts:29) 主要是打包后的命令和脚本分发器，不是复杂业务所在。

1. Orchestrator 根据磁盘快照选择下一动作

核心控制面在 [build-orchestrator.ts (line 129)](E:/allwork/download/agent/understand-book/packages/core/src/build-orchestrator.ts:129)。逻辑阶段是：

| 阶段                  | 当前主要协议 | 工作                             |
| --------------------- | ------------ | -------------------------------- |
| `pass1`               | V3           | 局部语义提取、切片和树形归约     |
| `paper_metadata`      | V2           | 论文元数据                       |
| `paper_lexicon`       | V2           | 术语表                           |
| `profile_sidecar`     | V3           | profile 专属语义、公式和篇章信息 |
| `pass2`               | V2           | 跨段、长程关系                   |
| `book_structure`      | V2           | 全书结构拼装                     |
| `paper_reading_guide` | 验证阶段     | 验证最终阅读产物输入是否新鲜     |

具体 work unit 可以并发，但阶段完成必须满足各自的 artifact、身份哈希和 quality gate。

[nextAutomaticBuildAction (line 2037)](E:/allwork/download/agent/understand-book/packages/core/src/build-orchestrator.ts:2037) 把快照归约为几类结果：

- 有遗留产物或协议冲突：要求人工迁移或 recovery。
- 有正在执行的 lease/dispatch：等待。
- 有 pending work unit：调度执行。
- 工作单元完成但尚未收口：write、quality、close。
- 所有阶段关闭：最终完成。

1. V2 路径是传统批处理描述符

V2 work unit 主要描述：

- stage、work unit ID、输入哈希。
- 依赖关系。
- token、节点数等预算估计。
- 对应的 input/write/batch 脚本。

它仍覆盖 metadata、lexicon、Pass2 和 BookStructure。相关类型从 [stage-work-unit.ts (line 58)](E:/allwork/download/agent/understand-book/packages/core/src/stage-work-unit.ts:58) 开始。

`paper_lexicon` 仍使用 V2 descriptor，但 `paper_lexicon_policy.v2 / paper_lexicon_cluster.v4` 不再复用旧 V1 scope：direct、fragment、reduce 和 deterministic skip 的 work-unit ID 都携带由 stage policy、router 与 prompt 计算的 scope digest；首次 claim 在 `.build/automatic-build/v2/policies/paper_lexicon/<policy_digest>.json` create-only 冻结完整策略。旧 `.build/automatic-build/v2/policies/paper_lexicon.json`、旧 task attempts 与 `.build/paper-lexicon/<legacy-id>.json` 只读保留。

1. V3 路径只落在 Pass1 和 Profile Sidecar

V3 descriptor 从 [stage-work-unit.ts (line 81)](E:/allwork/download/agent/understand-book/packages/core/src/stage-work-unit.ts:81) 开始，与 V2 形成显式联合类型。

它比 V2 多出来的核心不是“版本号”，而是一整套执行证明：

- 输入可以切片和归约。
- 每个 work unit 携带实际渲染输入的预算证明。
- 携带 router、model、prompt、policy fingerprint。
- generation task 在调度前冻结。
- 产物必须同时匹配 input hash、proof digest 和 policy-set digest。
- 超预算或策略代际冲突不再普通报错，而是产生 recovery envelope。

Pass1 的 V3 状态计算在 [build-orchestrator.ts (line 778)](E:/allwork/download/agent/understand-book/packages/core/src/build-orchestrator.ts:778)：先拆 source fragment，再逐层 stitch，最终归约为一个窗口根。

Profile Sidecar 在 [build-orchestrator.ts (line 1103)](E:/allwork/download/agent/understand-book/packages/core/src/build-orchestrator.ts:1103)：小输入走 fast path，超预算的篇章输入走 fragment → reduce；shadow artifact 的严格验证集中在 [profile-sidecar-reduction.ts (line 976)](E:/allwork/download/agent/understand-book/packages/core/src/profile-sidecar-reduction.ts:976)。

1. 调度前还要处理迁移和冻结

发现 legacy artifact 时，CLI 不允许直接宣称当前协议完成，而是要求显式选择：

- `legacy_resume`：只按冻结的旧生产契约继续，不能宣称 V2 完成。
- `v2_rebuild`：从当前协议重新构建。

入口在 [automatic-build.ts (line 988)](E:/allwork/download/agent/understand-book/skills/build/automatic-build.ts:988)。

V3 work unit 被 lease 或放入 dispatch 前，还要调用 [freezeAutomaticBuildGenerationTask (line 917)](E:/allwork/download/agent/understand-book/skills/build/automatic-build.ts:917)。这样执行期间 policy、prompt 或切片结果发生变化时，不会悄悄污染当前 generation。

### 复杂度主要在哪里

按影响排序：

1. `build-orchestrator.ts` 的控制面过度集中

它同时知道：

- 所有 stage 的完成条件。
- V2/V3 work unit。
- source、artifact 和 quality 新鲜度。
- budget routing、reduction、recovery。
- generation task、policy set 和迁移状态。

它实际上兼任状态投影器、阶段编排器、路由器和协议适配器，是最大复杂度热点。

1. V2/V3 代际并存

[WorkUnitDescriptor 联合类型 (line 99)](E:/allwork/download/agent/understand-book/packages/core/src/stage-work-unit.ts:99) 让很多下游逻辑必须先判断 descriptor 版本。

更容易混淆的是，`AutomaticBuildStageQualityReportV2` 已经会消费 V3 work unit；“quality report 版本”和“work unit 版本”不是同一个版本轴，可见 [automatic-build-quality.ts (line 139)](E:/allwork/download/agent/understand-book/packages/core/src/automatic-build-quality.ts:139)。

1. 一次 stage 执行实际上是磁盘事务

真实链路不是 `extract()`，而是：

```
snapshot
→ route
→ freeze policy/generation
→ claim lease
→ build dispatch
→ executor handoff
→ candidate
→ submit/write
→ quality
→ close
→ recompute snapshot
```

每一步都要处理幂等、进程中断、陈旧 lease、重复提交、身份冲突和部分完成。

1. Pass1 与 Profile Sidecar 的预算归约

这两个阶段既要保证模型输入不超预算，又不能丢失 LID/evidence 关系，因此引入：

```
source slices
→ fragment work units
→ verified children
→ reduction levels
→ final contributor
```

Profile Sidecar 还同时拥有 fast path 和 discourse map-reduce，两条路径最终必须产生相同语义契约。

1. 迁移、shadow routing 与正式生产路径重叠

当前重构沿用了大量 `shadow task` 命名和目录结构，但调度时已经出现 `policy_generation: "v3_only"` 的正式约束，见 [automatic-build.ts (line 1449)](E:/allwork/download/agent/understand-book/skills/build/automatic-build.ts:1449)。这使“影子验证设施”和“生产 V3 路径”的边界在命名上尤其难理解。

最实用的心智模型是：

- Workbench = 来源层。
- `automatic-build.ts` = 运行时和协议适配层。
- `build-orchestrator.ts` = 控制面。
- stage input/write/reduction = 数据面。
- lease/mailbox/dispatch = 持久化并发协议。
- quality/recovery/migration = 收敛与安全门禁。

本次严格保持只读：没有修改文件，也没有运行测试、构建或格式化命令。



## 严格

你的感觉基本正确：问题不是“用了 SHA-256”，而是同一份语义身份被 `input_hash → proof_digest → policy_set_digest → plan_digest → artifact_hash` 多次包裹，并且许多运行时信息也被提升成了 artifact 的硬 freshness 门禁。

先说明：`Understand-Anything-main/.understand-anything` 目前只有 `config.json` 和空的 `intermediate/tmp`，没有 `knowledge-graph.json`，所以这次无法使用现成图谱；以下结论来自源码定点分析。若要图谱支持，需要先在该仓库运行 `/understand --full`。

## Understand-Anything 实际怎么做

它的核心思路比我们轻：

1. 用 Git commit/diff 找出变化文件。
2. `contentHash` 只做“字节完全相同”的快速路径。
3. 字节变了以后，再比较函数、类、import/export 等结构，分成 `NONE / COSMETIC / STRUCTURAL`，见 [fingerprint.ts (line 131)](E:/allwork/download/agent/Understand-Anything-main/understand-anything-plugin/packages/core/src/fingerprint.ts:131)。
4. 根据结构变化数量决定跳过、局部更新、架构更新或全量更新，见 [change-classifier.ts (line 21)](E:/allwork/download/agent/Understand-Anything-main/understand-anything-plugin/packages/core/src/change-classifier.ts:21)。
5. LLM batch 是可损坏、可丢失的增量：格式错误就警告并跳过，见 [merge-batch-graphs.py (line 134)](E:/allwork/download/agent/Understand-Anything-main/understand-anything-plugin/skills/understand/merge-batch-graphs.py:134)。
6. 确定性的 `scan-result.json#importMap` 才是真相源；LLM 漏掉 import edge 时，merge 阶段重新补回，见 [merge-batch-graphs.py (line 913)](E:/allwork/download/agent/Understand-Anything-main/understand-anything-plugin/skills/understand/merge-batch-graphs.py:913)。
7. 允许保存部分图谱，但必须把降级和丢失显式报告给用户。

不过不能把它当成完整范本：

- `analyzeChanges`、`classifyUpdate`、`loadFingerprints` 当前没有生产调用点，只有定义和测试；实际 skill 的增量路径仍主要依赖 Git diff。
- [staleness.ts (line 15)](E:/allwork/download/agent/Understand-Anything-main/understand-anything-plugin/packages/core/src/staleness.ts:15) 会把 Git 错误吞成“没有变化”，这太宽松。
- [persistence/index.ts (line 78)](E:/allwork/download/agent/Understand-Anything-main/understand-anything-plugin/packages/core/src/persistence/index.ts:78) 直接覆盖 JSON，不如我们已有的原子/create-only 发布安全。

因此该借的是“分层与降级思想”，不是照抄实现。

## 我们哪里确实过严

一次定点统计在预构建相关文件里找到约 965 处 `hash/digest/fingerprint` 文本出现——不是 965 个独立校验，但已经说明身份信息贯穿过深。

V3 artifact 同时绑定：

```
target
+ stage
+ work_unit_id
+ input_hash
+ policy_fingerprint
+ proof_digest
+ policy_set_digest
+ artifact_hash
```

见 [semantic-artifact.ts (line 45)](E:/allwork/download/agent/understand-book/packages/core/src/semantic-artifact.ts:45)。

其中有两处明显越界：

- `proof_digest` 包含 estimator 版本、prompt hash、router、token 预算、各种 reserve 和输入 hash，见 [model-input-budget.ts (line 7)](E:/allwork/download/agent/understand-book/packages/core/src/model-input-budget.ts:7)。改变 token estimator 或安全余量，也会让已经生成的语义 artifact 失去 freshness——这属于调度变化，不是语义变化。
- `policy_set_digest` 对 target、stage 和该 stage 的所有 policy member 整体求摘要，见 [automatic-build-policy-generation.ts (line 190)](E:/allwork/download/agent/understand-book/packages/core/src/automatic-build-policy-generation.ts:190)。一个 member 改变，会改变整个 set digest，使其他本来等价的 work unit 也进入新 generation。

另外，“policy 是否相同”现在至少有三套定义：

- `stableJson(left) === stableJson(right)`：[stage-work-unit.ts (line 135)](E:/allwork/download/agent/understand-book/packages/core/src/stage-work-unit.ts:135)
- 全字段 `extractionPolicyEqual`
- 较宽松的 `policyAdoptionCompatible`：[automatic-build-policy-generation.ts (line 435)](E:/allwork/download/agent/understand-book/packages/core/src/automatic-build-policy-generation.ts:435)

真正的问题是：我们没有先定义“哪种相等”，而是让 digest 相等代替了语义判断。

## 建议的新边界

把 artifact 身份压缩成一份可读契约：

```
type SemanticArtifactIdentity = {
  target_revision: string;       // 可信 source/base 修订
  stage: SemanticBuildStage;
  work_unit_id: string;
  input_hash: string;            // 该单元真实模型输入
  semantic_contract: {
    profile_version: string;
    stage_policy_version: string;
    router_version: string;
    prompt_sha256: string;
    schema_version: string;
    quality_profile: string;
  };
};
```

运行证据独立出去：

```
type ExecutionEvidence = {
  run_id: string;
  plan_id: string;
  lease_epoch: number;
  dispatch_id?: string;
  model?: string;
  budget_evaluation: ModelInputBudgetEvaluation;
};
```

规则应是：

| 信息                                         | 处理                                    |
| -------------------------------------------- | --------------------------------------- |
| source/base 内容身份                         | 保留硬门禁                              |
| work-unit 真实输入 hash                      | 保留硬门禁                              |
| prompt/schema/router/profile 语义契约        | 保留一次，不嵌套重复摘要                |
| artifact payload checksum                    | 保留，用于损坏和幂等检测                |
| 用户确认的 `plan_digest`                     | 保留，用于防止确认后计划漂移            |
| budget proof、estimator、reserve             | 调度时重算，不决定旧 artifact freshness |
| `policy_set_digest`                          | 只作为一次 run/generation 的分组索引    |
| dispatch/preflight/evaluation/receipt digest | 留作审计，不参与语义复用                |
| model、lease、时间、executor                 | 只进 provenance/性能账本                |

对应状态不再只有“匹配/冲突”：

```
VALID
STALE_REBUILDABLE    // 输入或语义契约变化，自动重建
INVALID              // payload 损坏、target 错误，隔离
DEGRADED             // 部分可选单元失败，显式警告
```

尤其是 `STALE_REBUILDABLE` 不应升级成需要用户理解 digest 的 `policy_generation_conflict`。

## 最值得借鉴的四点

- 借鉴结构变更分级：哈希不同不等于语义失效。我们的 [ADR-0019 (line 1)](E:/allwork/download/agent/understand-book/docs/adr/0019-构建侧增量-merkle双轨检测-变更分级-pass2受影响追踪读时兜-独立基座内容寻址.md:1) 其实已经借过这一点，但后来 V3 执行协议又把严格性加回来了。
- 借鉴“确定性基座 + 有损 LLM 增量”：`base.json/LID/source_manifest` 是真相源；LLM artifact 是可重试的补充，不必每层都互相证明。
- 借鉴 merge 时修复和显式警告：坏单元隔离、确定性关系补回、最终按覆盖率/质量关闭，而不是任意 digest 漂移都阻断整 stage。
- 借鉴只在提交点严格：像 Understand-Anything 只有 fingerprint 基线成功后才推进 `meta.json`；我们也应把最强门禁集中在 source 信任、用户确认和最终原子发布。

不应借鉴它吞 Git 错误、非原子写入、以及无条件“部分结果总比没有好”。对 source、引用锚定和必需 Pass1 覆盖，我们仍应 fail-closed；只有可选 enrichment 才适合 `DEGRADED`。

如果进入重构，我建议第一刀先不删除任何字段：只新增统一的 `classifyArtifactFreshness()`，把现有每个失败归入 `VALID / STALE_REBUILDABLE / INVALID / DEGRADED`。收集一轮真实工作区结果后，再把 `proof_digest` 和 `policy_set_digest` 从语义 freshness 中移除。这样能先证明哪些门禁真的在保护正确性，哪些只是制造重建和迁移噪声。
