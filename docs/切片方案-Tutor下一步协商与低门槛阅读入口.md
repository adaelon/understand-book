## 1. 对齐确认

**FrozenIntent**：读者不必会写教学 prompt，就能从一处真实阅读卡点开始；Tutor 先交付帮助，再提出具体、可执行、可纠正的下一步。读者可接受建议、对原回答点击“这一步没跟上”、自由改问或返回阅读，仍由同一个 Resident / TutorLoop 承接。

**TermMap**：TutorSession 保存学习意图；ResidentGoal 保存任务交付；TeachingMove 是本轮实际动作；Continuation 是未来帮助的轻量提议；ContinuationChosen 是用户接受路线的事实，不是作答；回答接续是绑定已交付回答的本次继续／纠偏请求，不等于正式活动回应；Hypothesis 与 Performance 沿用现有定义。

**RiskReceipt**：用户确认复用 TutorLoop、区分选择与作答，并接受补齐原题帮助归属、低门槛回答纠偏、首次帮助后的显式开启入口及提前产品验证。字段细节和切片粒度尚待实现验证。

**ChangeType**：增加低门槛输入与教学交付的继续操作合同；扩展既有事实和请求元数据，不新建推荐 Agent、推荐数据库或用户能力档案。

### 首版范围

首版闭环是：**已核验选区 → 直接解释 → 显式进入活动 Tutor → 一个具体建议 → 用户接受 → 获得下一轮帮助 → 点击“这一步没跟上”或自然纠偏 → Tutor 改变讲法**。已经处于活动 Tutor 时直接接续；普通模式仍可解释与纠偏。

Markdown/PDF 复用各自既有选区来源合同；建议范围继承当前教学焦点，支持解释、对比、观察。图形或交互是否必要仍由原呈现能力判断。不新增跨章/跨书自动路线、整书计划、停留触发、自动测试、完整答案预生成或长期偏好自动分类。

本方案不修改公共 TeachingMap、预构建流水线和 ADR-0162 的远程 MCP/调用次数合同。Tutor 基础成品准入、无正式对象时的来源教学、普通理解观察继续沿用 ADR-0158/0161。

## 3. 端到端行为合同

### 3.1 直接帮助

1. 用户主动点击“帮我弄懂这段”。绑定此刻的不可变选区、来源版本、聊天和工作区，不在请求发送时重新取一个不同选区。
2. 原“围绕这段提问”仍进入编辑。直接帮助不清空已有草稿，也不把草稿自动追加到请求；未确认提交留在原恢复入口。
3. 服务端先校验选区，再解析动作及原活动帮助归属。命中第 3.3 节时返回原活动帮助入口，不接纳解释 Run。其余路径允许合法类型化输入的零文字；没有动作的空聊天继续拒绝。
4. Tutor 关闭、暂停、材料不匹配或未就绪时，按原边界执行普通解释，不偷偷开关 Tutor。普通观察可按 ADR-0161 继续发生。
5. 满足原首次教学条件时，初始意图包含动作和来源范围；不把“帮我弄懂这段”这几个字直接当作无锚点的长期目标。
6. 活动 Tutor 的 TeachingTarget 仍需满足本轮完整目标原文读取。精确子串选区不是已读取整个 LID 的证明，不能为降低点击门槛而绕过 target_read_this_turn。

### 3.2 下一步协商

本轮先交付有用内容。需要继续时，附一个推荐项，最多一个备选项。例如“用同一组数字对比这两个量分别变化时的结果”，而非固定的“总结/举例/动画/测试”功能菜单。

首版每回合至多一个建议集合。一个回合含多个实际 Move 时，显式指定唯一承载建议的 Move；不改变已有合法多活动的含义。建议缺省时仍可自然结束。

用户接受后，新 Run 完成所选帮助，不再次要求用户复述已知对象或选择同一教法。用户直接改问时，不自动附带旧 choice；新请求被接纳后旧建议退出可执行主入口。未发送的编辑草稿不会令服务端候选失效。

示例文案只是验收夹具，不是写入全局 prompt 的固定剧本。推荐应随真实内容改变，不能以“生成高阶展示”代替回答用户问题。

### 3.3 正式活动与演示

有待回应的当前正式评分活动时，以回答、提示、揭示、改答等既有控件为主，不并列展示新的路线建议。判断以同一 TutorSession、当前焦点、来源版本及活动事实为准，不把所有历史未答题永久当作阻塞项。

原文直接帮助、回答继续和回答纠偏都在接纳 Run 前经过共用分流：选区与当前活动 TeachingTarget 的来源范围相交，或原回答就是该活动及其已关联帮助时，返回原活动引用并定位其已有提示／揭示控件。旧对象式活动使用原冻结评分来源范围，不要求改写历史 target。多个当前活动命中时列出对应原活动供用户选择，不猜测帮助归属。Tutor 关闭或暂停仍保留当前原题关系；无关选区与回答按普通请求处理。

定位原题不记为已获得帮助；读者实际请求并看到提示／揭示后，沿原 HelpDelivered → HelpDisplayed 路径保存，后续作答冻结原 assistance_refs 和尝试次数。没有可用帮助时明确显示当前题目未提供该帮助，保留原活动与返回阅读入口，不另起无关联的解释 Run。首版不新增题内生成帮助链路。

解释型交付可显示 continuation；推荐本身不包含正确答案、私有评分准则或未来题面。之后实际产生题目时，仍在交付前冻结原评分合同。

普通回答和演示工作区共用同一建议所有者，不复制成两个可执行集合。涉及演示参数的请求复用原不可变 PresentationFollowUp 回执；没有确切现场时，只承诺概念层解释，不声称已绑定滑块当前值。不同版本不可静默换绑。

### 3.4 回答接续、纠偏与首次开启

已持久交付的回答提供“这一步没跟上”，请求绑定原聊天、回答 turn 及可选的回答摘录。选中回答文字时可直接对该片段求助；不选文字时以该次回答为背景。服务器核验原公开回答并冻结引用，模型直接拆开一步或换一种具体讲法，确实无法定位时才问一个简短具体问题。只点击该动作不能支持“缺少某前置知识”等具体诊断。

回答选区的定位与摘录可复用现有笔记／分享代码；回答提问的输入类型、服务端验证、历史投影和发送控件均须新增。摘录属于 Agent 回答，不转换成书源选区或用户原话，不自动填 teaching_ref。命中当前正式活动时仍走第 3.3 节。

Tutor 默认关闭的首次解释附近提供现有“开启连续教学”入口，说明其对所有书籍生效。开启只改变控制状态；成功后，在本材料会话边界满足时显示“继续理解这段”，用户点击才以原回答和来源范围发起 continue_answer。无当前会话时沿首问规则建立有范围的意图；已有匹配会话则接续。存在暂停、结束或其他材料会话时先完成既有显式管理，再单独发起请求。开启失败不发送，后续请求失败则保留已经成功保存的控制状态并按原请求恢复。

不为已交付普通回答后台补造建议。就绪不足时明确说明动态建议暂不可用，原文解释与回答纠偏继续工作。自由输入草稿在以上动作中都独立保留。

## 4. 新增最小数据与接口合同

本节固定语义边界；新增 Rust/TypeScript 类型采用项目现有合同导出流程。不得同时维护两套含义不同的手写 schema，也不得只改 TypeScript 类型而漏掉 Runtime ToolSpec 和 serde 校验。

### 4.1 TeachingMove.continuation

TC1 已实现以下核心结构；省略导出属性，完整类型见 `crates/runtime/src/tutor_continuation.rs`：

```rust
// TC1 核心序列化字段。
struct TeachingContinuation {
    recommended_option_id: String,
    options: Vec<ContinuationOption>,
}

struct ContinuationOption {
    option_id: String,
    label: String,       // 用户可见的、具体的行动请求
    purpose: String,     // 用户可见：本步解决什么问题
    move_kind: ContinuationMoveKind, // explain | compare | observe
}

// TeachingMove 增加：
// #[serde(default, skip_serializing_if = "Option::is_none")]
// continuation: Option<TeachingContinuation>
```

运行时和服务端同时校验：集合为 1–2 项、推荐项属于集合、标识唯一、文字非空、kind 在白名单中、总载荷有界。TC1 已用共用常量固定文字上限 240 个 Unicode 字符、标识上限 64 个 Unicode 字符，并覆盖边界测试。

继承本 Move 的 TeachingTarget、原来源和绑定，不接受模型在选项内额外传入用户身份、原始工具调用、导航命令、持久写入命令或一份未验证的新目标。目的和文案走原公开文本/来源校验。系统生成的文案不能据此获得 reader_write 等额外权限。

建议只在已完成回答的公开交付中可见；未完成的 select、预览和内部制作候选不可选择。增加公开读取投影，至少返回 delivery_ref、origin_turn_id、原 target 摘要、continuation、availability 及已接纳 Run 引用（如有）。读投影不调用模型。

### 4.2 用户输入

AgentChatMeta 新增两类互斥入口；回答引用只与相应 entry_action 配套：

```text
entry_action: "explain_selection" | "clarify_answer" | "continue_answer"
answer_ref: { turn_id, excerpt? }             # 后两种动作必填
teaching_choice: { delivery_ref, option_id }   # 接受已交付建议
```

二者与自由输入规则：

| 请求形态 | message | 处理 |
|---|---|---|
| 普通聊天 | 必须非空 | 沿原路径 |
| explain_selection | 可空，question_quote 必须有效 | 解析为解释选区；不带 answer_ref |
| clarify_answer | 可空，answer_ref 必填 | 绑定原回答及可选摘录，表达本次仍需帮助；不带 question_quote |
| continue_answer | 可空，answer_ref 必填 | 绑定原回答及原范围，明确请求下一步帮助；允许已开启且就绪的首次教学请求或匹配的活动会话 |
| teaching_choice | 可空 | 服务端从原交付解析行动；额外文字仍是用户原话 |
| 两种新入口同时出现 | 任意 | 拒绝歧义输入 |
| 新入口与不相容的 teaching_ref / note / replacement 操作混用 | 任意 | 拒绝，不猜测哪个授权有效 |

已支持且同版本、同对象的 presentation_follow_up 可与选择同行；不允许借此换成另一活动或来源。原任务关系由服务端解析，客户端不能凭伪造 goal_id 把选择接到他人或其他材料任务。

归一化白名单必须增加新字段，支持“有合法动作的空 message”，并保留动作、回答引用、摘录及选项之间的差异。不能把它们归一化为同一个“继续”，否则同一请求身份可能误接纳不同意图。

新选择必须携带原建议对应的 expected_chat_head，并在服务端再次检查；不能在发送前读取最新 head 覆盖它。当前 network-client 的 createRun 并未自动填写该字段，必须显式接通。该字段的有效性不替代真实 delivery 所有权核验。

answer_ref 只能指向当前读者、本聊天中已完成且成功交付的回答；excerpt 复用原回答文字提取规则核验。回答接续可明确指向历史回答，但携带点击时的当前 expected_chat_head，不使用旧回答生成时的 head，也不消费旧 continuation。continue_answer 的接纳条件为 Tutor 已开启、材料就绪，且无当前会话或当前会话有效并匹配材料；无会话时由本次已接纳请求建立初始意图。控制在点击后变化时返回现状，不隐式开启或恢复。

### 4.3 服务端解析与来源表达

新增共用的解析结构（建议名 `ResolvedInteraction`），保存：输入来源、原始用户补充、被接受的公开行动、原 delivery/option 或 answer_ref、经核验的回答摘录、来源与可用 target、接纳所用聊天 head、必要的演示回执引用。普通回答可以没有 TeachingMove，其背景来自原持久回答和原来源关联，不伪造教学目标。数据源仅为已核验请求和原交付，不调用模型解析“按钮是什么意思”。

共用解析器在 Run 接纳前返回 `run_input(ResolvedInteraction)` 或 `activity_help(delivery_refs)`。后者只提供当前读者可访问的原活动帮助入口，不创建 Run、选择事件或模型请求；提示／揭示继续调用原 tutor action/display 协议。原文和回答两类求助均适用，前端隐藏按钮不替代服务端分流。

来源用 `typed / ui_entry / ui_choice` 区分。模型上下文中的 `current_request` 可包含被接受的公开请求，但同时携带结构化来源；聊天历史与后续画像审核也保留此区分。界面显示“选择：……”或对应“操作：……”，不显示系统补写的长 prompt。clarify_answer 只表明这次仍需帮助，continue_answer 只表明希望接续，二者不互相替代。

`tutor.step` 的 intent_origin 增加 `current_action`：服务端依据本轮冻结 ResolvedInteraction 校验，不靠构造虚假 intent_quote。用户补充的真正原话仍可使用 current_request 来源。当前明确要求优先于会话默认或已确认偏好，直接解释继续满足现有动作一致性规则。

choice 和回答接续均不自动生成 chat_response、attempt 或 assessment。不要将其写进 teaching_ref 来偷用旧路由。

| 已交付建议集合 | 原 MessageDelivered 的公开 Move 内容 | 不独立建推荐表；建议不是未来教学正文 |
| 已接纳动作、解析结果和请求身份 | 已持久接纳的聊天回合/Run 输入 | 建议消费状态从这里判断；回答接续保存原回答与摘录，不等学习事实补记才防重 |
| 展示与选择事实 | 原 learning.db / teaching_trace | 可从原接纳输入幂等补记，不是另一份执行队列 |
| 能力假设和表现 | 原 LearningEvidence / projection | 仅有合法依据时更新 |
| 稳定偏好 | 原 Profile 体系 | 不由单次选择自动确认 |

新增 `ContinuationDisplayed`、`ContinuationChosen` 事件。前者记录真正可见项、顺序及推荐标识；后者关联原集合、被接受选项和接纳 turn。展示事件按交付/实际展示集合幂等，选择事件使用接纳 turn 派生的稳定身份。

展示上报失败不阻止一个已通过来源与权限校验的真实选择。不可补造“用户看过所有备选”，也不可把遥测完整性当学习证据充分性。

建议的 offered、eligible、consumed、stale 等是依据原交付、当前控制与接纳事实计算的视图，不另建一份可独立漂移的状态机数据库。

## 5. 接纳、并发与恢复

### 5.1 多人入口的明确顺序

```text
原 client_request_id + 原 typed payload
  → 按 key 查已有接纳；同 key 同载荷回原结果，异载荷冲突
  → 核验 workspace / chat / expected head / publication / 动作所需 Tutor 边界 / 原引用
  → 共用解析：命中当前题目帮助则返回 activity_help，不接纳 Run
  → 其余动作冻结 ResolvedInteraction，分配原 Run/turn 身份
  → 在回合持久输入中保存原请求、解析结果及待追加教学事件
  → 幂等追加教学事件，并标记 preparation_complete
  → queued
  → 沿原领取、额度、取消和执行路径运行
```

顺序中的存储分布于聊天、学习库与控制库。复用 run_admission 的准备/对账协议，不声称它们共享 SQLite 事务，也不先持久写一个“点击成功”再指望浏览器发第二条聊天。

此接纳顺序覆盖原文解释、回答接续、回答纠偏与建议选择。只有 teaching_choice 追加 ContinuationChosen；其他动作保留输入来源与原引用，沿原使用事实路径记录。回答接续不受“同一建议集合只可选一次”的限制，新点击是新明确请求，重试仍复用原请求身份。

同一个交付集合只接纳一次新路线选择。新请求身份不能绕过原 head 与已接纳回合约束；同 key 重试必须先识别已有 Run，不能因该 Run 已经改变 head 而误报过期。

原选择已接纳后遇到额度停止、取消或执行失败，仍是“选择已接纳、任务未完成”，不是“建议可无限重选”。恢复沿既有未完成任务/显式继续入口，来源和授权变化仍须核验，不复制出新的选择事实或重置费用账目。

### 5.2 本地入口

复用同一解析器、边界校验和上下文结构，但不把本地调用假装成已有多人 RunAdmissions。

在既有本地 turn/history 接纳中持久保存新动作的 client_request_id、归一化载荷与解析输入，先查重再 precommit。接纳后才补教学事件、执行模型；重启只恢复已有结果或如实标记中断，不自动重放未知执行。

必要扩展局限于新类型化动作及既有本地回合存储；不要为本功能引入远程控制库或改造整个本地运行架构。无法证明本地幂等时，本地新类型化动作入口不开放，不能靠前端一次点击锁宣称已满足。

### 5.3 故障注入矩阵

| 注入位置 | 期望恢复行为 | 禁止行为 |
|---|---|---|
| 校验失败，尚未接纳 | 返回具体错误，旧阅读现场和草稿保留 | 创建新教学会话或调用模型 |
| preparing 已登记，冻结输入未保存 | 沿原流程关闭/对账；新操作不得撞旧身份 | 恢复时重新跑模型或重造建议 |
| 回合输入已保存，学习事件未全补齐 | 从原输入补齐同一事件，再到准备终态 | 再产生一条选择或第二个回合 |
| 事件已补齐，prepared 未写完 | 幂等重试并补 prepared | 按当前现场重新解释原选项 |
| queued 后响应丢失 | 按原 key 找到同一 Run | 浏览器生成新 key 重发 |
| claimed 后宿主退出 | 沿原中断/未保存恢复；不盲重放 | 假设模型未执行而自动再调用 |
| 交付已存，教学交付回执写失败 | 从已保存结果补交付与建议 | 重新生成答案或重复扣费用 |
| 展示回执写失败 | 保留可重试展示记录；合法选择独立核验 | 把回执失败当用户没学会 |
| 双击或两标签页选不同项 | 最多一个新选择被接纳，另一方获取现状/冲突 | 只依赖 disabled 或浏览器去重 |
| 已开启连续教学，后续请求未接纳 | 保留成功保存的开关状态与原回答，恢复原请求 | 把开关动作当成已执行请求，或重复开启／创建会话 |
| 已定位原题，帮助尚未展示 | 保持原活动入口；按原 action/display 恢复 | 写入 HelpDisplayed 或新解释 Run |

## 6. 模式、失效与用户可见结果

| 条件 | 接受建议前的行为 | 用户出口 |
|---|---|---|
| 活动 Tutor、原来源和 head 有效 | 可以接纳 | 原建议或自由输入 |
| Tutor 关闭 | 动态建议不执行；直接帮助走普通解释 | 自由提问或显式开启 |
| 暂停/结束 | 不借旧 choice 隐式恢复 | 既有恢复/新学习入口，且恢复不自动发送旧选择 |
| 控制或学习目标 revision 变化 | 旧集合过期 | 按当前现场显式继续，不后台刷新模型 |
| 新用户请求已接纳 | 原集合停止可执行 | 使用新请求结果，不与旧推荐竞争 |
| 仅编辑输入、尚未发送 | 不写失效事实 | 用户仍可选择；已有草稿不被清空 |
| 来源/发布授权变化 | 不换绑最新来源 | 查看旧结果或重新明确请求 |
| 其他聊天/用户/材料引用 | 拒绝，按原访问规则返回错误 | 不泄露对方建议内容 |
| 同一集合已选择 | 读取原接纳/结果状态 | 进入原任务，而非重新执行 |
| 一般网络错误、结果未知 | 保留原 key 与元数据并核对 | 原重试/恢复入口 |
| 运行中暂停 | 沿原语义完成已明确请求或用户停止；不继续自动教学 | 原停止按钮，不自动恢复开关 |
| 首次解释后 Tutor 仍关闭 | 就近显示现有显式开启入口；开启本身不发送 | 开启成功后另点“继续理解这段”，或直接对原回答纠偏 |
| 回答继续／纠偏指向历史回答 | 核验原回答，以点击时当前 head 接纳新请求 | 原回答与摘录可见，不重放旧建议 |
| 求助命中当前待作答活动 | 返回 activity_help，不接纳解释 Run | 原提示／揭示；无可用帮助时明确提示并保留阅读出口 |

新增错误语义建议归并为：INVALID（无效输入）、STALE（来源/目标/head 过期）、ALREADY_ACCEPTED（已有接纳）、UNAVAILABLE（当前控制/能力不允许）。复用原认证、忙、额度和存储错误，不另发明平行状态码体系。TC1 固定具体代码及用户可见文案。

## 7. 证据接续与防污染

选择事实进入当前意图和近期交互；纯选择不放入必须产生理解假设的待处理集合。需要同步更新 `teaching_recent` SQL 过滤、trace 摘要与回读、LearnerContext 组装及公开历史，否则存储成功不等于下一轮真正用到。

在 source/revision/会话规则内，用户真正的复述、纠正和困难描述仍可形成 hypothesis。系统必须保留原话、依据、适用目标、teaching_implication 与 supersedes，不用选项文案替代用户的认知表达。

下列断言纳入自动测试：

- 点击“看例子”，不增加 independent_support / assisted_support / difficulty，也不自动写稳定偏好。
- 点击“继续读”或不选任何项，不更新掌握或能力高低。
- 连续多次选同一形式，不强制生成永久“学习类型”。
- 用户指出“不是不懂计算，是不懂这个条件”，下一轮确实改变讲解重点；不能只保存一条假设却继续旧方案。
- 点击“这一步没跟上”保留其动作来源与原回答，下一轮拆解或改变讲法；不得仅凭点击生成具体知识缺陷诊断。
- 点击“继续理解这段”只形成继续请求，不生成“仍不懂”的陈述或能力假设。
- 正式题目看到提示后再作答，沿原帮助条件评分；新入口不能清空 assistance_refs 或尝试次数。
- 待作答题目 → 相关原文直接帮助／原回答纠偏 → 原题帮助实际展示 → 首次答对，保留帮助引用，不能增加 independent_support。
- 有正式待作答活动时，不生成可绕过活动语义的新 continuation；后续扩展需另行满足原活动帮助合同。
- 普通自由对话不被新按钮系统截获；Tutor 关闭时不 select/assess/隐式创建会话。

首版不对完整 learning_evidence 体系做重构。正式评分、帮助后表现与用户纠正使用既有存储和投影，只增加必要的输入来源识别、事件过滤和回归测试。

## 11. 产品验证与结果解释

形成性验证随切片推进：TC2 先验证直接帮助与显式开启入口，TC3 验证真实材料建议，TC5 验证建议未猜中后的纠偏；TC7 完成全部工程矩阵与完整读者路径。每次运行针对明确断点，结果决定是否调整对应入口、建议策略或讲法，不以同一批样本反复证明已通过的结论。

首次入口验证从默认关闭 Tutor、尚无当前会话的真实起点开始；完整验收同时包含已有活动会话。可安排首轮约 5 位目标读者各完成一次自己的阅读卡点任务，数量作为形成性工作安排，结论保留实际任务与人数。

任务只说“找一段确实没看懂的内容，用产品帮助自己继续读下去”，不提前教产品术语、开启 Tutor 或演示 prompt。记录用户在哪一步犹豫、重复输入、改问、退出，以及系统有没有兑现下一步。对读者实际仍未弄懂或建议未对准的任务，继续观察其能否少量表达完成纠偏；未发生这类情况的样本不能计作纠偏成功。

| 观察项 | 记录口径 | 不能声称 |
|---|---|---|
| 独立开始 | 有效卡点任务中，无旁人指路完成首次帮助的比例 | 只点一次按钮就一定理解 |
| 入口转换 | 从默认关闭状态自行开启并以原回答发起第二次帮助的情况；区分不愿开启与找不到入口 | 预先开启的演示证明新用户可独立接续 |
| 操作性表达 | 为补范围、教法和功能指令而额外输入的次数；与内容思考区分 | 所有输入越少越好 |
| 建议适用 | 人工检查建议是否围绕当前障碍、是否真的可执行 | 点击率高等于有学习收益 |
| 选择兑现 | 已接纳选择中，完成所承诺帮助的比例；列失败原因 | 模型输出成功等于用户学会 |
| 低门槛纠偏 | 原问题仍未解决的任务中，通过回答按钮、片段或少量表达后，解释是否实际改方向；记录额外操作性表达 | 只会接受推荐的路径证明协商完整 |
| 阅读推进 | 用户能否说明关键关系、继续理解后文；保留证据局限 | “继续读”或曝光时长证明掌握 |
| 成本与可靠性 | 每次接纳的 Run、调用、用量、停止和恢复事实 | 新功能无额外 token 成本 |

报告保留任务和分母，区分工程替身、真实模型与真实读者结果。不预设“提高百分之多少”的结论，不把不选推荐当负反馈训练数据，不收集无关的键击或阅读停留轨迹。

## 12. 最终交付与停止条件

实施完成应留下：相应源码与定向测试、更新后的类型/公开投影、真实失败恢复记录、Markdown/PDF 与两种宿主的覆盖表、首次入口与纠偏的形成性记录、内容质量对照、兼容和发布准备文档。

任一关键权限/证据/接纳门禁未通过时，停止开放对应新入口，保留原阅读、自由提问和已有 Tutor 能力。改进范围限定在发现的断点，不以“后续做一个更智能的推荐系统”代替本轮闭环。

本轮成功的最小证据是：**读者从一处原文卡点开始，无须组织功能指令就能获得帮助，并自主进入下一次有用帮助；建议未猜中时，通过绑定原回答的少量表达让 Tutor 改变讲法；全过程保留原题帮助条件、输入身份与用户控制。**

**已知限制**：首版要求读者能指出原文或已交付回答中的卡点；无法定位卡点和跨范围补前置知识仍需其他入口。普通模式提供直接解释与纠偏，动态建议需活动 Tutor。学习收益与表达负担的实际改善以真实读者证据说明。
