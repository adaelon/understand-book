# 第 3 章 数据身份与状态归属

设你同时打开两个窗口。左边阅读一本书的第三章，右边查看另一份材料。你在左边提问，请 Agent 解释当前段落并保存笔记；等待回答时，又在右边翻了几页。

系统需要让两个窗口各自保留位置，让笔记属于同一位读者，让左边的回答继续使用最初那本书。如果另一位读者也打开同一本书，公共材料可以共享，聊天和笔记则应进入各自的存储。

这些要求最终都会变成数据问题：一个标识到底指向什么，一份状态由谁持有，一次运行结束后应该把结果交给谁。本章先解释材料的身份，再追踪服务、用户、阅读现场和运行之间的关系。

## 先确定“同一本书”指什么

文件路径是寻找材料的一种方式。把一个构建工作区从一个目录搬到另一个目录，材料内容可以完全不变；如果把修订后的正文覆盖到原路径，路径相同，材料却已经变了。依赖路径本身，难以准确回答旧笔记和旧引用指向哪份内容。

项目使用 `book_id` 表达一份内容基座的身份。原文、定位树和相关公开成果都需要回到这份基座。项目的[版本约定](../../adr/0146-portable-build-workspaces-and-incremental-book-updates.md)规定，搬迁保持身份，正文或实际来源附件改版形成新的基座，并保留前后版本的关系。

材料内容固定之后，准备程度仍可能变化。例如，同样一份原文可以后来补齐全书结构或其他阅读能力。于是还需要指出读者使用的是哪一次发布。[PublishedBookRef](../../../crates/server/src/published_library.rs) 用两个字段表达这个身份：

```rust
pub struct PublishedBookRef {
    pub book_id: String,
    pub publication_id: String,
}
```

`book_id` 确定内容基座，`publication_id` 进一步确定该基座的一次不可变发布。发布清单与具体目录由 `PublishedBook` 连接起来；URL 也包含书籍和发布两个层次。运行保留确切发布，就能够说明自己当时使用了哪份成果。

这里有四类相关但用途不同的标识或位置：

| 标识或位置 | 它回答的问题 | 例子中的作用 |
| --- | --- | --- |
| 文件目录 | 去哪里读取文件 | 搬迁后可以重新找到材料 |
| book_id | 这些原文与成果属于哪份内容基座 | 区分修订前后的正文归属 |
| publication_id，连同 book_id | 使用的是哪次发布 | 区分同一基座不同准备程度的已发布成果 |
| LID，连同材料身份 | 这份材料内部的哪个位置 | 将段落、引用、导航和批注连接起来 |

LID 解决的是材料内部寻址。例如，`3.2.5` 表达一个层级位置；另一份材料也可以有同样的 LID。引用要同时知道所在材料，才能把这个位置解析成有意义的原文。

## 三类数据怎样连接

有了身份，再看内容怎样组织。理解项目时，可以先区分原文与定位、语义与结构、用户记录三类数据。

原文与定位提供“文字实际在哪里”。`ReadOnlyBase` 包含 `book_id`、`lid_nodes`、`graph_nodes` 和 `graph_edges`；其中 `LidNode` 的 `span` 回到原文范围，`children` 与数值路径表达层级和顺序。读取工具加载正文后，就能从 LID 找到对应文字。

语义与结构提供“怎样接近所需信息”。概念、关系和全书结构把问题与可能相关的位置连接起来。它们建立在材料之上，可以辅助检索和阅读规划。第 2 章讨论的补充成果，也通过旁路文件与基座一起提供这些能力。

用户记录提供“这位读者做过什么”。笔记、高亮、聊天与学习状态需要保留个人归属，并根据用途关联书籍和来源位置。两名读者使用相同的公共材料，所产生的私人记录仍然可以不同。

这样的分离让公共成果可以被重复使用，也让私人状态按自己的生命周期保存。更新语义成果时，系统需要考虑发布身份；保存一条笔记时，则需要找到用户的存储和对应材料。两种操作会进入不同的写入路径。

## 跨语言契约还包括单位

[base-schema](../../../crates/base-schema/src/lib.rs) 使用 Rust 声明基座类型，并通过 `ts-rs` 向构建侧导出 TypeScript 定义。[生成的 LidNode.ts](../../../packages/core/src/generated/LidNode.ts)可以看到相应字段，[segment.ts](../../../packages/core/src/segment.ts) 则导入该类型构造位置节点。

这样可以减少字段名称和形状各自演进造成的偏差。但类型形状一致，还需要字段含义一致。`Span` 就是一个很具体的例子：它包含两个整数 `start` 和 `end`，实际含义是原文中半开区间的 UTF-16 code unit 下标。

为什么要把单位写清楚？构建侧使用 JavaScript 字符串下标；Rust 中的字符串则以 UTF-8 存储。用同一对数字直接索引两种表示，可能取得不同结果。

以教学字符串 `A中B` 为例，`中` 在 UTF-16 下对应 `[1, 2)`，在 UTF-8 字节序列中对应 `[1, 4)`。如果把构建侧的 `[1, 2)` 当作 UTF-8 字节范围，就只取得这个汉字编码的一部分。普通中文正文已经足以触发这种单位错误。

因此，`Book` 加载正文时建立 UTF-16 表示，`Book::text` 按同一单位切片：

```rust
    pub fn text(&self, lid: &str, end_lid: Option<&str>) -> Result<String, ToolError> {
        let start = self.node(lid)?.span.start;
        let end = match end_lid {
            Some(e) => self.node(e)?.span.end,
            None => self.node(lid)?.span.end,
        };
        Ok(String::from_utf16_lossy(&self.source_u16[start..end]))
    }
```

`end_lid` 缺省时，读取一个位置的范围；存在时，结束边界来自目标位置的末尾。最后一行使用 `source_u16`，把构建侧的范围单位一直延续到读取侧。

这个例子说明了数据契约的两个层次。生成类型约束“有哪些字段、用什么形状表达”，源码中的语义约定则继续约束“这些数字怎样解释”。面试中讨论跨语言接口时，可以用它说明为什么仅仅能够成功解析 JSON 还不够。

## 服务、用户、现场和运行分别持有什么

接着回到两个窗口的场景。如果把所有状态都放进一个“当前书籍”对象，两个窗口容易相互影响；如果给每次请求复制一份用户存储，又会让并发写入缺少共同的归属。因此，当前实现按不同的使用范围组织对象。

| 范围 | 主要实现入口 | 主要持有内容 | 生命周期上的关键含义 |
| --- | --- | --- | --- |
| 服务 | ServiceState，以及网络宿主使用的 PublishedLibrary 等组件 | 运行配置、模型适配器、发布材料管理等 | 多个用户或现场可以使用服务能力 |
| 用户 | UserRuntime；网络侧由 UserRegistry 管理 | 私人存储、聊天历史及相关持久状态入口 | 同一用户的窗口访问同一个用户状态归属 |
| 阅读现场 | ReaderWorkspace；网络侧由 WorkspaceRegistry 管理 | 所用材料、Reader、选中的聊天、现场消息和代际 | 每个现场可以独立阅读和导航 |
| 一次运行 | RunScope 与 RunContext | 固定归属、提问输入，以及运行中的消息、证据和进展 | 运行结果始终能够找到原任务与原材料 |

[本地 AppState](../../../crates/server/src/lib.rs) 直接组合 `services`、`user` 和 `workspace`。网络服务则还要管理多个用户和现场，相关注册表在各自范围内持有对象。这些实现的共同点是明确谁拥有可变状态，再让操作到相应所有者处执行。

[UserRuntime](../../../crates/server/src/user_runtime.rs) 持有 `MemoryStore`、聊天历史和会话存储等。网络侧的 [UserRegistry](../../../crates/server/src/user_registry.rs) 使用共享句柄管理加载的用户运行状态，避免每个窗口各自复制一套私人存储对象。

[ReaderWorkspace](../../../crates/server/src/reader_workspace.rs) 则持有 `Reader`、当前 `Book`、选中的聊天与现场消息。这里的 `messages` 服务于当前现场；私人聊天的持久归属仍在用户状态。切换现场中的聊天，不等于删除原聊天。

同一用户再打开一个窗口时，新现场可以拥有自己的 `Reader`。在第二个窗口翻页，只改变那个现场的阅读位置；两个窗口仍能访问属于同一用户的私人记录。公共 `Book` 可以通过 `Arc` 共享引用，复制一个引用不会复制整本已加载材料。

这个结构也影响回收。发布库可以撤下自己缓存中的强引用，现场或运行保留的引用仍然维持材料存活。缓存是否还想保留一本书，与正在运行的任务是否还需要它，是两项不同的判断。

## 一次运行为什么要固定归属

假设左边窗口的一个 Run 已经开始，使用材料 A、聊天 C、现场 W。模型等待期间，其他状态可能继续变化。后续工具如果只查询“现在选中了什么”，就有可能偏离原任务。

[RunScope::capture](../../../crates/server/src/run_scope.rs) 在接纳任务后保存用户、现场 ID 和代际、聊天、回合、书籍及存在时的发布对象。它还保存提问时的 Reader 输入、选区和模型绑定。这样，运行既知道要解释哪次输入，也知道结果应当回到哪个归属。

保存这些引用不等于冻结整个应用。运行中的笔记写入仍然要访问用户当前的权威存储，阅读动作也需要操作真实 Reader。固定的是任务的归属和所用输入，可变状态继续由各自对象管理。

因此，`RunScope` 分别提供两类检查。`check_user` 确认用户身份，以及原聊天、书籍和回合仍然对应；`check_scene` 确认现场 ID、代际、发布和选中聊天仍与运行开始时一致。需要同时满足时，`check_workspace` 将两者连接起来。

现场中的 `generation` 用来识别一次重绑。重新绑定发布或选择另一个聊天时，会使现场失效；其中最小的状态变化是：

```rust
    pub fn invalidate(&mut self) {
        self.generation += 1;
        self.active_agent_stream = None;
    }
```

如果现场从 W 的第 7 代变成第 8 代，旧 Run 再尝试操作现场，就会得到 `WORKSPACE_STALE`。即使后来又回到同一本书，代际变化仍然表明期间发生过重绑。另一个独立窗口的普通翻页，则不会让原窗口的代际自动变化。

这项检查保护的是任务指向。旧任务要导航的位置属于原材料和原现场，不能因为界面已经打开别处，就把动作应用到新现场。

## 现场变化后，哪些结果仍然可以保存

现场失效并不自动抹去原任务。一个 Run 可能已经查到了材料，随后还需要保存原书笔记或把回答写回原聊天。只要用户和原任务的归属仍然有效，这些私人结果有明确的去处。

`RunScope::private_user` 根据原书、原目录和原聊天形成私人操作上下文。需要读取或修改实时阅读现场的操作，则另行检查现场。这样，原书笔记的保存与新现场的导航可以产生不同结果。

项目的 [Agent 运行测试](../../../crates/server/src/agent_run_tests.rs)包含一个明确的归属用例：`mu1c_old_run_cannot_touch_replaced_workspace_but_saves_original_note_and_answer`。它在模型等待期间从内部替换现场，再让旧 Run 尝试读取现场、导航、保存笔记和高亮。用例要求旧现场动作被拒绝，新 Reader 保持原状态；原书的笔记与高亮仍保存，回答进入原聊天，新的现场消息不混入旧回答。

这个用例把状态分层的意义表达得很直接：需要知道某个操作正在修改什么，再决定它依赖用户归属、现场有效性，还是两者都需要。一次运行的所有结果未必拥有完全相同的失效条件。

第 9 章会沿实际请求进一步追踪这些入口，第 16 和第 19 章则分别讨论会话提交与网络准入。理解本章之后，可以先抓住一条主线：运行携带原归属，操作进入权威状态，交付回到原任务。

## 当前边界

本地现场的 `publication` 可以为空；网络发布路径才具有显式的不可变发布对象。阅读源码时需要保留这个入口差异。

上面的现场替换测试直接调用内部路径，以验证状态归属合同。测试中的注释明确保留公开 Host 的切换与忙碌边界，因此这个用例不表示所有界面都允许在活跃 Run 中切换书籍。本文对测试的使用是源码对照，本批未重新执行产品测试。

搬迁保持身份、内容修订产生新基座是当前版本约定；自动完成新版成果复用、笔记投影与学习状态衔接，仍要结合 ADR-0146 中尚未完成的阶段理解。当前已发布材料的身份与运行绑定机制，不能代替完整的跨版本迁移流程。

## 用项目机制回答面试问题

**为什么已经有 book_id，还需要 publication_id？**

`book_id` 表达内容基座，同一内容可以继续补齐阅读成果。发布身份进一步固定某次可消费的成果集合，使运行能说明当时使用了什么。正文改版则涉及新的内容身份和旧记录的来源归属，需要按版本流程处理。

**同一用户开两个窗口，应该共享什么？**

可以共享用户的私人数据归属和公共材料引用，各现场分别持有 Reader、选中的聊天与窗口状态。这样窗口能够独立翻页，笔记仍属于同一用户。要进一步讨论并发写入时，再进入用户状态的串行入口和持久化机制。

**已经固定了 RunScope，为什么还要检查 generation？**

固定归属保存的是运行开始时的事实，后续现场仍然可能重绑。代际让旧任务识别这种变化，避免把原任务的阅读动作应用到新现场。它与用户检查配合，使私人记录和现场操作按各自条件处理。

**生成 TypeScript 类型后，跨语言一致性是否就解决了？**

生成类型能约束字段形状，字段单位和行为还需要共同约定。项目中的文本范围使用 UTF-16 下标；Rust 读取时也按 UTF-16 切片，才能让中文原文与构建侧的位置对应。这是一个可以从数据定义追踪到实际返回值的例子。

**关闭窗口后，整本书和聊天都应该立即销毁吗？**

先分别看生命周期。聊天是用户的持久数据；窗口现场可以被回收；书籍是共享材料，缓存或尚未结束的运行可能仍持有它。销毁决策应以各自所有者和实际引用为依据，不能把窗口生命周期套到所有数据上。

到这里，项目的工作时机、材料身份和状态归属已经连接起来。[第 4 章](04-原文定位与LID.md)将进入位置本身：一份原始材料怎样被切分，LID 和范围怎样产生，又怎样保持可读回的原文对应关系。
