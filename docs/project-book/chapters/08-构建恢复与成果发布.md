# 第 8 章 构建恢复与成果发布

沿着上一章的三个输入片继续思考。假设前两个片的候选已经被接受，第三个片正在执行时，构建进程中断了。重新打开项目后，用户希望继续完成这本书：已做好的工作应当保留，未完成的工作需要接续，阅读侧最终应当看到一份完整、可解释的成果。

这是一个教学场景。它把恢复问题分成了三个判断：哪些计算仍然有效，哪些执行已经失去所有者，以及哪些结果已经正式发布。三个判断使用的证据不同。一个成果文件可以仍然有效，而写出它的旧执行器已经结束；一组任务可以全部完成，而公开文件还没有组装；某阶段可以已经关闭，而构建计划仍有后续阶段。

本章沿这条链路解释恢复与发布。到章末，应当能够说明：为什么搬一个目录可以保留成果，却不能继续使用旧租约；为什么同一个候选可以重放提交，却不能换一份内容冒充原提交；为什么阶段收口成功后还要重新规划；以及工作区中的公开文件怎样进入网络阅读服务的一次不可变发布。

## 恢复先要确定继续处理哪份材料

构建工作区不仅保存生成结果，也保存生成结果所依据的材料。技术书的工作区位于 `.understand-book/<book_id>`，规范正文、位置树、来源清单和必要附件共同形成继续构建的基础。

当前 [technicalLearningTargetFromWorkspace](../../../packages/core/src/build-orchestrator.ts) 会读取工作区内部的 `source.txt`、`base.json`、`source_manifest.json` 和 `profile_metadata.json`，核对材料与 profile 的归属。Markdown 续建使用内部正文。EPUB 若有内部包快照，则从来源清单的相对 `snapshot_path` 或 `source.epub` 读取，并核对包中的规范正文与 `source.txt` 一致。

这样，用户在工作区外编辑、删除或移动最初导入的文件，不会悄悄改变这次续建的输入。外部原文件路径保留来源记录，实际续建消费已经导入的快照。

EPUB 还有一个容易忽略的细节：规范正文未必保留 Markdown 标题标记。若旧工作区缺少包快照，[loadBookSource](../../../packages/core/src/book-source.ts) 会结合已有 `base.json.lid_nodes` 恢复结构，而不是把 `source.txt` 当作一份新 Markdown 重新切分。否则文字相同，位置树却可能变化，前面章节建立的来源关系就无法继续沿用。

工作区内的几类材料各自回答不同问题：

| 材料 | 恢复时回答的问题 |
| --- | --- |
| 规范正文、来源清单、位置树和附件 | 正在处理哪份材料，引用怎样定位？ |
| 冻结的工作描述与策略代次 | 当时要求模型完成什么，依据什么规则？ |
| 已接受的语义成果信封 | 哪项计算产生了什么结果，是否仍适用于当前任务？ |
| 租约、输入观察、尝试与提交回执 | 哪次执行持有任务，走到了哪一步？ |
| 阶段公开文件、质量报告与关闭结果 | 哪些内容已经组装，当前阶段是否具备完成条件？ |

恢复由这些持久材料重新计算下一步。最后一条进度消息可以帮助理解现场，但它本身不能代替成果和状态。

## 文件存在之后，还要判断成果是否有效

第 7 章的候选写入器会生成语义成果信封。当前 [SemanticArtifactEnvelopeV3](../../../packages/core/src/semantic-artifact.ts) 除了 payload，还保存目标、阶段、工作单元、输入身份、策略代次、语义合同、成果摘要和生成来源。

这些字段不是另一份业务正文。它们使系统能够回答：“眼前这个结果，是否就是当前这一项工作可以使用的结果？”

[semanticArtifactMatches](../../../packages/core/src/semantic-artifact.ts) 首先比较书籍、来源、profile、阶段、工作单元和输入，再核对 payload 与保存的成果摘要。对于 V3 信封，还要匹配策略代次和语义合同。合同包括 profile 版本、阶段策略、路由版本、提示、schema 和质量档位。

目录地址在这里有一个特殊地位。[sameBuildContent](../../../packages/core/src/semantic-artifact.ts) 的实现为：

```typescript
  return left.version === right.version
    && left.book_id === right.book_id
    && left.profile_id === right.profile_id
    && left.input_fingerprint === right.input_fingerprint;
```

这段比较没有工作区绝对路径。完成的计算属于这份书籍内容；文件搬到另一处，并不会自动改变计算含义。稍后会看到，执行中的租约仍然核对具体位置，两者采用不同的归属规则。

本书使用现有确定性 Pass1 夹具生成一份已接受的 V3 成果，再逐项改变匹配条件，实际得到：

| 期待条件的变化 | 当前成果直接匹配 |
| --- | --- |
| 输入与策略均保持不变 | 是 |
| 只改变 workspace_dir | 是 |
| 改变 book_id | 否 |
| 改变 input_hash | 否 |
| 改变 schema_version | 否 |
| 改变 policy_generation_id | 否 |

这个算例只改变匹配函数的期待条件，用来隔离“成果属于谁”的判断；它没有实际搬动整个工作区。完整搬迁续建的项目记录将在后面介绍。

这里也能看出输入身份为什么重要。模型的结果受它看到的全部任务输入影响，包括最终没有引用的上下文。如果只比较输出中的来源 LID，就可能把输入已经变化的旧判断继续当成当前判断。

## 策略升级需要说明旧结果怎样进入新任务

当提示、schema、路由或任务划分变化时，旧文件仍然是历史成果，但它未必直接满足当前合同。项目用策略代次保存这一变化，并通过迁移回执表达采用或重建的决定。

[ADR-0100](../../adr/0100-budget-routable-model-work-units-and-truthful-build-recovery.md)记录了 Pass1 路由升级时的取舍。旧窗口需要进入新的预算与切片机制：无条件重做全书会丢弃相同输入上的有效计算；直接把旧成果标成新鲜，又会跳过新的路由约束。

当前 [recordAutomaticBuildPolicyMigration](../../../packages/core/src/automatic-build-policy-generation.ts) 中，旧 V2 单元的迁移先核对当前工作描述和预算依据，再读取旧成果及其完整渲染输入。已有活动租约时先返回阻塞；旧输入无法核实时，也不能宣布精确采用。书籍来源、单元类型、语义策略或渲染输入改变，会进入相应的重建决定。

只有满足这条迁移路径的采用条件，才记录 `adopt_exact`：新旧任务的完整渲染输入逐字相同，提示、schema、质量等语义要求兼容，而且新任务已经通过当前路由约束。迁移随后通过明确回执把来源成果接到当前代次，旧成果及其来源关系继续保留。

这是对“直接匹配失败”的进一步处理。上一节改变代次得到“否”，说明旧信封不能直接冒充新信封；经过当前实现支持的迁移判定后，仍可能采用它。对较早 V3 成果，项目还提供 [recordAutomaticBuildPriorGenerationAdoption](../../../packages/core/src/automatic-build-policy-generation.ts)，按已有成果与当前合同判定是否能够明确采用。

普通续建、策略升级和内容改版由此有了不同入口。前两者已有相应实现；正文修订后的跨版本段落对应与大范围增量复用，还需要后文所述的新版机制。

## 一次中断不一定是一次语义失败

上一章已经把输入交付、领取和生成分开。恢复时还需要看中断发生在哪一步。

[inspectAutomaticBuildTaskClaim](../../../packages/core/src/automatic-build-lease.ts) 先寻找当前目标和任务范围内仍有效的租约。任务已有有效所有者时，调用方得到 `already_leased`；没有可继续使用的活动租约，才通过 [nextAutomaticBuildExecutionIdentity](../../../packages/core/src/automatic-build-task-store.ts) 计算下一次执行身份。

这个身份包含 `semantic_attempt` 和 `lease_epoch`。前者表示候选生成的语义尝试，后者表示该尝试内的执行接管。下面是当前分支所表达的区别：

| 中断或返回的状态 | 恢复依据与下一步 |
| --- | --- |
| 四工具协议尚在交付输入 | 尚未创建语义尝试；继续核对当前交接并完成输入交付 |
| 已开始执行，租约仍有效 | 等待原执行，不直接另领同一任务 |
| 没有语义失败结果，旧租约已过期 | 保持语义尝试，增加租约代次，例如 `(1,1) → (1,2)` |
| 当前尝试已有候选失败结果，仍在重试额度内 | 下一次语义尝试增加，租约代次从 1 开始，例如 `(1,2) → (2,1)` |
| 候选已经 committed，但返回响应未被收到 | 按原提交身份重放，读取已有回执 |

接管同一语义尝试，仍可能需要重新调用模型。两个计数的目的，是区分模型候选失败与执行器失联，并据此采取不同恢复动作；它们不保证进程内的模型上下文能够原样复活。

提交重放也有明确条件。[submitAutomaticBuildCandidate](../../../packages/core/src/automatic-build-mailbox.ts) 在找到已有回执时，核对候选内容身份和尝试范围，随后返回原回执并补齐成功记录。相同提交可以恢复响应，内容不同的提交则发生冲突。

[执行器会话测试](../../../packages/core/test/automatic-build-executor-session.test.ts)覆盖了这个区别：同一个结构化候选再次提交，返回与第一次相同的结果；语义尝试仍为 1，提交修订记录增加到 2。换一份候选不能借用已经提交的身份。[租约测试](../../../packages/core/test/automatic-build-lease.test.ts)则覆盖过期后接管，保持语义尝试 1、进入租约代次 2。

## 重试停止时，系统需要给出可行动的原因

重试次数不能把所有失败都变成成功。无效字段可以纠正，暂时的 Provider 故障可能值得重试，执行器反复失联需要处理宿主，而合同本身不适用时要改变策略。

[automaticBuildRetryBoundaryRequiredRecovery](../../../packages/core/src/automatic-build-attempt-recovery.ts) 把这几种情况分开：暂时的 Provider 失败可进入 `authorize_transient_retry`，可纠正候选失败可进入 `authorize_candidate_retry`，其他 schema 或证据失败可能要求 `publish_new_policy`，剩余情况交给 `operator_fix`。输入交付和候选接收通道的失败不能直接创建语义重试耗尽边界。

需要在同一范围再开一个重试窗口时，恢复回执绑定原失败、尝试范围和具体决定请求。旧失败因此仍然可解释，而不是通过清空计数把它抹掉。

路由、迁移和阶段收口的预期阻塞使用另一类 [AutomaticBuildRecoveryEnvelopeV1](../../../packages/core/src/automatic-build-recovery.ts)。它携带阶段、稳定错误码、受影响单元、相关预算、是否可重试，以及允许的恢复动作。例如，发布回执不合法返回 `publication_receipt_invalid`，发布后的条件不成立返回 `stage_close_postcondition_failed`；两者都会指向 `inspect_publication`。

这使上层能够展示具体处理方向，并在条件改变后继续规划。结构化原因没有授权系统擅自降低质量、修改原文或扩展已确认计划；恢复仍沿原来的构建范围推进。

## 把已接受成果组装成一组公开文件

一个工作单元的 committed 回执，只证明这一项候选已经经过写入器接纳。阶段公开文件则可能聚合许多单元。例如，BookStructure 要把发现、章节选择、主题和关系等贡献组装成阅读侧可以消费的 `book_structure.json`。

阶段发布由 [publishAutomaticBuildArtifactSet](../../../packages/core/src/automatic-build-publication.ts) 处理一组预期文件。它先在临时目录写候选文件，运行调用方提供的候选检查，再逐个备份旧文件、替换正式文件，全部成功后写入 committed 发布回执。可捕获的替换异常会撤回已经替换的文件，并恢复相应备份。

发布回执列出文件相对路径、字节数和内容摘要，事务身份由阶段及这份有序清单确定。这里的摘要用于识别同一组预期字节，并决定能否直接返回已有回执，或者需要重新写出正式文件。

如果相同事务已有回执，发布器仍会检查当前正式文件是否匹配。匹配时可以直接重放结果；文件缺失或被改动时，会重新发布预期字节。这避免把“历史上成功过”当成“当前公开文件仍然正确”。

本书在独立临时目录中，用两份带新旧标记的 JSON 演示发布器。文件名采用 `base.json` 与 `profile_metadata.json`，内容只是教学标记，不承担正式 Pass1 schema 验证。实际结果如下：

| 操作 | 公开文件结果 | 发布结果 |
| --- | --- | --- |
| 替换第 1 个文件后注入异常 | 两份旧文件均保留 | 抛出本次注入的异常 |
| 去掉故障后重试 | 两份文件均为新内容 | committed，清单包含 2 个文件 |
| 原样再次发布 | 两份文件仍为新内容 | 返回同一事务身份 |
| 改动其中一个正式文件后再发布 | 被改动的文件恢复为预期新内容 | 仍为同一事务身份 |

这个例子展示的是发布字节、异常回滚与重放。正式阶段还要证明这些字节确实来自当前有效成果，这由收口过程连接起来。

## 收口把发布前后的证据连接起来

[closeAutomaticBuildStage](../../../packages/core/src/automatic-build-close.ts) 先构建阶段快照，收集当前质量报告。报告通过后，保存报告并运行阶段组装脚本。脚本需要返回可解析的阶段批次结果，其中引用已经写入的发布回执。

接下来，收口函数核对回执身份和本阶段允许的公开路径，再读取正式文件，比较字节数与内容摘要。随后它重新计算阶段快照、质量、策略与覆盖情况。当前源码中的关键判断为：

```typescript
  if (!postStage.closed
    || postQuality.gate_status !== "passed"
    || postQuality.digest !== preQuality.digest
    || canonicalBuildJson(postEvidence.policy_contracts) !== canonicalBuildJson(preEvidence.policy_contracts)
    || postEvidence.coverage_digest !== preEvidence.coverage_digest
    || !freshness?.fresh
    || !freshness.freshness_digest) {
    return closeRecovery(
      input.target,
      input.stage,
      "post_close",
      "stage_close_postcondition_failed",
    );
  }
```

这段比较连接了两侧的事实：发布前获准组装的是哪组贡献，发布后是否仍然是同一组有效贡献，以及公开阶段是否已经关闭。它能发现发布过程中成果变化、公开文件缺失或质量状态漂移等问题。

质量报告也包含几类不同证据。[collectAutomaticBuildStageQuality](../../../packages/core/src/automatic-build-quality.ts) 读取当前任务成果，再由相应评估函数检查工作单元计数、预算依据、原文覆盖、归并关系、成果完整性和既有质量下限。原文范围无缺口、无核心重叠，与候选内容质量分别记录。

新鲜度不是“文件最近写过”。[inspectAutomaticBuildStageFreshness](../../../packages/core/src/build-orchestrator.ts) 使用已经重算的阶段 `closed` 状态，结合当前目标和策略形成新鲜度身份。各阶段的关闭条件由各自实现提供。例如，BookStructure 会把公开文件与当前组装结果逐字比较，并寻找对应发布回执；通用收口则额外完成上述发布前后核对。

这还有一个与第 6 章相关的细节：BookStructure 从 `ready` 变成 `published` 是发布状态变化。质量报告把该观察放在质量摘要之外，避免仅仅因为发布成功，就让发布前后的同一份质量证据变成不同身份。

本书还调用当前收口函数，使用现有 512-token 合成段落夹具与固定候选准备 Pass1，实际得到三种结果：

| 阶段脚本及发布后的状态 | 收口结果 | 后续方向 |
| --- | --- | --- |
| 返回合法发布结果，正式文件与当前成果匹配 | closed | replan |
| 只返回“wrote base.json”一类普通日志 | publication_receipt_invalid | inspect_publication |
| 已有回执，但返回前删除正式 base.json | stage_close_postcondition_failed | inspect_publication |

第一种成功结果保存质量、发布和后置条件的身份，`next` 明确为 `replan`。本次重算后的下一动作实际是 `extract / profile_sidecar`，并没有宣布整本书完成。

## 当前计划完成，是另一层判断

为什么收口只返回重新规划？因为当前阶段无法替其他阶段证明完成，也不知道已确认计划是否还要求私人产物。

[nextAutomaticBuildAction](../../../packages/core/src/build-orchestrator.ts) 沿阶段顺序读取当前快照：已关闭的阶段跳过；仍需准备的阶段返回相应边界；有待办任务时安排抽取；没有待办但尚未关闭时安排收口。所有纳入此次判断的阶段都完成后，才得到内部 `done`。

有明确 BuildPlan 时，执行范围还受到已确认的阶段依赖闭包限制。计划声明复用的公开成果也要与当前新鲜度相符，发生漂移则进入计划边界，不能继续沿用旧的完成判断。

[automaticBuildStep](../../../skills/build/automatic-build-driver.ts) 收到阶段收口的 `next: replan` 后继续读取当前状态。内部公共阶段完成后，它还处理计划要求的私人产物；只有这些工作也结束，才对 Harness 返回 `DONE`。

因此，这里的 DONE 表示本次已确认计划完成。不同阅读目标可能要求不同成果集合，不应把每一次 DONE 都解释为“项目能生成的全部能力都已经齐备”。

## 搬迁保留成果，重新建立执行归属

现在可以回到开篇的恢复场景。若用户把完整工作区复制到另一处，前两个片的已接受结果仍属于同一书籍、来源与策略，可以参与新位置的规划。第三个片的旧租约却不能自动成为新位置的执行权。

当前 [automatic-build-task-store.ts](../../../packages/core/src/automatic-build-task-store.ts) 读取历史尝试时，会识别执行记录的原位置。复制来的记录仍保留物理序号，避免覆盖历史目录，但不消耗新位置的租约或语义重试额度。[readAutomaticBuildLease](../../../packages/core/src/automatic-build-lease.ts) 则核对包含工作区位置的完整目标，旧 token 和复制后的旧租约都不能直接代表新运行。

冻结任务可以经 [relocateGenerationTask](../../../packages/core/src/semantic-artifact.ts) 在内存中投影到当前地址。原成果信封保留历史归属，当前写入器仍按当前目标接纳新结果。

关闭结果也分别保存。发布事务由预期字节确定，搬迁后相同字节可以保留事务身份；关闭时的新鲜度身份包含当前构建位置，因此记录位于：

```text
.build/automatic-build/v2/close/<stage>/<transaction_id>/<freshness_digest>.json
```

这样，同一组成果在新位置重新核对，不会覆盖旧位置的关闭记录。

[2026-10-01 的 U1—U2 验证记录](../../performance/workspace-u1-u2-20261001.md)提供了完整链路的已有证据：两章材料完成一项 Pass1、领取另一项后复制工作区，新位置只调度未完成项，原位置的旧提交被拒绝。另一个用例使用 29 章 BookStructure 生产夹具，搬迁后没有待抽取任务；删除新目录的公开结构文件后，经正常 close 入口从已完成成果重发 82,514 字节，结果与原输出完全一致。

这说明公开文件丢失与模型成果失效是两种不同故障。前者在已有有效贡献时可以重新组装，未必需要再次付出模型生成成本。

## 工作区发布怎样进入不可变的阅读版本

阶段发布会更新构建工作区中的公开文件。网络阅读服务还需要固定一组可供多个用户、现场和运行共同使用的材料，对应第 3 章的 `PublishedBookRef`。

[PublishedLibrary::publish](../../../crates/server/src/published_library.rs) 是这层入口。它将所需正文、成果及附件复制到暂存目录，加载 Book，读取现有构建 readiness。只有 readiness 的路由允许进入 Reader，才继续建立发布对象。

这里的阅读就绪与完整教学就绪分别表达。当前 [build_workbench_snapshot](../../../crates/server/src/lib.rs) 对论文材料检查可信来源与基础成果，已有技术书走对应入口；发布清单另外保存 `teaching_readiness`。材料可以进入阅读，不能据此推导所有教学能力都已就绪。

每次发布创建新的 `publication_id`，将 `book_id`、来源、文件清单、能力、成果版本及 readiness 写入 `publication.json`。随后，代码把暂存目录移到正式位置，封为只读，最后在数据库事务中登记发布并更新默认发布。

文件就位与登记之间的顺序使阅读入口有明确边界：数据库登记成功之后，库才暴露这个发布。登记前中断可能留下未登记目录，但它不会成为一个可读取的半成品条目。[网络发布测试](../../../crates/server/src/tests/mu3_tests.rs)包含登记失败不产生默认发布和已登记条目的用例。

```mermaid
flowchart LR
    A[已接受的工作单元成果] --> B[组装并发布阶段文件]
    B --> C[重算阶段状态与计划]
    B --> D[工作区阅读能力与就绪状态]
    D --> E[复制并验证阅读发布]
    E --> F[封存文件并登记 publication_id]
    F --> G[阅读现场与 Run 固定该发布]
```

这两层发布使用不同身份。阶段发布的事务身份对应同一组预期字节，所以重复发布可以返回同一事务；网络阅读发布为一次固定快照分配新的 publication_id。默认发布切换后，原现场或运行已经持有的发布引用仍然指向原版本，历史回答也保留当时的归属。

同一个 book_id 可以在原文不变时获得更完整的能力，再产生一次发布。规范正文、PDF 或来源图片改变时，当前网络发布器要求使用新的 book_id，并返回 `BOOK_CONTENT_CHANGED` 阻止覆盖原内容身份。

[ADR-0146](../../adr/0146-portable-build-workspaces-and-incremental-book-updates.md)进一步规划了正文改版后的增量更新：建立新旧段落对应，重算新版任务的完整输入，对能够重绑且输入等价的结果做复用，并让历史引用继续保留原始归属。该方案当前完成 U1—U2 搬迁续建，U3—U11 尚待实施。已有不可变发布机制，为版本并存提供基础；它还不能代替完整的新版构建、跨版引用与私人学习记录衔接。

## 已知边界与验证范围

本章依据 2026-10-07 的工作区，重点解释公共构建中的语义成果、通用阶段发布与收口。教学阶段有专用关闭路径，paper reading guide 使用验证路径，它们的结果也回到重新规划；具体教学规则留到后续章节。

当前阶段发布器逐文件执行替换，其回滚依赖捕获异常。进程被强制终止时，catch 不会继续执行，工作区中的正式文件可能停在中间状态。本章实际验证了可捕获异常的回滚与后置条件拒绝，没有验证强制终止后的完整自动修复；这条实现不能当作文件系统层面的多文件原子事务。网络发布则通过封存后登记，控制阅读库何时暴露新版本。

U1—U2 的搬迁仍要求保留工作区结构与 book_id，活动 invocation 和执行器不会迁移归属。旧 EPUB 若丢失原包，而旧任务绑定的恰是包字节身份，不能用正文身份代替，需要恢复原包或重建。

本次确定性重放使用固定候选与现有夹具，验证成果匹配、发布重放和阶段收口；没有评价真实模型的语义质量。已有租约、提交、收口及网络发布用例为源码阅读，没有运行完整产品测试或付费模型，也没有重新执行 U1—U2 历史实验。

**构建中断后，你怎样避免把已完成工作全部重跑？**

先从导入快照和当前策略重建任务，再检查已有成果是否与当前输入、任务和合同匹配。有效贡献继续参与组装，未完成任务重新调度；公开文件丢失时先判断能否从有效成果重新发布。追问若变成“正文已经改了”，就需要进入版本对应与完整输入比较，不能直接套用搬迁复用。

**为什么租约过期不直接增加模型失败次数？**

租约过期说明原执行不再有效，还不能证明它生成了错误候选。项目用语义尝试记录候选失败，用租约代次记录接管。追问若执行器一直失联，仍有独立的接管上限与恢复边界，不能无限循环。

**如何解释重复提交不会多写一次结果？**

对已经形成 committed 回执的同一候选，提交路径核对候选身份与尝试范围并返回原回执。换一份候选会冲突。这个保证针对明确的提交身份与已有回执；不能把它扩大为任意进程中断点上的所有副作用都只发生一次。

**为什么阶段发布成功后还要做后置检查？**

阶段脚本只负责它的组装与写入过程。收口还要证明实际文件对应回执、当前任务和质量没有漂移，而且阶段状态已经关闭。成功后重新规划，继续执行后续阶段。追问若“脚本退出码是 0”，需要继续寻找结构化发布结果，而不是从退出码推断完整成果。

**为什么既有 book_id，又有 publication_id？**

book_id 固定内容基座，publication_id 固定该基座一次可消费的成果快照。同一原文可以逐步补齐能力，旧运行继续持有旧发布。正文或来源附件改版则需要新内容身份；未来跨版复用也必须保留历史引用原来的归属。
