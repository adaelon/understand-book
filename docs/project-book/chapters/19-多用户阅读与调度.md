# 第 19 章 多用户阅读与调度

第 18 章中，读者甲正在等待学习率演示的修订。他在电脑上提交问题，又在手机上打开同一本书，查看另一个小节。与此同时，读者乙也在服务器上阅读这份材料，并请 Agent 保存一条自己的笔记。

现在，“模型等待时还能滚动”只是起点。我们还要回答：甲的两个窗口是否共享当前位置？乙能否通过甲的聊天 ID 读到回答？甲连续提交三个任务后，乙要等多久？服务器在返回“已接纳”之后重启，又该继续哪些任务？

这些问题围绕同一个中心展开：**共享材料和模型资源时，怎样保持私人数据与阅读现场独立？** 本章沿一次多人请求，从身份进入私人权威状态，再进入窗口、持久接单和两层调度。第 3 章建立的归属概念、第 16 章的日志合同，以及上一章的锁外执行，在这里组成一个实际服务。

## 19.1 服务、用户、现场与 Run 的分层

### 第二个窗口不该生成第二份私人真相

先看一个直接后果。若手机和电脑各自从甲的目录加载一份 Memory，模型结束后分别整体写回，后提交的一份可能覆盖另一窗口刚刚保存的笔记。给两个副本各加一把锁没有帮助：它们锁住的是不同对象。

当前 [UserRegistry](../../../crates/server/src/user_registry.rs) 以 user_id 为键保存 UserHandle，后者是 Arc<Mutex<UserRuntime>>。get 先核对账号的存储路径，未加载时才构造 UserRuntime，随后返回同一句柄的克隆。因此，甲的两个请求共享一个私人权威实例；乙取得另一个实例。模型只持有句柄，需要具体操作时才借用它，不会得到可在结束时整体覆盖回去的私人副本。

[UserRuntime](../../../crates/server/src/user_runtime.rs) 持有 MemoryStore、AgentHistory、SessionStore、画像上下文缓存及私人产物根；LearningStore 由同一用户的 MemoryStore 解析。其持久路径来自 [UserStoragePaths::for_service](../../../crates/server/src/user_storage_paths.rs)：甲的记忆、学习数据库和聊天日志位于甲的用户目录，乙有自己的目录。路径由可信宿主根据身份构造，不由模型或浏览器选择。

现场采用另一层注册表。[WorkspaceRegistry](../../../crates/server/src/workspace_registry.rs) 以 `(owner, workspace_id)` 为键管理 ResidentWorkspace。里面的 ReaderWorkspace 持有材料绑定、Reader、选中聊天、消息投影和 generation；外层另有已提交 revision、主页面 attachment、演示附属视图和现场检查点。

于是，开头的场景可以这样分解：

| 层次 | 本例中的对象 | 共享与独立的具体含义 |
| --- | --- | --- |
| 服务 | 发布书库、身份与授权、准入、资源限制 | 甲乙共享材料加载和有限的模型、制作资源 |
| 用户 | 甲的 UserRuntime、乙的 UserRuntime | 同一用户共享笔记、聊天、学习与画像；两个用户分别拥有 |
| 现场 | 甲的电脑窗口、甲的手机窗口、乙的窗口 | 分别保存 Reader、材料绑定、选中聊天与演示现场 |
| Run | 电脑窗口接纳的那次演示修订 | 固定甲、原聊天、原发布和提问输入；按需访问当前私人状态 |

“服务层”在这里是职责层次，不能机械等同于名为 ServiceState 的一个结构体。当前网络 Host 将 AuthService、UserRegistry、PublishedLibrary、WorkspaceRegistry、RunAdmissions 和 Resources 组合在 [Authorization](../../../crates/server/src/authorization.rs) 中；本地 AppState 的 ServiceState 仍主要保存宿主能力和适配器配置。

一次网络请求也不需要先借到全局“当前书”。[multi_user_host::dispatch](../../../crates/server/src/multi_user_host.rs) 取得 AuthorizedContext 后，根据 URL 中的 workspace_id 和可信 owner 找到现场。甲在手机上切书，只改变手机现场；乙的切书也不替换甲正在使用的 Book。

### 四种“会话”必须分开

登录会话证明这条连接代表谁；聊天会话保存持续对话；TutorSession 属于这个人的教学过程；ReaderWorkspace 保存一个阅读窗口的现场。它们有不同生命周期。

例如，甲的两个窗口可以选择同一个聊天。两个 Reader 仍各自独立，但该聊天的写入顺序只有一条，后文的准入会阻止同时出现两个待执行回答。另一方面，甲从手机关闭 Tutor，改变的是甲的用户级控制；电脑中的旧 Run 不能把这个改变当作与自己无关的局部窗口偏好。

本轮执行的 [多窗口与 Tutor 用例](../../../crates/server/src/tests/mu5_tests.rs) 分别验证了这两层关系：一个窗口导航后，另一个窗口和乙的 Reader 不变；重复取得甲的 UserHandle 指向同一对象。Tutor 用例从另一现场关闭控制后，旧端口不能继续教学；重新开启也不使旧控制绑定复活，乙的控制 revision 仍保持独立。

### 原现场还在，也不代表旧动作可以覆盖新操作

上一章的 RunScope 检查原 owner、chat、turn，以及 workspace generation。网络端口还增加一个更细的条件：effect_revision。

假设 Agent 已把甲的电脑 Reader 移到第 1.5 节，随后等待模型；甲亲手跳到第 1.20 节。材料和聊天都没有变，generation 仍相同。旧 Run 此时读取实时 Reader，可以看见第 1.20 节；但若它根据原计划再跳回第 1.1 节，就会覆盖刚刚发生的用户选择。

[NetworkRunPort::check_effect_revision](../../../crates/server/src/workspace_registry.rs) 明确阻止这一覆盖：

```rust
if scene.revision != self.effect_revision {
    return Err(error(
        "READER_USER_ACTION_SUPERSEDED",
        "conflict",
        "A newer user action takes priority over this Run effect",
    ));
}
```

运行准备时冻结 effect_revision；本 Run 成功提交自己的 Reader 动作后，才把它推进到新 revision。read_live_reader 不要求这个值相等，所以“看见最新现场”和“有资格修改现场”可以分开。本轮上述导航顺序已实际通过用例，迟到动作返回 READER_USER_ACTION_SUPERSEDED，读者的新位置保留。

这项规则表达的是用户操作优先。它不会撤销原书的私人笔记，也不更换原聊天的回答归属。私人写入、实时读取、Reader 动作和最终回答各有接纳条件，不能用一个全局 busy 或一把大锁替代。

## 19.2 身份、对象授权与材料发布

### 先确定是谁，再解释他请求的对象

甲乙都可能提交 `session_id`、`turn_id` 或 `workspace_id`。这些字段负责指认对象，不负责证明所有权。如果宿主把客户端传来的 user_id 当成可信归属，后面的目录隔离便失去了依据。

当前 [auth::Principal](../../../crates/server/src/auth.rs) 的字段是私有的，只能由认证模块构造。多人 start 入口要求后端绑定 loopback，并要求配置 HTTPS origin；实际 HTTPS 由前置代理承担。账号由管理员提供，登录入口校验密码并建立可撤销的服务器端会话。Cookie 带 Secure、HttpOnly、SameSite=Lax，默认有效期为十二小时；这是当前代码的设置，部署如何组合留给下一章。

进入普通业务时，dispatch 的关键顺序是：

```rust
let token = token.ok_or_else(auth::unauthenticated)?;
let principal = access.auth.authenticate(token, now)?;
if !matches!(method, "GET" | "HEAD")
    && headers.get("X-CSRF-Token") != Some(auth::csrf(token).as_str())
{
    return Err(crate::user_storage_paths::error(
        "CSRF_REJECTED",
        "permission",
        "CSRF token is required",
    ));
}
```

在这段代码之前已经检查 Host 和 Origin，之后还会拒绝查询或正文中的 user_id、owner_user_id、dir、book_dir、service_root 等字段，再通过 capability 表选择业务能力。普通阅读请求因此不能通过换一个路径参数进入另一个用户根，也不能借旧接口名字打开服务器目录或修改 Provider。

认证之后仍要检查具体对象。[AuthorizedContext::history](../../../crates/server/src/authorization.rs) 只从当前 UserRuntime 的聊天中寻找 ID；Workspace 查询把 owner_user_id 和 workspace_id 一起放入条件；Run 查询也使用 owner 和 turn 的组合。私人演示还要回到原聊天、原 turn，再加载其发布材料。身份正确不意味着对象自动可读。

本轮通过当前 [MU8 用例](../../../crates/server/src/tests/mu8_tests.rs) 验证：甲保存的笔记不会出现在乙的 recall 中；甲自己的另一份材料也不能借原 mem_id 删除这条记录。画像和来源解析同样保留用户与发布绑定。这里验证的是当前业务入口对这些对象的归属处理。

### 观察连接不能永久沿用打开时的资格

SSE 会存活很久。若只在建立连接时授权，之后退出登录或撤销材料访问，已经打开的连接仍可能继续收到内容。

[AuthorizedObservation](../../../crates/server/src/authorization.rs) 保存确切 Principal、原发布引用、运行描述和观察许可。allows 每次检查服务是否停止、描述是否匹配、该登录会话是否仍有效，以及原材料是否仍授权。[serve_checked](../../../crates/server/src/agent_stream.rs) 在取事件前后调用它，再写出事件。

这里有两个不同结果。退出登录使该登录会话失效，观察者不再有资格继续接收；已接纳 Run 的 owner 却仍是原用户，任务不因此自动取消。禁用账号或撤销原发布权限，则会影响运行在领取、模型调用和状态操作边界的材料授权检查。显式取消仍走原 turn 的取消入口。

本轮通过的观察许可用例直接确认：乙拿不到甲的观察许可；甲用满自己的四个许可后再申请得到 OBSERVATION_CAPACITY，释放一个后可再次申请；退出甲的会话使已有许可失效，乙仍可读自己的聊天，原 queued 回合并未被取消。连接传输和许可失效是两个验证层次，具体未覆盖部分集中列在章末。

### 共享的是确切发布，不是“当前最新目录”

身份分开以后，甲乙仍需要共享同一本书。这里可共享的是纯材料，不是 Reader 或私人派生状态。

[PublishedBookRef](../../../crates/server/src/published_library.rs) 由 book_id 和 publication_id 组成。publish 把允许的依赖复制到暂存目录，沿用已有 readiness 检查，生成发布清单；文件移动到最终目录并封存之后，SQLite 事务才登记发布和默认指向。文件先存在、登记尚未成功的目录，不会因此成为读者可打开的半份发布。

同一 book_id 可以有不同能力完备程度的发布，但源码会直接比较原文、原 PDF 和 assets 附件内容，内容变化要求新 book_id。材料默认指向的更新影响后续按默认打开的选择，不会替换已固定 publication_id 的现场、Run 或历史来源。

这与第 17 章的演示 revision 有相似的理由：原问题必须能回到当时的内容。区别在于，publication_id 指向管理员登记的公共阅读材料；演示版本属于某位读者在原聊天中交付的私人产物。

书库访问也不是“加载过一次就永远允许”。load 的开头先做以下检查：

```rust
self.authorize(owner, reference)?; // also on a cache hit
let (directory, manifest) = self.record(reference)?;
if !directory.is_dir() {
    return Err(unavailable());
}
```

该摘录来自 [PublishedLibrary::load](../../../crates/server/src/published_library.rs)。Book 可以从共享缓存命中，授权仍按当前用户检查。图片、PDF 和正文都带确切发布路径进入能力表；HTTP 分支在处理 HEAD、Range 或条件头之前先核对材料资格。当前后端对 Range 可以返回完整的 200 表示，不把它写成后端已经实现分段读取。

本轮发布用例将默认指向改为第二次发布，并移走原现场。旧 Run 仍读取第一份 Book，回答也保留第一份引用；只有旧 Run 释放之后，一本书容量的缓存才能加载新发布。材料版本和资源寿命在这里发生了直接联系。

## 19.3 SQLite 接单和运行准入

### 202 要承诺什么

甲点击发送后，网络可能在收到响应之前断开。如果“接受”只是把任务推入一个内存队列，服务随后重启，甲既找不到回答，也无法确定是否应重发。若简单重发又启动一次模型，已经发生的笔记或教学动作还可能重复。

当前 [RunAdmissions](../../../crates/server/src/run_admission.rs) 把这个问题分成持久接单和业务日志两部分。[control_schema.sql](../../../crates/server/src/control_schema.sql) 中，run_admissions 保存 owner、client_request_id、turn、chat、workspace、原 generation、发布、调度状态及取消、未保存等标志。主键是 `(owner_user_id, client_request_id)`，同一用户的 turn 也唯一。

问题正文、规范化请求、提问快照、Goal、教学准备和模型绑定放在私人 FrozenTurn 中；当前持久聊天通过 JSONL 保存，冻结历史使用 HistoryPosition 指向已经提交的位置。执行时由 frozen_input 读取该位置的原始消息，再交给既有 Runtime 处理上下文，而不是拿“此刻最新聊天”重新组装。

这两处存储各有真相：SQLite 回答“是否接单、能否领取、占着谁的位置”，私人日志回答“原问题是什么、输入是什么、最终交付了什么”。SQLite 没有再保存一份替代聊天日志的答案。

### 从 preparing 到 queued，需要跨过哪些提交

admit 首先检查请求键、Provider、现场 stamp、所选聊天、可选的 expected_chat_head 和用户输入。它还要确认同一聊天没有 pending 回合。随后，在准入状态锁和 SQLite 事务内判断是否正在删除、是否已有同聊天或同现场的未结任务，以及总容量和用户容量是否足够。

准入事务通过后，把已经分配的稳定 turn_id 连同 preparing 记录提交。后面的提交顺序如下：

| 阶段 | 写下的事实 | 这时能否向新请求返回已接纳 |
| --- | --- | --- |
| preparing | 请求键、原归属、turn 和容量占位 | 不能，私人输入可能尚不存在 |
| Pending Turn 已持久化 | 用户问题、FrozenTurn、冻结历史位置 | 不能，必要教学准备可能未完成 |
| preparation_complete | 原教学事件已按身份复用或写入，TurnPrepared 已提交并完成关联 | 尚需把接单转为 queued |
| queued | 准备完成且可进入调度 | 可以返回 202 和同一 turn_id |

其中 complete_preparation 对教学事件的处理是：

```rust
let mut learning = user.learning_store()?;
for event in &frozen.teaching.events {
    learning.append_teaching(event)?;
    self.point("teaching_receipt")?;
}
```

这段 [真实代码](../../../crates/server/src/run_admission.rs) 中的 point 是测试故障注入点；生产环境不在这里主动中断。关键在于 event 已经来自原 frozen.teaching。恢复时逐个复用原事件，不根据新的学习状态重新生成回答次数或教学绑定。

本轮教学准备用例在第一份回执后注入失败，再加入一条更晚的学习动作并关闭 Tutor。重开后，原回答 attempt 仍为 1，原控制绑定保持不变，TurnPrepared 只出现一次。这说明“把准备补完”与“按最新状态重新准备一次”有不同语义。

实际过程没有跨 SQLite、聊天 JSONL 和 learning.db 的共同事务。它依靠稳定 ID、明确阶段和恢复对账，把中途失败变成可辨认的状态。只有所有必要准备都到达 queued，新接单才能得到 202。

### 请求幂等比较的不只是文字

设甲用请求键 `ask-7` 提交问题。再次发送同用户、同键、同规范化内容，会返回原 turn；换一个 key，即使文字相同，也是一项新请求，需要重新经过聊天和现场占位。

[normalize](../../../crates/server/src/run_admission.rs) 保留 workspace、message、显示文字、session、generation、expected_revision、attachment、确切发布、聊天头、引文、演示追问、教学和 Goal 等字段。因此，重试期间只把 expected_revision 换成最新值，也已经改变了原请求。恢复连接时，客户端应保留原接单内容，或通过 client_request_id 查询原 turn；“再发送相同的一句话”不是完整的重试合同。

repeat 在 preparing 时返回 ADMISSION_PREPARING；输入已经冻结后，逐字段比较规范化值，不同则返回 REQUEST_KEY_CONFLICT；已关闭的键返回 REQUEST_KEY_CLOSED。比较直接使用已保存字段，没有另造请求摘要。

本轮同键用例修改问题、锚点、Goal 动作、generation、教学引用和引文，均得到冲突；原请求重复提交只产生一个问题和一个 turn。执行完成后再发原请求，仍返回同一身份，不再调用模型。

### 领取是自动恢复的分界线

启动多人 Host 时，recover 先于监听和工作线程执行。它逐条读取未结接单，结合原用户日志恢复。UserRuntime 加载时暂不自行关闭已登记在准入表中的 pending 回合，把这部分判断留给接单协调器。

恢复规则可以沿故障位置理解：

| 停在什么位置 | 当前恢复动作 | 是否再次调用模型 |
| --- | --- | --- |
| 只有 preparing，没有原 turn | 标记 admission_failed 并关闭请求键 | 否 |
| 原输入完整，尚未领取 | 校验冻结归属，补原准备；满足条件后保持或进入 queued | 由后续 worker 领取后调用 |
| 原请求已经取消 | 保存取消结果并结清 | 否 |
| claimed，但私人历史仍 pending | 以 INTERRUPTED 收口 | 否 |
| 私人终态已经保存，接单尚未 settled | 补教学交付等关联，修复接单索引 | 否 |
| 临时敏感确认候选已丢失 | 结束为需要重新确认 | 否 |

最重要的分支只有几行：

```rust
if row.state == "claimed" {
    self.end_pending(&mut user, &row, "INTERRUPTED", false)?;
    return self.update(&row, "settled", false);
}
```

摘录来自 [RunAdmissions::recover](../../../crates/server/src/run_admission.rs)。claimed 表示已经越过可执行边界，无法只凭接单表断定工具有没有产生副作用。即使进程刚领取、还没调用模型就退出，也采用这条保守的中断规则。它防止自动重复执行，不等于已经实现任意工具的恰好一次语义。

本轮 JSONL 用例分别在 preparing、pending、prepared、queued、claimed 和 terminal 注入失败后重新打开存储：未领取且输入完整的回合恢复排队；claimed 不增加模型调用；终态已保存的回合仅修复索引。测试保留了原问题次数和请求键身份。这里是显式故障返回与重开，不是断电实验。

### 执行退出、保存失败和释放聊天不是一回事

领取前，run_one 还会重新检查原材料资格、冻结输入、教学恢复条件和 ProviderBinding。ProviderBinding 固定协议、endpoint、model 和模型运行配置，不保存凭据。当前配置若已不能提供相同绑定，回合结束为 PROVIDER_BINDING_UNAVAILABLE，不会悄悄换模型继续；对应用例本轮已通过。

真正执行复用上一章的 execute_model，通过 NetworkUserPort 和 NetworkRunPort 访问原用户和现场。完成后 save_finished 保存原结果及必要关联，成功才把接单设为 settled。

若保存失败，执行线程可以退出，但原接单仍占着聊天和现场，unsaved 标志与内存 Unsaved 记录保留原结果。retry_save 使用原 prepared 和 finished 再提交，不重新采样。若私人终态已经成功、只剩后续关联失败，则按已保存终态修复。

取消也有两条路：queued 的回合可以直接写取消终态而不调用模型；claimed 的回合先持久记录 cancel_requested，再向活动令牌传播，等执行与收尾退出。delete_chat 与接单共用占位边界，未处理完的 preparing、queued、claimed 或未保存结果会使删除返回 CHAT_BUSY。删除成功后，引用该聊天的现场清除选择并换代，原请求键关闭。

本轮验证了三个具体顺序：排队取消没有模型调用；活动 Run 已保存笔记后取消，笔记保留，执行未退出时聊天仍忙；终态写入失败后重试保存，原回答成为 completed，模型调用计数没有增加。

## 19.4 用户公平调度与模型并发

### 接了多少任务、运行多少任务、调用多少模型

甲可以在不同现场为不同聊天排队，但不能靠多开窗口获得无限份额。当前 [ServiceLimits](../../../crates/server/src/service_limits.rs) 同时规定多个容量；配置来自服务根的 service-limits.json，缺省值如下。

| 资源 | 全服务默认值 | 每用户默认值 | 实际限制什么 |
| --- | ---: | ---: | --- |
| 未结准入 | 20 | 4 | preparing、queued、claimed 的总数，包含仍占位的未保存回合 |
| Run 执行份额 | 4 | 1 | 从领取前准备到执行、保存路径退出的 reserved 份额 |
| 模型许可 | 2 | 1 | 正在通过 LimitedAdapter 调用 Provider 的数量 |
| 预览、绘图、动画 | 各 1 | 各 1 | 三类分别计数的制作执行 |
| SSE 观察连接 | 40 | 4 | 已取得观察许可的连接 |
| 旧同步接口等待者 | 20 | 4 | 等待已接纳结果的 HTTP 调用者 |

queued_runs 这个字段名容易造成误读：实际 SQL 统计的是三个未结阶段，不只是排队列表长度。active_runs 也不是模型并发数。某个 Run 可以处于模型许可等待、工具执行或最终保存中，仍占执行份额；拿到模型许可才真正进入下一次 Provider 调用。

在默认配置下，即使某个用户有四个窗口和四个未结回合，也最多有一个 Run 取得执行份额。服务最多有四份这样的执行，最多两份模型请求同时进行。HTTP 普通接入仍用四个线程，但工作线程数取 active_runs；SSE 和旧同步等待另有线程及许可，因此普通读取不必跟随模型等待。

本轮同步入口用例让同一原 turn 的四个 `/agent/chat` 请求停在等待中，乙仍能读取聊天；第五个等待申请返回 202 和原 turn_id，转为异步观察。放行假 Provider 后，四个等待者得到同一答案，采样计数为一次。这个结果验证生命周期分离，不代表生产响应时间的分位数。

### 第一层公平：空闲执行份额在用户之间轮转

run_one 先从 SQLite 按 rowid 读取 queued 且未标记 unsaved 的记录。它跳过已经 reserved 的回合及已用满用户执行份额的 owner，再为每个合格用户保留最早的一项。

下一位用户的选择如下：

```rust
let next = users
    .keys()
    .find(|owner| state.last_owner.as_ref().is_none_or(|last| *owner > last))
    .or_else(|| users.keys().next())
    .cloned();
```

摘录来自 [RunAdmissions::run_one](../../../crates/server/src/run_admission.rs)。users 是 BTreeMap，选择从 last_owner 之后继续，没有后继则绕回。用户内部取最早记录，用户之间轮转；这与把所有窗口请求放进全局 FIFO 有不同结果。

确定 owner 后先登记 reserved，再退出准入状态锁，加载私人输入和发布。正式领取用带条件的 UPDATE，将仍为 queued、未取消、未标记 unsaved 的行改成 claimed，并记录 boot_id 和递增 attempt。若期间取消已生效，这次更新不会成功，也不会启动该 Run。

ActiveGuard 保证领取前返回错误或执行退出时释放 reserved；长模型调用不持准入状态锁。本轮用例让甲的第一个 Run 暂停，确认甲的第二个窗口不能再取一份；乙加入后，下一次轮转先服务乙，甲的第二项仍为 queued。

### 第二层公平：每次模型调用重新取得许可

只限制活动 Run 还不够。同一个 Run 可能采样多轮，也可能在工具内部做综合、压缩或结构化判断。若旁路直接调用 Provider，就会绕过模型并发限制。

run_one 把 Provider 适配器包在 LimitedAdapter 中，再交给共同执行核心。complete、complete_structured 和 chat 及其 observed 形式都进入同一个 call。取得许可的关键代码是：

```rust
let permit = self
    .resources
    .acquire_model(&self.owner, &self.cancellation);
if let Some(stream) = &self.stream {
    stream.resource_wait(false);
}
let _permit = permit?;
```

在这之前，流进入资源等待状态。取得 Permit 后重新检查取消和原材料授权，才调用内层 Provider；call 返回时 Permit 析构、减少计数并唤醒等待者。工具分派发生在模型调用返回之后，因此一次 Python 渲染不会继续占着已经结束的模型许可。

acquire_model 为请求登记 ticket，为每个尚有用户余量的 owner 选最早 ticket，再按 last_owner 轮转。全局模型数达到限制时，通过 Condvar 等待并释放资源状态锁。取消检查发现信号后移除该 ticket 并通知等待者；它不把一个已取消请求永远留在队首。

制作资源也按服务和用户计数，但算法不同。[presentation_sandbox::Execution::run](../../../crates/server/src/presentation_sandbox.rs) 每五十毫秒检查取消并尝试 try_acquire，取得许可后才进入沙箱。预览、绘图和动画分别有上限，这条轮询路径没有模型队列那样的用户轮转机制。不能从“都有限流”推导所有资源具有相同公平保证。

### 一个只分析次序的教学算例

下面使用明确的教学设定：只有一个 Run 执行份额和一个模型许可；甲的 A1、A2、A3 与乙的 B1 都在时刻零之前完成接纳，入队次序为 A1、A2、A3、B1；last_owner 为空。每项只调用一次模型，耗时四秒，忽略准备、存储、传输和本地计算。

| 策略 | 执行次序 | B1 开始与完成 | 四项开始前等待之和 |
| --- | --- | --- | ---: |
| 教学对照：全局 FIFO | A1、A2、A3、B1 | 第 12 秒开始，第 16 秒完成 | 0+4+8+12=24 秒 |
| 当前轮转规则在此设定下的次序 | A1、B1、A2、A3 | 第 4 秒开始，第 8 秒完成 | 0+4+8+12=24 秒 |

模型总工作仍是十六秒，平均开始前等待仍是六秒。改变的是等待由谁承担：乙不必排在甲的全部任务后面，甲的后续任务相应推迟。这个算例解释的是公平次序，没有制造额外吞吐量，也不是本轮性能测量。

再看默认的四个 Run 份额和两个模型许可。若四位用户各有一项已取得执行份额的任务，每项仅调用一次模型四秒，且同时竞争模型，则两批请求可在理想设定下用八秒完成。两份后取得许可的任务各等待四秒，累计资源等待八秒；这些等待在不同线程上重叠，不能再加到八秒墙钟时间上。

真实运行仍要像上一章那样拆时段。接单排队是在取得 Run 份额之前，模型许可等待发生在已活动 Run 内部，Provider 调用墙钟时间又包含模型服务和上游网络等待；锁等待、磁盘提交、制作执行与下行传输分别计量。LimitedAdapter 位于模型活动观察包装之内，因此模型活动时长可能包含许可等待，不能直接读成 GPU 计算时间。

### 用量记录与硬额度是不同合同

RunUsage 的 calls 逐次保存可选 ModelUsage，known_total_tokens 累加已知总量。一次请求若收到多份累计 usage，call 保留最后一份；若没有流式 usage，chat 可从 AssistantTurn 的总量补齐；仍未知时保留 None。

当前实现没有用单 Run 的累计调用次数或 Token 数触发停机。每次请求有 output_token_limit，但累计账本不自动缩小下一次输出限额。对应 [ADR-0147](../../adr/0147-linux-multi-reader-service-without-redis.md) 的修订引用持续执行约定，不能把早期预算设想写成现行硬配额。

本轮固定 Provider 用例报告两次各 120,001 tokens，中间保存一条笔记；最终记录 240,002，Run 正常完成，模型许可已经释放。这是测试输入与断言，既不是实际模型消耗，也不能用于费用估算。该用例说明当前累计用量的作用是记录，而不是停止条件。

## 19.5 现场回收、恢复和未来扩展条件

### 刷新、复制标签页和接管表达三种意图

甲刷新电脑页面，希望回到原位置；把标签页复制一份，希望获得一个可以独立滚动的新现场；明确接管则希望原页面失去控制资格。只保存 workspace_id 无法区分这三种情况。

[WorkspaceStamp](../../../crates/server/src/workspace_registry.rs) 包含 attachment_id、generation 和 expected_revision。attachment 指认页面实例及被允许的附属视图；generation 判断现场是否换代；revision 判断本次修改是否基于仍然有效的已提交状态。

当前 attach 逻辑在原现场仍绑定另一个 attachment 时创建分叉，复制现场检查点和聊天选择，但分配新的 workspace_id。相同 attachment 的刷新可以继续原现场。takeover 明确换代并更新主 attachment，使旧页面的读写请求失效。演示附属页则通过 linked/attach 接到原现场，校验原聊天、turn 和已交付版本，不自动创建另一段聊天。

普通状态读取与写操作也有区别。reader/state、chat/history、部分画像和来源读取要求 attachment 与 generation 有效，可以接受旧 expected_revision，以便读到服务器的新状态；修改 Reader 或 checkpoint 则要求 revision 相等。当前 [MU12 用例](../../../crates/server/src/tests/mu8_tests.rs) 已验证旧 revision 可读最新现场，但同一 stamp 写入会冲突，错误 attachment 或旧 generation 连读取也不能通过。

保存检查点时，persist 使用当前 revision 作为更新条件，提交成功才推进内存 revision。Reader 命令先对单次操作的候选 Reader 修改，检查点失败就恢复旧可见 Reader。这种局部候选位于受控操作内部，与上一章反对的“复制整轮应用、模型结束后整体写回”具有不同范围。

### 回收释放内存，保留持久归属

现场不会一直常驻。默认上限为全服务二十个、每用户四个；闲置阈值为十五分钟。evict_idle 只回收注册表独占句柄、已经闲置且没有 preparing、queued、claimed 占位的现场。每次成功的相关现场命令已经保存检查点，回收不删除聊天或学习事实。

再次加载时，scene 按原 PublishedBookRef 读取材料，由检查点恢复 Reader，恢复仍存在的聊天和演示状态，并增加 generation；主 attachment 和 linked 集合重新建立。若选中的聊天已经不存在，则清理该选择及相应演示现场。旧页面不能凭曾经合法的 stamp 再次控制恢复后的实例。

新建独立现场时，create_bound 可以读取同用户、同确切发布的最近检查点。最近由服务端 checkpoint_seq 决定，persist 在事务内取得下一个序号，不使用手机和电脑的本地时钟排序。新独立现场可以继承阅读位置，但该路径会清除演示现场，也不会自动复制某个当前聊天选择；显式 fork 才复制所选聊天和相应检查点。

本轮回收用例先用极大的 client_time 保存一个位置，再用更小的 client_time 保存另一个位置，第三个新窗口继承后者。它随后推进测试使用的 Instant，回收三个闲置现场，而运行端口持有的第四个现场和 Book 仍在；重新 attach 后原位置和发布恢复，generation 变大。这里没有真的等待十五分钟。

用户实例采用另一套条件：默认最多常驻十个用户，闲置阈值三十分钟。UserRegistry 在需要加载新用户时尝试淘汰；只有没有外部句柄，并且没有有效待确认操作、pending 回合、运行中的复核或历史回填等工作，才由 prepare_eviction 冲刷已读并允许卸载。未保存结果持有 UserHandle，所以不会因“最近没有 HTTP 请求”而失去原私人权威实例。

### Book 缓存不能只数缓存表里有几个强引用

回到甲乙共享的书。关闭一个窗口不代表 Book 已经无人使用；在途 Run 仍可能持有它。若缓存只计算自己的强引用，把旧 Book 从 LRU 中删除就当作释放，会低估真实存活材料。

[ResidentEntry](../../../crates/server/src/published_library.rs) 同时保存 Weak<Book> 与可选缓存强引用。缓存淘汰可以放下自己的 Arc，但只要现场或 Run 仍持有 Book，resident_usage 继续把该项计入预算：

```rust
self.residents.retain(|_, e| e.book.strong_count() > 0);
(
    self.residents.len(),
    self.residents.values().map(|e| e.bytes).sum(),
)
```

默认材料预算是二十份存活发布与 2 GiB 的计费量，两个条件共同生效。新材料加载需要腾出容量；若能放下的缓存引用都已放下，仍有窗口或 Run 占着预算，则返回 BOOK_CAPACITY。

这个字节数来自 [Book::resident_budget_bytes](../../../crates/read-tools/src/lib.rs)：它结合原文、索引及公开结构序列化大小等估算加载成本。它是准入计费量，不是进程 RSS 采样。甲乙读取同一发布可复用同一 Book，但他们的私人状态、Reader 和 Run 上下文仍各有成本。

### 恢复观察不等于让执行倒带

服务重启后，原现场可从检查点恢复，聊天可从 JSONL 重开，接单可按阶段对账，SSE 却不能假装旧内存事件还在。[RunStream::cursor](../../../crates/server/src/agent_stream.rs) 将 observation epoch 与序号一起解析；旧 epoch 返回重新取快照的路径，新快照带 live_buffer_reset。

本轮观察用例先订阅 queued 回合，执行后得到 saved 终态，再重开服务并携带旧游标连接。返回的是新观察代次的快照，仍指向原已保存回合，Provider 计数没有增加。重连恢复的是“我能看见什么”，不是“把原问题再执行一遍”。

[ControlStore](../../../crates/server/src/control_store.rs) 与 ServiceWriter 给这些行为规定了部署边界。一个服务根先取得文件写入者锁，服务和遵守同一协议的离线维护工具不能同时拥有写资格。每个 ControlStore 使用自己的连接，设置 WAL、synchronous=FULL、foreign_keys=ON 和五秒忙等待；当前运行的答案和私人事实仍通过各自的权威入口保存。

[ADR-0147](../../adr/0147-linux-multi-reader-service-without-redis.md) 因此选择一个 Rust 主服务、服务级 SQLite 和进程内注册表与调度，不引入 Redis 首版。这个取舍对应小范围受邀阅读和单机运行条件：接单耐久性已经有明确归属，通知也不需要成为业务真相。

如果以后需要多个后端同时领取，首先要定义跨进程的领取与租约、共享私人写入口、失联执行及副作用确认，再决定使用什么协调设施。如果瓶颈是数据库写争用，则需要测量事务等待和提交成本；如果是模型等待，换数据库不能增加 Provider 容量；如果是大量存活 Book，就要分析材料计费、实际内存和现场生命周期。Redis、其他数据库或独立 Worker 只有在解决对应约束时才有价值。

## 已知边界与本轮验证

本章于 2026-10-07 回读当前工作区，Git 基线为 4e0b68e。正文的实现结论回到当前文件；ADR 用于解释方向与历史取舍。四秒模型、十六秒与八秒排程都是教学假设，没有把测试耗时当成容量测量。

1. **公平选择不提供等待时间上界。** 当前 Run 和模型都不抢占已经取得的工作。四个长 Run 可以一直占据四份执行资格，后来用户要等资格释放；模型轮转只在已经到达该队列的请求间生效。预览、绘图和动画使用轮询竞争许可，没有同样的轮转保证。当前也没有按用户累计金额或 Token 的硬额度。

2. **本机容量上限不是服务能力验收。** 常驻用户、现场、Book、未结接单和连接各有上限，但历史与已结接单会继续增长，完整 Run 上下文也不包含在 256 KiB 事件队列限额中。Book 字节是估算计费量，未保存结果仍占私人资源；本轮没有做混合负载、真实 Provider、长历史或进程内存评测。

3. **多份存储没有共同事务。** 接单通过准备与对账恢复，已领取的不明执行以中断结束。Reader 检查点失败可以恢复可见 Reader，却不表示此前私人 Store 的写入同时回滚。第 18 章确认的笔记/高亮缺口也适用于这类顺序：私人保存成功、后续 Reader 动作失败时，当前分派可能不把该写入放入 effects，不能从效果摘要为空推断无副作用。

4. **授权复核与取消都发生在执行边界。** 退出登录撤销观察资格，不自动取消已接纳 Run；账号禁用或材料撤权会在后续相应检查点阻止继续访问。已经进入的同步网络读、磁盘提交和 socket 写入不能由这些检查即时抢断。本轮没有测量静默连接上的停止延迟，也没有验收真实 HTTPS 代理。

5. **恢复保留原绑定。** 现场冷加载需要重新附着，Provider 绑定不可用会结束原回合，丢失的临时确认不能自动恢复。默认发布改变不替换旧现场；ADR 中视频同源补齐自动接入仍标为待实现设计，不能从当前默认指向推导自动升级行为。

6. **三项旧授权测试在夹具准备时失败。** 当前 mu4_tests::Fixture::seed_private 向历史快照入口直接保存人工聊天；服务用户已经创建 JSONL 目录，save_agent_history_path 因此返回 SESSION_EVENT_WRITE_REQUIRED。三个选中 MU4 用例都未到授权断言，不能计为授权通过，也不能据此认定线上越权。本轮仅记录，没有修改产品测试或实现。

实际执行共 29 个不同的 Server 定向既有用例：第一组 26 个中 23 个通过、3 个出现上述夹具失败；随后只补充 3 个采用当前会话路径的归属与观察许可用例，均通过。合计 26 个通过、3 个失败，0 忽略。

## 面试时怎样解释本章

1. **从单用户改为多用户，为什么不是给 AppState 加一个 user_id？**

   因为私人数据和阅读现场有不同的共享单位。同一用户的多个窗口应共用一个私人权威实例，各窗口分别拥有 Reader 和材料绑定；不同用户再分别拥有私人状态。当前网络 Host 用用户、现场、书库和接单注册表组合服务，而 Run 固定原归属，通过端口访问这些对象。

2. **怎样防止客户端指定另一个用户或服务器目录？**

   身份由应用登录生成 Principal，业务正文不能提供 owner 或私有目录。路由能力表先限定可调用操作，对象查找再带可信 owner，材料按确切发布授权。正文、PDF、图片、演示和 SSE 各自经过对应检查，不能把难猜 ID 当成访问许可。

3. **两个窗口都选中了同一聊天，能并行提问吗？**

   Reader 仍独立，但当前准入规定同一聊天和同一现场各只有一个未结 Run。另一请求会得到忙碌响应；任务处于未保存状态也继续占位。若未来要同聊天分叉，需要另行定义消息顺序和合并语义，不能只增加 worker。

4. **服务返回 202 前究竟保存了什么？**

   先在 SQLite 建立带请求键和归属的 preparing 记录，再把问题、冻结输入和历史位置写入私人日志，复用或提交必要教学事件并记录准备完成，最后转为 queued。202 表示该问题已经可按原身份领取，不代表模型已开始或答案已完成。

5. **为什么 queued 可以恢复，claimed 通常不能自动重跑？**

   未领取且输入完整时，系统能从原日志重建输入；已领取后，工具可能已产生副作用，接单表不能证明哪些动作尚未发生。因此 claimed 的 pending 回合以中断收口，已保存终态只修索引。队列耐久性与工具恰好一次是不同问题。

6. **有四个工作线程，为什么模型并发默认只有两个？**

   Run 份额覆盖准备、模型许可等待、工具和保存；模型许可只覆盖一次 Provider 调用。两层分别设全局和每用户上限，并按用户轮转。工具执行期间释放模型许可，下一次采样重新申请，使长任务内部的多次调用也进入共享资源安排。

7. **公平调度能保证新用户很快得到回答吗？**

   它决定有空闲份额时优先选谁，不能缩短已经运行的请求，也不承诺按秒或按 Token 平分。没有空闲 Run 份额时，新用户仍要等待；任务进入模型队列后才参与第二层轮转。应分别观察准入等待、模型等待和实际执行时间，再判断瓶颈。

8. **怎样避免一个旧 Agent 动作把用户的新位置覆盖掉？**

   generation 阻止切书、换聊天或接管后的旧现场访问；网络端口的 effect_revision 进一步阻止同代次内覆盖用户的新操作。旧 Run 仍可以读取新 Reader，但不一定能应用旧动作；原书私人结果和原聊天回答另按自己的归属保存。

9. **为什么首版不需要 Redis？什么时候重新考虑？**

   当前一个 Rust 服务管理一个写入根，SQLite 保存接单与服务元数据，私人日志保存业务事实，进程内完成注册表、许可和观察。需要多个后端协调、独立 Worker 或实测共享缓存时，才重新确定协调与恢复合同；换通知设施不会自动解决跨存储提交或工具重复执行。
